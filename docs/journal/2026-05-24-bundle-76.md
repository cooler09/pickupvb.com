# 2026-05-24 — Bundle 76: Complete server-side analytics capture set + PII guardrail test

## Context

Bundle 75 shipped the `AnalyticsPort` scaffolding, PostHog adapter, and
the first two captures (`event_published`, `event_joined`). The audit's
P1 #2 taxonomy lists seven events; five remained unwired. This bundle
finishes the server-side capture set and closes P1 #4 by adding a
domain-layer Vitest that pins the `AnalyticsTraits` surface to a small
non-PII allowlist.

The user asked for "A and C" off the menu of follow-ups: (A) finish the
server-side captures, (C) add the PII guardrail test.

## Decisions

- **Capture at the existing server-action seam, not via a
  domain-event outbox.** The outbox pattern (audit P2 #6) is the right
  long-term answer but it's a separate refactor — wiring the
  remaining five events at the action layer keeps Bundle 76 small and
  lets us start collecting data immediately. Each call site is one
  `analytics.capture(...)` line plus an import.
- **`event_left` reuses a shared `loadEventAnalyticsContext` helper.**
  Bundle 75's `captureEventJoined` had its own narrow Supabase query;
  rather than duplicate it for `captureEventLeft`, we extracted a
  single loader returning `{ hostId, priceCents, metroId }`. Anything
  we add later (`event_cancelled`, `event_modified`) reuses the same
  shape.
- **`event_left` reports `byPosition: false` for now.** There is no
  leave-by-position UI today; both leave paths (refund-success and
  unpaid-leave fall-through) bypass position bookkeeping. Noted in a
  one-line code comment + the audit remediation log so the next agent
  knows to revisit once positional leave exists.
- **`checkout_started` fires at all four payment surfaces.** Tickets
  (`checkout-actions.ts`), tips (`tip-actions.ts`), ad-hoc team
  registrations (`team-checkout-actions.ts`), and roster-mode team
  payments (`roster-team-checkout-actions.ts`). The guest variants
  (`startGuestTicketCheckout`, `startGuestTipCheckout`) tail-call
  their authed counterparts after minting an anon session, so the
  single capture covers both flows. Each insertion sits immediately
  before `redirect(session.url as Route)`, after every domain guard
  has passed, so we never count an abandoned-before-Stripe flow as a
  checkout start.
- **`checkout_completed` lives in the Stripe webhook.** Mirrors the
  four `meta.kind` branches in `handleCheckoutCompleted` (attendee,
  tip, team_registration, roster_team_payment) and maps each onto
  the taxonomy's `kind: 'ticket' | 'tip' | 'team'`. The metadata
  carried by some checkout sessions doesn't include `host_id`
  (attendee and roster_team_payment kinds in particular), so a small
  `lookupHostId(eventId)` helper does one admin-client query when
  missing. The capture fires only after the DB write succeeds — a
  failed `markPaid` will throw before the capture, which is the
  right ordering (PostHog tracks completed payments, not attempted
  webhook handlers).
- **`host_payout_setup_completed` fires on every `account.updated`
  where `charges_enabled === true`.** The strictly-correct semantics
  would be "false → true transition", which requires reading the
  prior mirror state from `host_stripe_accounts`. Pragmatic call: the
  cost of overshooting is duplicate PostHog events (deduped at the
  dashboard layer by first-occurrence-per-actor filters), the cost
  of undershooting is missing the entire payout-enable funnel.
  Documented as a known leniency in the audit remediation log so the
  follow-up bundle that adds prior-state comparison is easy to
  scope.
- **`signup_completed` splits on `app_metadata.provider`.** OAuth
  callers (`google`, `apple`, `facebook`) map to
  `method: 'oauth'`; everything else (including email magic-link)
  maps to `method: 'email'`. The taxonomy's third option,
  `anon_claim` (anonymous shell → real email upgrade), needs prior
  state tracking through the conversion flow and is explicitly
  deferred — `auth/callback/route.ts` doesn't know whether the user
  arrived from an anon session.
- **New-account detection uses a 60-second `created_at` heuristic.**
  Same callback fires for new signups AND for OAuth re-auths after
  session expiry. Distinguishing them without persistent server
  state requires checking `Date.now() - user.created_at < 60_000`.
  Imperfect (slow callbacks could miss the window) but
  good enough — false negatives are signups we don't count, not
  duplicate captures.
- **PII guardrail = type-level Vitest, not a runtime check.** The
  `AnalyticsPort.identify(actorId, traits)` signature already
  accepts only `AnalyticsTraits`, so the compiler enforces the
  allowlist. The risk is someone broadening the interface (adding
  `[k: string]: unknown`, adding a permissive new field, etc.) The
  test pins `keyof AnalyticsTraits` to the exact four-key allowlist
  via `expectTypeOf().toEqualTypeOf<...>()` and uses
  `@ts-expect-error` on six common PII names (`email`, `displayName`,
  `phone`, `fullName`, `ipAddress`, `address`). Both directions
  fail compilation if the interface drifts. No runtime overhead.

## Patterns surfaced

- **Per-action mini-loaders compose well.** `loadEventAnalyticsContext`
  is the second consumer of the same `select host_id, location_city,
event_divisions(price_cents, sort_order)` shape introduced in
  Bundle 75. If a third capture (`event_cancelled`?) needs the same
  context, promoting the loader into `_loaders/` becomes worthwhile;
  for now co-locating with `rsvp-actions.ts` matches the
  page-decomposition convention.
- **Webhook captures are the right home for "settled" funnels.**
  `checkout_completed` and `host_payout_setup_completed` only have
  meaning after the Stripe state machine settles. Putting them in
  the webhook means we capture exactly once per real-world
  outcome, not once per user button-click. Trade-off: each capture
  needs to derive its actor id from session metadata
  (`user_id` / `captain_id`) rather than from a request-scoped
  Supabase session.
- **`@ts-expect-error` is a load-bearing test primitive.** The PII
  guardrail test would silently succeed if PostHog's adapter were
  later changed to accept arbitrary props, but a `@ts-expect-error`
  on a still-valid line fails compilation and surfaces the drift
  immediately. Cheap, zero-runtime guard.
