# Bundle 67 — 2026-05-23 — Remote Turbo cache (Organization P2, Wontfix-by-design)

## Context

The Organization audit's P2 "No remote Turbo cache configured" was
filed with the framing: _"Every CI run rebuilds from scratch; the
Vercel free remote cache would meaningfully cut PR feedback time."_
That premise is worth testing against the current build, not
inherited at face value.

Measured locally on an M-series Mac after `rm -rf .turbo/cache`:

```
Tasks:    8 successful, 8 total
Cached:    0 cached, 8 total
  Time:    32.632s
```

A clean-cache `pnpm build` runs **8 turbo tasks in 32.6s**. CI
wall time on top of that is bound by:

- `actions/checkout@v4` — a few seconds.
- `pnpm/action-setup@v4` + `actions/setup-node@v4` with
  `cache: pnpm` — usually 10–30s combined including pnpm-store
  cache restore.
- `pnpm install --frozen-lockfile` — even with the pnpm cache hit,
  10–30s of link/verify work.

That's 30–60s of fixed overhead that remote cache cannot touch. The
turbo phase remote cache _could_ help with is already <33s on a
cold machine. The realistic best case is shaving 10–20s off PR
feedback while introducing a live runtime dependency on the Vercel
cache server, GitHub secret rotation hygiene (`TURBO_TOKEN` and
`TURBO_TEAM`, plus `TURBO_REMOTE_CACHE_SIGNATURE_KEY` if signed
mode is enabled), and an extra signed-cache attack surface (cache
poisoning is a real category once a third party can serve build
artifacts back into CI).

Same shape as the Bundle 59 composite/project-refs close: the
audit's own premise ("would meaningfully cut feedback time")
doesn't survive measurement. Closure type: Wontfix-by-design with
a quantitative re-open trigger.

## Pattern notes

### Always measure before adopting a "free perf win"

The audit's framing assumed remote cache was a no-brainer because
the Vercel free tier exists. Measurement showed the cache lives on
the wrong side of CI's actual bottleneck — install + node setup.
Pattern: when an audit prescribes a "free" optimization, the first
move is to time the thing being optimized. The cost only gets paid
once; the operational complexity gets paid forever.

### Wontfix-gated vs. Wontfix-by-design distinction holds up

This is the fourth Wontfix-by-design close in the recent run
(Bundles 58, 59, 67) alongside one Wontfix-gated-on-release-cadence
(Bundle 60). The split is useful:

- **Wontfix-by-design** = the thing being prescribed is genuinely
  not a win given current evidence; re-open requires the underlying
  measurement to change.
- **Wontfix-gated** = the thing might be a win but only after an
  unrelated external event (release event, contributor influx,
  Vercel team formation, etc.); re-open requires that event.

Both produce closure, but the re-open trigger lives in a different
place. Keeping the labels distinct in audit status blocks helps
future readers know which lever they're looking for.

### Audit-fully-closed milestones are worth flagging

This is the second audit to reach **✅ Fully closed** status
(after Documentation in Bundle 61). Worth calling out explicitly
in the audit's status block and the README row so the next
sweep knows to skip it unless something changes. The README index
becomes the working "what audits actually have open work" filter.
