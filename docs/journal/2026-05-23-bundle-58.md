# Bundle 58 — 2026-05-23 — CI Supabase placeholder keys (Organization P3, Wontfix-by-design)

## Context

The Organization audit's "CI uses hardcoded Supabase placeholder keys"
P3 sat in an ambiguous state: the audit body said _"Either leave
as-is (cheap and clear) or wire a real CI Supabase via the GitHub
Action"_ — i.e. the audit itself proposed two acceptable answers and
left the call open. The Open questions block phrased it as "intentional
fast-CI or worth a real CI Supabase?" Six months on, the answer is
clear from how the project actually operates: `smoke-prod.yml` covers
real-Supabase regressions after deploy via Playwright against the live
URL, so the CI build is genuinely a build-correctness check, not a
runtime check. Wiring a real CI Supabase would burn shared quota and
require a long-lived service-role secret without catching anything the
post-deploy smoke doesn't already catch.

This bundle closes the P3 as Wontfix-by-design and codifies the
rationale in `ci.yml` so the next reader doesn't "fix" it back to a
real key.

## What shipped

### `.github/workflows/ci.yml` (edit)

Twelve-line comment block prepended to the `Build` step explaining:

- The two env vars are deliberate placeholders, not secrets.
- `next build` requires them to be _present_ at import time (the
  Supabase browser client throws on import otherwise) but doesn't
  issue real requests during the build.
- Real-Supabase validation is intentionally deferred to
  `smoke-prod.yml` post-deploy.
- Pointer to the audit entry so the rationale is one click away.

The placeholder values themselves are unchanged — same `https://placeholder.supabase.co`
URL and `sb_publishable_placeholder` key already in tree.

## Pattern notes

### Wontfix-by-design is a real audit outcome

The audit-grading rubric is P1 / P2 / P3, not P1 / P2 / P3 / Wontfix.
But several open P3s in this repo are best closed with a documented
"we deliberately don't do this and here's why" rather than left
open forever. The right shape is:

1. Flip the finding header to "✅ Closed Wontfix-by-design" with the
   date and bundle.
2. Keep the original Where/Issue/Fix lines intact (so the audit
   history is preserved).
3. Add a "Resolved:" paragraph explaining the deliberate choice and
   pointing at the system that fills the gap (here: `smoke-prod.yml`).
4. If the audit was the surface where someone would otherwise "fix"
   the perceived issue (e.g. swap placeholders for real keys), land
   a code comment at the call site so the choice survives without
   the audit being open.

Reference fixes in this repo following the same shape: Security P3
#11 (preemptive upload hardening, Bundle 53) and SEO P3 `og:type`
(Bundle 54). Both closed as Wontfix with explicit re-open triggers.

### Re-open triggers matter for Wontfix-by-design closures

The rationale ("smoke-prod.yml covers real-Supabase regressions") is
the right answer _today_. If `smoke-prod.yml` is ever disabled or
loses its Supabase coverage, the closure logic evaporates. The
comment in `ci.yml` deliberately calls out `smoke-prod.yml` by name
so a future grep for "smoke-prod" surfaces the dependency. Worth a
sweep next organization audit: any Wontfix that depends on another
workflow / system should be re-checked when that workflow changes.
