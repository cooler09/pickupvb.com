# Bundle 9 — Event detail page side-load parallelization

_Date: 2026-05-24_

## Context

After Bundle 8 closed the lint-coverage P1, the cross-audit survey
pointed to the [performance audit](../audits/performance.md) as the next
high-leverage P1. The audit lists four P1s for the event detail page:

- **P1 #0** React Compiler purity + setState-in-effect — already closed
  by Bundle 2.
- **P1 #1** `force-dynamic` regression on three public pages —
  `apps/web/src/app/events/[id]/page.tsx` is _not_ one of them, so this
  page isn't currently opting out of caching itself.
- **P1 #3** sequential web-push fanout — already closed.
- **P1 #4** event detail page does ~14 DB roundtrips — open.

P1 #4 is the only event-detail-specific P1 with measurable user-facing
impact. The audit estimates 300–800 ms warm-cache per render. Cleanest
split: the page-level orchestration (multiple sequential `await` waves)
vs. the infrastructure `getDetail()` repository (two large parallel
rounds against Supabase). The page side is purely an orchestration
refactor — no read-model changes, no migration — which makes it the
right scope for one bundle. The infrastructure side wants
JOIN-consolidation against co-host profiles + team captains and is left
for a follow-up.

## Scope

Edits all in [event detail page.tsx](../../apps/web/src/app/events/%5Bid%5D/page.tsx):

1. **Collapsed four-to-six sequential side-load waves into two.** Before:
   `getEventPricing` → 5-way `Promise.all` (breakdown / viewerIsPro /
   tipTotal / payments / viewerPaymentStatus) → ad-hoc registrations →
   ad-hoc captain profiles → eligible-winning-teams → primary-host
   social. After:
   - **Wave 1 (6 things in parallel):** `getEventPricing`, viewerIsPro,
     tip-jar total, primary-host social, eligible-winning-teams map,
     ad-hoc bundle.
   - **Wave 2 (3 things in parallel, only fetched when paid):**
     breakdown, host payments map, viewer payment status.
2. **JOINed captain profile into the ad-hoc registrations query.**
   Replaced the post-fetch `profiles` lookup with a nested select using
   the `event_team_registrations_captain_id_fkey` relation. The ad-hoc
   sub-bundle now resolves in a single RTT instead of two.
3. **Folded each side-load into a typed IIFE inside the parallel
   block** so the destructuring at the top stays flat and the per-load
   logic stays co-located. `AdHocBundle`, `EligibleTeamOption`, and
   `SocialHandles` are the only new local types.

## Decisions

- **Page-level fix only; left infrastructure `getDetail()` for a
  follow-up.** Splitting at the `apps/web` ↔ `packages/infrastructure`
  boundary means no read-model contract change, no test-data drift, and
  no migration. The infrastructure-side change wants JOINing
  `event_co_hosts → profiles`/`groups` and JOINing teams → captain
  `profiles` — both touch the read-model assembly path and deserve
  their own diff with focused review.
- **Two waves, not one.** Wave 2 (breakdown / host payments / viewer
  payment status) all gate on `paid`, which is derived from the pricing
  config that only wave 1 can fetch. Considered relaxing the gates to
  always over-fetch — would have saved one wave but charges every free
  event a host-payments scan. Wave 2 is free-event-free, so it's a net
  win to keep the gate. Free events finish in 1 wave; paid events in 2.
- **JOIN captain profile rather than parallel sub-fetch.** Both options
  reduce ad-hoc RTTs from 2 to 1. JOIN is the right shape because
  captain id is a single-valued FK with `references profiles(id)`; the
  Supabase PostgREST relation is exact-match on the FK constraint name.
  Bonus: the captain payload arrives in the same RTT as the
  registration row, so there's no chance of the two getting out of
  sync between waves.
- **IIFE-per-side-load over hoisted helper functions.** Each side-load
  reads `event.id` / `user` / `event.canManage` from the surrounding
  closure; hoisting would force passing 4–6 props each. IIFE keeps the
  side-load definitions next to the destructured names. The downside is
  ~20 lines of inline `(async () => { ... })()` syntax, which is
  acceptable given the alternative.

## Patterns observed

- **Page-level "Promise.all everything at the page boundary" pattern.**
  This is the second page to follow it (the events listing was the
  first); worth promoting if a third lands. The reusable shape is
  "after the domain read model returns, gather every independent
  side-load into one `Promise.all` of typed IIFEs, gated only on data
  that's already in the read model." Anything gated on a previously
  awaited fetch goes in the second wave.
- **Audit P1s often split cleanly along package boundaries.** P1 #4
  reads "the event detail page does X" but the X spans the page
  orchestration _and_ the infrastructure aggregator. Splitting at the
  package boundary gave a contained bundle with no migration / no
  read-model change and the larger half scoped as a clean follow-up.
  This is a generalizable bundling rule: when a P1 spans both
  `apps/web` and `packages/infrastructure`, ship the page-level half
  first.

## Follow-ups deferred

- **Infrastructure `getDetail()` JOIN consolidation.** The two parallel
  rounds together issue ~17 queries. Targets:
  - JOIN `profiles` + `groups` into the `event_co_hosts` select so
    co-host detail arrives in one query instead of three.
  - JOIN captain `profiles` into the `event_teams` select (via the
    nested `teams!inner` relation) so team captain detail arrives in
    one query instead of two.
  - Replace the per-team `team_members` row count with a `count`
    subquery (or a view) so member counts arrive inline with teams.
  - Aim for ≤3 queries total inside `getDetail()`. Add before/after
    timings from the Supabase slow-query log per the audit's note.
- **OG image route caching (P3 #11).** Cheap follow-up: set
  `Cache-Control: public, max-age=3600, immutable` on each OG route.
  Now that the page itself is faster, the OG-render-on-share path is
  the next bottleneck for newly-shared links.
- **`isPro()` per-render memoization (P3 #12).** With the parallel-wave
  refactor, `hasProBenefits` is still called twice per render (once for
  the host inside `attendeeChargeBreakdownAsync`, once for the viewer in
  the wave 1 block). Wrapping in `React.cache()` would dedupe across
  the render but the two calls take different user ids so they wouldn't
  benefit from a single shared cache — left as an open question.
