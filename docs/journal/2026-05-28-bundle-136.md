# Bundle 136 — Dropdown menu on Radix (2026-05-28)

Eighth M3-adoption bundle. Closes the Menu-pattern half of audit
**P2 #12 "`<details>` / popover patterns used where M3 prescribes
Menu"** by migrating `<NavDropdown>` — the desktop header's
Community / Account / etc. dropdowns — onto
`@radix-ui/react-dropdown-menu`. Public API preserved exactly so
the one consumer ([site-header.tsx](../../apps/web/src/components/site-header.tsx))
needed zero edits. Content-panel disclosures (notification bell
panel, host-panel `<details>` blocks) are not Menu-pattern targets
and stay as-is.

See [docs/audits/m3-alignment.md § Bundle 136](../audits/m3-alignment.md#bundle-136--dropdown-menu-on-radix-2026-05-28)
for the line-by-line decision log.

## Context

[P2 #12](../audits/m3-alignment.md#12-details--popover-patterns-used-where-m3-prescribes-menu)
flagged that the header's `<NavDropdown>` hand-rolled the focus
management Radix would have given us for free — Escape-to-close,
click-outside dismissal, route-change close — but skipped the
features Radix would have added: arrow-key navigation, typeahead,
roving tabindex, focus return on close. That's the textbook case
for adopting the headless primitive.

The Bundle 132 (Toast) and Bundle 134 (Dialog + BottomSheet) Radix
bundles established the convention now documented in AGENTS.md:
preserve the public API exactly, bridge `data-state` to M3 motion
via CSS keyframes consuming Bundle 129 tokens, compose `state-layer`
(Bundle 131) where applicable. This bundle is the third application
of that convention.

## Decisions

- **Public API frozen.** `NavDropdown({ label, items, hasIndicator,
indicatorLabel })` + `NavDropdownItem { href, label, badge? }`
  unchanged. site-header.tsx untouched. Matches Bundle 132 + 134
  pattern: a Radix migration should not be a call-site migration.
- **Controlled `open` state, not Radix's uncontrolled default.**
  Radix would happily own the open state, but we need to close on
  Next.js route change (trigger stays mounted across client-side
  nav) and that requires an external signal. `useState(open)` +
  `<Root open onOpenChange>` is the only shape that lets the
  pathname effect run.
- **rAF-deferred setState in the pathname effect.** AGENTS.md
  Pattern 5 (added with Bundle 133's hide-on-scroll work) forbids
  synchronous setState in an effect body. Wrapping the
  `setOpen(false)` in `requestAnimationFrame` matches the Bundle 133
  pattern and keeps the linter at 3 pre-existing warnings.
- **`Item asChild` wrapping `<Link>`** rather than nesting `<Link>`
  inside Radix's default `<div role="menuitem">`. Keeps the link
  itself focusable, which is what Radix's roving-tabindex expects.
  Typed routes survive because `<Link href>` is the actual rendered
  child.
- **Two paint paths for the active item.** Bundle 131 `state-layer`
  paints the mouse-hover overlay; `data-[highlighted]:bg-fg/5`
  paints the keyboard-focus highlight (Radix tags the
  arrow-key-active item with `data-highlighted`). Single
  `data-highlighted` -based paint would lose the M3 hover surface;
  single `state-layer` -only paint would lose keyboard discoverability.
- **`md-menu-motion` keyframes anchored to the trigger.** Setting
  `transform-origin: var(--radix-dropdown-menu-content-transform-origin)`
  uses Radix's computed origin (from the resolved popper `side` +
  `align`) so the scale-in feels attached to the trigger. Centered
  scale would have the menu "land" rather than "unfold" — the M3
  Menu motion intent.
- **Shorter durations than dialog.** Menus on `medium2` enter feel
  laggy. `short4` enter / `short3` exit matches the M3 Menu motion
  spec and matches the Bundle 132 toast family's pacing.
- **Notification-bell panel + host `<details>` are not menus.** They
  carry multiple sections, scroll, rich link rows. A Menu primitive
  would lose layout flexibility. Bundle 128 already converted the
  `<details>` blocks that were really dialogs; the rest are inline
  content. If a Popover primitive ever lands, the bell panel is the
  obvious candidate.

## Patterns observed

- **The "two paint paths" thing is a Radix property in general.**
  Anywhere a Radix primitive has both `:hover` (CSS) and a
  data-attribute-driven highlight (Radix), both need styling. Bundle
  134's Dialog Close button does the same dance: `tap-target` +
  `state-layer` for hover, `focus-visible:ring` for keyboard focus.
- **`--radix-*-content-transform-origin` is the right anchor for
  any anchored popper motion.** Tooltips, popovers, submenus, hover
  cards — they all expose a `-transform-origin` CSS variable. Use
  it instead of guessing the origin.
- **`Item asChild` is the typed-route-safe item.** Any future
  migration of `<details>` -based dropdowns to Radix Menu should use
  this pattern verbatim.
- **Controlled-open is unavoidable when you need a client-side route
  signal.** Radix's uncontrolled `Root` is convenient but is opaque
  to external effects. The cost is one `useState` + one `useEffect`
  — small.

## Follow-ups deferred

- **`@radix-ui/react-popover` for the notification bell panel** —
  separate audit item if the bell ever needs focus-trap +
  Escape + click-outside as one cohesive contract.
- **Submenu / checkbox-item / radio-item** Radix variants — no
  current call site needs them.
- **`<details>` audit pass** beyond what Bundle 128 already
  converted — most surviving `<details>` are inline expanders, not
  popovers. Not a Bundle 136 follow-up.
- **Hover-open / pointer-leave-close** convenience modifiers
  (Material-style menu hover behavior on desktop). Radix supports
  it via `onPointerEnter` / `onPointerLeave` on Trigger; current
  click-to-open behavior matches our existing UX so deferred.
