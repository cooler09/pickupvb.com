strictly less informative and would duplicate the journal headers.
`git log` covers anything below journal-entry granularity.

Closure type: Wontfix-gated-on-release-cadence (a variant of
Wontfix-by-design where the gate is an external event rather than a
design choice). Co-closing both audits in a single bundle because
they share the same finding and the same trigger — splitting would
risk drift if the trigger ever fires.

## Pattern notes

### Co-closure when two audits share a finding

Until Bundle 60 the same finding lived in two places with two
slightly different framings. Co-closing in one bundle:

1. Guarantees the two audit pages stay in sync about the closure
   reason — no risk that one says "Wontfix" while the other says
   "deferred."
2. Lets the journal entry serve as the single source of truth for
   the rationale, with both audit pages linking back to the same
   entry.
3. Eliminates the temptation to re-discover the same trigger
   independently if the gate ever fires (re-opening one without the
   other would look inconsistent).

Worth scanning future audits for cross-listed findings — they're
co-closure candidates by construction.

### Wontfix-gated as a distinct closure mode

The repo now uses three closure flavors that the audit-grading
rubric (P1/P2/P3) doesn't natively express:

- **✅ Fixed** — code/doc shipped that implements the audit's fix.
- **✅ Closed Wontfix-by-design** — the deliberate choice is the
  opposite of the audit's fix, with rationale and a re-open trigger.
  Bundles 53 (upload hardening), 54 (`og:type`), 58 (CI Supabase
  placeholders), 59 (composite refs).
- **✅ Closed Wontfix-gated-on-X** — the audit's fix would be right
  if condition X held; X doesn't hold yet, and there's a concrete
  external trigger for X. Bundle 60 (release cadence).

The distinction matters when the trigger fires: a Wontfix-by-design
closure stays closed unless the rationale rots; a Wontfix-gated
closure should be the first thing re-opened when the gate condition
appears.

### Audit endgames are worth flagging visibly

Documentation now has one P3 left (optional flow diagrams). That's
worth saying loudly in the audits-index row — both because it sets
expectations for the next contributor scanning the backlog and
because it identifies which audits are de-facto done. The Bundle 60
documentation index row leads with **"Only one P3 remains: flow
diagrams (optional)"** for exactly this reason. Worth mirroring the
pattern in other audits as they approach completion.
