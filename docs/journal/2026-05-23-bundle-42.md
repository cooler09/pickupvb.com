# 2026-05-23 — Bundle 42: Accessibility quick-wins II

## Context

After Bundle 41 closed the FieldError sweep, the accessibility audit's
"Still open" list had several small, mechanical P2s that didn't merit
individual bundles but did fit a clean quick-wins set. Three of them
target component-level primitives where a single change benefits every
caller, which made bundling them attractive: the diff stays small and
the audit log advances three rows at once.

## What shipped

1. **Datetime picker — Escape + return-focus.** Added a `triggerRef`
   on the trigger `<button>` and a document `keydown` effect (active
   only when `open`) that closes the popover on Escape and refocuses
   the trigger. The Done button now routes through the same
   `closeAndReturnFocus` helper so keyboard users land back on the
   field they came from regardless of how they closed the picker. The
   `aria-expanded={open}` attribute the audit flagged as missing was
   already present — verified and noted in the audit update.
   File: [datetime-picker.tsx](../../apps/web/src/components/datetime-picker.tsx).
2. **`confirm-submit-button` — `aria-modal="true"`.** One-line
   addition on the native `<dialog>`. Most screen readers infer
   modality from `.showModal()`, but a few still need the explicit
   attribute to announce focus boundaries correctly.
   File: [confirm-submit-button.tsx](../../apps/web/src/components/confirm-submit-button.tsx).
3. **"(opens in new tab)" sr-only cues.** Appended a
   `<span className="sr-only"> (opens in new tab)</span>` inside two
   shared components rather than at each call site:
   - [open-in-new-tab-button.tsx](../../apps/web/src/components/open-in-new-tab-button.tsx)
     — fixes every billing / Stripe-dashboard caller (`Stripe
dashboard ↗`, `Open tax forms in Stripe ↗`, …) in one shot.
   - [share-link.tsx](../../apps/web/src/components/share-link.tsx)
     `QuickShareButton` — added the cue only when `external` is set,
     so the WhatsApp / X grid items announce correctly while SMS /
     Email (same-tab `sms:` / `mailto:` schemes) don't get a
     misleading cue.

## Pattern notes

- **Push sr-only "(opens in new tab)" into the shared component, not
  the call site.** The audit's recommended fix said "add an sr-only
  span next to the arrow" at each call site, but that would have
  meant editing every `OpenInNewTabButton` consumer plus opening the
  door to drift (someone adds a new call site, forgets the cue, no
  lint catches it). Moving the cue into the primitive itself means
  every current and future caller gets correct behaviour by default.
  The same reasoning applies to `QuickShareButton`'s `external`
  branch — the cue is a property of the new-tab behaviour, so the
  component that owns that behaviour should own the cue.
- **Don't add cues where they don't apply.** `QuickShareButton`'s
  SMS and Email items use `sms:` / `mailto:` schemes that open the
  user's native handler, not a new browser tab. They share the
  visual treatment with the external links but the announcement
  would be wrong. Branching on the existing `external` prop kept
  this honest without adding a new flag.
- **One-line a11y fixes still earn a journal entry when bundled.**
  `aria-modal="true"` is genuinely one line, but it's a real
  behaviour change for AT users and grouping it with two other
  small wins gave it enough context to write up without padding.
  The alternative — landing it as a drive-by inside an unrelated
  bundle — would have made it invisible in `git log`.
