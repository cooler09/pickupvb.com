# Bundle 65 — 2026-05-23 — Node 22 LTS bump (Organization P3, full close)

## Context

Bundle 64 shipped the friend-edges sub-finding of the Architecture
P2 mapper extraction and called out that the three originally-named
row shapes (attendee, group-member, event-summary) all need either
new render sites or a design call before they can be extracted —
none of them is a clean next bundle.

Scanning the per-audit "remaining" list in
[docs/audits/README.md](../audits/README.md), the smallest open
item was the Organization audit's lone P3: "Node pinned to 20.11.0
while TypeScript is 6.x. Bump to Node 22 LTS at the next dependency
sweep." Pre-conditions for closing it cleanly were already in place:

- All four GitHub Actions workflows (`ci.yml`, `e2e.yml`,
  `e2e-develop.yml`, `smoke-prod.yml`) read
  `node-version-file: .nvmrc` rather than hardcoding a version, so
  a single file bump propagates everywhere.
- Only one `engines.node` declaration in the monorepo (root
  `package.json`).
- Next.js 16 and Vercel's runtime both support Node 22 LTS.
- Node 22 LTS is the current LTS line (active since October 2024).

Net: a two-file edit closes a long-standing P3 and brings the
organization audit's P3 column to fully resolved.

## What shipped

- [.nvmrc](../../.nvmrc): `20.11.0` → `22.11.0`.
- [package.json](../../package.json): `engines.node` `>=20.11.0` →
  `>=22.11.0`.

Nothing else needed editing — CI propagation is via
`node-version-file: .nvmrc`, and no Next.js / Supabase / Vercel
config carries a hardcoded Node version.

## Why 22.11.0 specifically

22.11.0 is the entry-point version of the Node 22 LTS line (became
"Active LTS" October 2024). Pinning to the LTS entry-point version
rather than the latest 22.x means:

- CI / contributors install a known-stable version, not a
  potentially-just-released patch.
- Vercel's deployment runtime maps any 22.x pin to its supported
  22.x build, so the exact patch is immaterial there.
- The next bump can be a deliberate decision rather than drifting
  via `~22` semver behaviour.

The `engines.node` floor uses `>=22.11.0` (matching the prior
`>=20.11.0` shape) so contributors on a slightly newer 22.x patch
aren't gated by pnpm.
