# Bundle 109 — Bracket: format picker UX

## Why

The bracket creation form was a bare `<select>` with four labels:
"Single elimination", "Double elimination", "Round robin", "Pool
play → playoff". A host who'd never run a tournament had no way
to choose other than guessing or leaving the page to research.
The pool-play extras (pool count, advance-per-pool) were always
visible regardless of selection, so the form looked the same
whether you were picking a 4-team single-elim or a 24-team pool
playoff.

Goal for this bundle: make the picker explain itself in place.
Show, for each format, what it's good for and what the trade-off
is; collapse the pool-play extras into the pool-play option; and
give the host a live "estimated matches" hint so they can sanity-
check the format against their field size before clicking
Create.

## What changed

### New `FormatPickerForm` client component

**NEW**
[apps/web/src/app/events/[id]/bracket/\_components/format-picker-form.tsx](../../apps/web/src/app/events/%5Bid%5D/bracket/_components/format-picker-form.tsx).
`'use client'` because the format choice drives conditional
controls and a live estimate. Four radio cards (visual radio,
hidden `<input type="radio" name="format">` so keyboard nav and
form-data semantics are unchanged) each carrying:

- **Title + one-line blurb** (what the format actually does).
- **Best for** — when to pick it.
- **Trade-off** — the main downside.
- **Min teams** — disable + dim the card if the registered team
  count is below the threshold.

The pool-play option additionally surfaces a "Pool play options"
fieldset (pool count, advance-per-pool) which is rendered only
when that format is selected. When it's hidden, the same field
names are written as hidden inputs so the server action's
`field()` reads work regardless — the existing
`createBracketFromForm` action doesn't need to learn about the
conditional UI.

Estimated match counts are computed client-side from the team
count + format + pool params:

- `single_elimination` → `teams − 1`
- `double_elimination` → `2 (teams − 1) + 1` (approx; covers
  WB + LB + grand final, ignoring the bracket-reset edge case)
- `round_robin` → `n (n − 1) / 2`
- `pool_play_playoff` → `pools × C(perPool, 2) + (advance × pools − 1)`

The hint reads "Estimated 11 matches with 8 teams." and updates
as the host changes pools / advance — gives an at-a-glance
sanity check ("oh, round-robin for 16 teams is 120 matches,
maybe not").

### NoBracketView simplification

[apps/web/src/app/events/[id]/bracket/\_components/no-bracket-view.tsx](../../apps/web/src/app/events/%5Bid%5D/bracket/_components/no-bracket-view.tsx)
shrunk to a thin server-component wrapper that renders the
spectator copy for non-hosts and the new `<FormatPickerForm />`
for hosts. The old inline form + `BRACKET_FORMATS` / `FORMAT_LABEL`
imports moved into the client component.

## Patterns observed

- **"Hidden inputs when collapsed" beats "server adapter
  branching."** The pool-play fields are only meaningful for
  one format, but rather than make the server action conditional
  on the format, we always submit them. The server-side `field()`
  helpers already cope with unused values, and the client
  component owns the UX without contorting the action signature.
  This is the same shape as the `useFormState` slot-prefix
  workaround documented in AGENTS.md — keep the server action
  simple, let the form layer handle whichever values it has.
- **Radio cards beat selects for "I have to teach the user the
  options."** A `<select>` is the right primitive when the user
  already knows what they want. For decisions that need context
  (tournament format, plan tier, payment method) a card with
  blurb + best-for + trade-off costs more pixels but cuts the
  bounce-to-Google rate to zero. Same idea as the format choice
  pattern in payment-flow tools.
- **Live "what does this cost me" estimates are cheap to add and
  high-signal.** The estimateMatches formulas are 10 lines and
  remove a category of "wait, this is way more matches than I
  budgeted court time for" surprises.

## Follow-ups deferred

- **Validate min-teams server-side too.** The client disables the
  Submit button if `teamCount < selectedMeta.minTeams`, but a
  malicious or scripted POST could still submit. The application
  layer probably already throws on under-team-count for
  round-robin / pool-play, but I didn't audit. Worth adding a
  domain test + explicit `ValidationError` if not present.
- **Court / time estimates.** Once a host enters "courts
  available" + "minutes per match", the estimate could become
  "~3.5 hours on 2 courts" instead of just match count. That
  turns the estimate into a real scheduling tool. Defer.
- **Remember last-used format per host.** A repeat host running
  the same league every Tuesday probably picks the same format
  every time. Storing the last choice on the host's profile and
  using it as the default radio selection would save a click.
  Defer.
- **Visual diagram thumbnails per format.** Tiny SVG sketches
  (4-team single-elim tree, double-elim with losers loop,
  round-robin grid, pool play → playoff) inside each card
  would make the format obvious at a glance for non-readers.
  Defer.
- **`<details>` for "Why these options?"** A collapsible
  explanation under the pool-play fieldset describing how pool
  size + advance-per-pool affect the playoff field size would
  help new hosts. Defer.
