# Bundle 128 — FormModal primitive + walk-in team modal conversion (2026-05-28)

## Context

User asked to evaluate where modals would beat inline `<details>` for
data isolation. Quick scan (via Explore subagent) found ~12 `<details>`
usages, 6 custom toggle patterns, and 8 server-action forms behind
toggles. The walk-in team form was the highest-leverage modal candidate
— appears in three places with the same form body, each one a discrete
"register one team" subtask competing for screen real estate with
unrelated host controls (format picker, seeding list, payment table).

User picked Bundle 128 as the first conversion: build the primitive,
convert the 3 walk-in sites, leave divisions / sponsor for later
bundles.

## Decisions

### Reuse native `<dialog>`, don't add a UI library

The codebase already uses native `<dialog>` + `aria-modal` in
[report-bug-button.tsx](../../apps/web/src/components/report-bug-button.tsx)
and [confirm-submit-button.tsx](../../apps/web/src/components/confirm-submit-button.tsx).
Rejected pulling in Radix Dialog / HeadlessUI Dialog — the native
element already gives us focus trap, Escape-to-close, backdrop scrim
(`::backdrop`), and inert-content semantics. The only thing missing is
a consistent wrapper so the 3 walk-in sites don't each rebuild
`useRef` + `showModal()` + `aria-labelledby` + heading markup.

### `FormModal` API: trigger render-prop + `(close) => children` render-prop

```tsx
<FormModal
  trigger={(open) => <button onClick={open}>+ Add walk-in</button>}
  title="Add a walk-in team"
  description="…"
>
  {(close) => (
    <form action={…}>
      <CloseOnSettled onSettled={close} />
      …
      <ModalFooter><Cancel/><Submit/></ModalFooter>
    </form>
  )}
</FormModal>
```

Rejected:

- **Imperative-ref API** (`const ref = useRef(); <FormModal ref={ref}/>;
ref.current.open()`) — forces every consumer to declare a ref and an
  open handler; doesn't compose with server components rendering the
  trigger inline.
- **Slot-based trigger** (`<FormModal.Trigger><button>…`) — Radix's
  pattern, but requires context plumbing and a `Slot` polymorphism
  helper. Render-prop is one line of consumer code and avoids the
  dependency.
- **Controlled `open` prop on `FormModal`** — pushes the boolean state
  up into every call site. The internal state + render-prop puts the
  state where it belongs.

### Drive `<dialog>` from React state, not directly from ref

First pass had `close = () => ref.current?.close()`. ESLint's
`react-hooks/refs` flagged passing that closure into a render-prop
because the lint can't prove the children won't invoke it during
render. Fixed by adding a `[isOpen, setIsOpen]` state and an effect
that calls `showModal()` / `close()` when `isOpen` flips. `open` /
`close` are now `setIsOpen(true)` / `setIsOpen(false)` — no ref reads
during render. Also added a `'close'` event listener so Escape and
backdrop dismissal sync back into state (otherwise the next `open()`
call would short-circuit because `isOpen` was still `true`).

### `CloseOnSettled` instead of `useFormState`-driven success branches

The three server actions today are void + `redirect(returnPath +
"?flash=…")`. Converting them to return typed `Result<T, E>` so the
modal closes only on success would balloon the diff and isn't aligned
with the existing error model (flash redirects). `CloseOnSettled`
watches `useFormStatus().pending` for a pending→idle transition and
fires `onSettled` either way. If the action redirects, the modal is
unmounted along with the page rerender. If the action throws and the
page rerenders, the modal closes anyway and the flash banner is what
the user sees — same UX as the current inline `<details>` flow. When
we start returning structured state per-form, swap `CloseOnSettled` for
a `CloseOnSuccess` driven by `useFormState`.

### Trigger styling encodes readiness

In `no-bracket-view` and `setup-view` the walk-in trigger is rendered
as a **primary fill** when the host can't proceed without adding a
team (`teamCount < 2` / `!canGenerate`), and as a **dashed-border
secondary** when registered teams already cover the case. Replaces
the Bundle 127 `<details open={!ready}>` auto-disclosure trick — the
modal can't "auto-open" politely (would steal focus on page load), but
the trigger's visual weight still signals "this is the unblocking
action."

### `WalkInTeamForm` learns `onSettled`, branches its layout

Rather than forking the form into a "standalone" and "in-modal"
component, `WalkInTeamForm` takes an optional `onSettled?: () => void`.
When set:

- Adds `<CloseOnSettled onSettled={…}>` inside the form body
- Drops the dashed-border card chrome (the modal already provides the
  container)
- Drops the inline heading + sub-copy (the modal `title` /
  `description` cover it)
- Renders a `<ModalFooter>` with Cancel + Submit instead of just Submit

When absent, the form behaves exactly as before. No other call sites
today, but the prop keeps it composable in case the form gets reused
inline elsewhere.

## Patterns observed

- **`react-hooks/refs` rejects render-prop callbacks that close over
  `ref.current`.** Even when the consumer only invokes the callback
  inside its own event handlers / effects, the lint can't prove that
  statically and flags `children(close)`. Workaround: drive the
  imperative target from React state and effect, then the `close`
  callback is just `setState` with no ref reads. Record this as a
  pattern — anyone building a similar imperative-shell primitive
  (`Popover`, `Sheet`, `Drawer`) will hit it.
- **`<dialog>` doesn't have a controlled `open` prop.** Setting the
  `open` HTML attribute opens it as a non-modal element (no backdrop,
  no focus trap). `showModal()` is the only API that gives modal
  semantics. Two-way binding requires both an effect that calls
  `showModal()` / `close()` from state, and a `'close'` event listener
  that syncs Escape / backdrop dismissal back into state.
- **Optional-prop form variants beat duplicated components.** Adding
  `onSettled?` to `WalkInTeamForm` and branching markup inside avoided
  forking into `WalkInTeamFormStandalone` + `WalkInTeamFormInModal`.
  The branch is small (chrome + footer) and stays right next to the
  form fields it modifies.
- **Native `<dialog>` is the right primitive for the codebase.** Three
  components now use it; once `FormModal` lands the others
  (`report-bug-button`, `confirm-submit-button`) could opt into it on
  the next pass for consistency, but they each have one-off behavior
  (open external link, confirm-then-submit) that doesn't need the
  generic shell.
