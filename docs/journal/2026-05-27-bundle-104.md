# Bundle 104 — Bracket: walk-in / unregistered team escape hatch

## Why

User asked to "implement a phase 1 generic tournament bracket
creator." Surface read of the request looked like greenfield work, but
a quick spelunk found the feature is already substantially shipped:
891 LOC under `apps/web/src/app/events/[id]/bracket/`, a full
[`Bracket`](../../packages/domain/src/brackets/bracket.ts) aggregate
with single/double-elim/round-robin/pool-play generators, per-division
DB scoping (migration
[20260605000300](../../supabase/migrations/20260605000300_bracket_per_division.sql)),
host-only seeding + score entry + reset, division tab nav. Everything
from the user's requirement list except one item.

The one gap: **no path to add a team that isn't registered to the
division** ("walk-in" / "this team showed up at the gym, put them in
my bracket"). Today the seeding list is hard-bound to
`listRegisteredTeams(event, division)` — host can reorder but can't
inject.

Important meta-lesson: stop and read before building. Asked the user
two clarifying questions before writing code — confirmed scope was
just the gap (not a full rebuild) and that the shape should reuse the
existing ad-hoc registration pipeline (ADR 0007) rather than invent a
new "bracket-only team" entity. Saved a multi-bundle rebuild of
something that already works.

## What changed

### Decision: reuse `RegisterAdHocTeamCommand`, no new entity

Two design choices were on the table:

1. **Add `display_name` to `bracket_seeds`** so a seed row could be
   `team_id IS NULL AND display_name = 'Walk-in'`. Cheap, but
   walk-in teams would only exist inside the bracket UI — invisible
   to capacity counts, the event attendee list, the post-event
   results page, etc.
2. **Register an ad-hoc team to the division** via the existing
   pipeline. Heavier (full registration row, captain assignment, RLS
   surface) but the walk-in team is then a first-class participant
   everywhere a normal team is. Matches the "ad-hoc vs. roster"
   discrimination already in ADR 0008.

Picked #2. The host becomes the nominal captain — acknowledged
misrepresentation, but lets the host rename / reassign / fill the
roster later from the existing team management UI without a separate
"bracket walk-in" surface to maintain. "Host knows best" applies to
the captain assignment too.

### Files

- **NEW action** in
  [apps/web/src/app/events/[id]/bracket/actions.ts](../../apps/web/src/app/events/[id]/bracket/actions.ts):
  `addAdHocTeamFromForm(eventId, divisionId, formData)`. Wraps
  `RegisterAdHocTeamCommand` with the acting host as captain and an
  empty member roster. Uses the existing `classify` + `back`
  helpers, redirects with `?notice=team_added` on success or the
  appropriate error notice on `Unauthorized` / `Conflict` /
  `NotFound` / `Invariant` / `Validation`.
- **NEW form** `AddAdHocTeamForm` in
  [apps/web/src/app/events/[id]/bracket/\_components/setup-view.tsx](../../apps/web/src/app/events/[id]/bracket/_components/setup-view.tsx),
  placed between the seeding list and the generate/discard buttons.
  Single `team_name` text input, dashed border so it reads as a
  secondary affordance, not a primary CTA. The new team lands in the
  seeding list as a "newly registered" row on the next render (the
  existing reconcile logic in `SetupView` already handles the
  diff).
- **Notices** in
  [apps/web/src/app/events/[id]/bracket/\_components/labels.ts](../../apps/web/src/app/events/[id]/bracket/_components/labels.ts):
  `team_added` (success) and `team_name_required` (error).

### Flow for the host

1. Open `/events/{id}/bracket?division=...`
2. Type team name → **Add team** → flash banner + team appears at
   the bottom of the seeding list, flagged as newly registered
3. Reorder → **Save seeding** → **Generate bracket**

If the team needs a roster, the host edits it from the event's team
management page afterwards (or never — a name-only placeholder is a
valid outcome at a walk-up event).

## Patterns observed

- **"Greenfield" requests often aren't.** The user described this as
  a phase-1 build; spelunking found ~900 LOC + a full domain layer
  already in place. The right move was to stop, write up "here's
  what exists, here's the actual gap" and let the user confirm
  scope. The
  `runSubagent` to the Explore agent paid for itself instantly here
  — it surfaced the ADR references and audit backlog entries that
  framed the conversation.
- **Reusing the ad-hoc registration pipeline beats inventing a
  bracket-only entity.** `bracket_seeds.display_name` would have
  been ~30 LOC and a migration; the walk-in team would then be a
  permanent special-case in every read path. The
  `RegisterAdHocTeamCommand` reuse is one new server action + one
  form, and the team is first-class everywhere immediately.
- **Phase-1 surface = one text field.** Roster, captain reassignment,
  and bracket-only "ghost" teams were all in scope to discuss but
  out of scope to ship. Easier to add later than to rip out.

## Follow-ups deferred

- **Drag-to-reorder seeding.** Current seeding list is a static
  `<ol>` — order is implicit by position in the form. Would need a
  client island with a dnd library. Logged as P3 against
  `events-page-ux.md` audit on next pass.
- **Roster fields on the walk-in form.** Host has to bounce to the
  event team management page to fill in members. Acceptable for
  phase 1; revisit if telemetry shows the bounce hurts.
- **Captain reassignment from the walk-in form.** Same — bounce to
  team management. Defer.
- **`BoardView` polish for single vs. double elimination.** Existing
  layout uses winners/losers/final round columns, which is
  functionally correct but not the "tree of brackets" visual most
  tournament tools render. No user signal that it's broken yet —
  ship if/when a host complains.
- **`force-dynamic` on bracket page.** Inherited from before; the
  page is host-gated so CDN caching is moot, but worth revisiting
  alongside the broader `force-dynamic` audit (architecture P2).
