# 2026-05-24 — Bundle 81: Consent affordance for analytics

## Context

Bundle 80 closed the last architectural item on the analytics audit
(server-side outbox at the handler boundary). The last open P2 was
**#5 — anonymous-auth users have no consent affordance**: every
visitor today is silently captured into Vercel Analytics and (since
Bundle 75) PostHog. For a US-only launch that's defensible — privacy
policy §11 already commits to honoring `Sec-GPC: 1` — but the audit
flagged it as table-stakes the moment we run paid acquisition or add
a third-party pixel. This bundle ships the banner, the cookie, and
the gate that the audit asked for.

## Decisions

- **Fire-and-forget gate at the port wrapper, not per-call-site.**
  `AnalyticsPort.capture` and `identify` are sync-void by contract
  (so the application + handler boundary stays free of `async`
  noise). Reading the consent cookie is async (`cookies()` in
  Next 16). A `ConsentGatedAnalytics` decorator wraps the singleton
  and does `void this.gated(() => inner.capture(...))` — the gated
  helper awaits `hasAnalyticsConsent()` and forwards if allowed.
  Race vs serverless freeze is identical to today's PostHog flush
  race (`flushAt: 1, flushInterval: 0`) — i.e. acceptable. The
  alternative (make `AnalyticsPort` async-void and refactor 15+ call
  sites) was rejected as a much larger change for no real benefit;
  every caller already treats analytics as fire-and-forget.
- **Opt-out default for analytics, opt-in for marketing.** Today's
  PostHog use is first-party product analytics with a salted-hash
  distinct id and a four-key trait allowlist (pinned by the
  domain-layer Vitest from Bundle 76); under US norms an opt-out
  posture is defensible and the audit explicitly recommends it.
  Marketing is denied-only because no third-party ad-tech pixel
  exists yet — when one lands, the existing two-state cookie shape
  (`{ analytics, marketing }`) supports promoting it to a real
  toggle without a schema migration.
- **Sec-GPC overrides default-analytics to denied.** Privacy policy
  §11 already promises this. Implementation: `defaultState(gpc).
analytics = gpc ? 'denied' : 'granted'`. An explicit cookie always
  wins over GPC (a user who clicks Accept while GPC is on has made
  an informed choice; we honor it).
- **Webhook captures fall through to default-granted.** Stripe
  webhooks run in a request scope with no user cookies — `cookies()`
  returns empty, `Sec-GPC` is absent, default is `analytics:
granted`. That's the intended behavior: business-event capture
  (`checkout_completed`, `host_payout_setup_completed`) is
  account-scoped data that the user has already consented to via
  the ToS by completing payment, and we can't show them a banner in
  Stripe's frame anyway.
- **Cron / outside-request-scope captures fall through to granted.**
  `await cookies()` throws outside a request scope. The gate wraps
  the read in try/catch with `allow = true` fall-through so future
  cron jobs that call `analytics.capture(...)` still emit. The
  fall-through is in `ConsentGatedAnalytics`, not in
  `readConsent()`, because we want `readConsent()` to fail loudly
  in pages that shouldn't be calling it.
- **Server-render the banner, not client-mount-after-hydration.**
  Root layout reads `isConsentDecided()` server-side (the cookie is
  on the request) and either mounts `<ConsentBanner />` or doesn't.
  No hydration flash, no flicker, no IntersectionObserver dance.
  The client component hides itself optimistically after Accept /
  Decline; the server action's `revalidatePath('/')` ensures the
  next navigation doesn't remount it.
- **Re-export `analytics` from `lib/handlers.ts`.** Bundle 80
  hoisted the singleton there. Moving the real singleton into
  `lib/analytics.ts` (so it can wrap with the gate without
  importing the handler graph) would force a rename across 15+ call
  sites. Re-exporting keeps every existing `import { analytics }
from '@/lib/handlers'` working unchanged.

## Patterns surfaced

- **`cache()` for per-request cookie reads.** `readConsent()` is
  called from the root layout (for `analyticsAllowed` + `decided`)
  and from the `ConsentGatedAnalytics` wrapper on every capture.
  Without `cache()` each capture in a single request would re-parse
  the cookie. With `cache()` it's a single read per request.
- **Sync-void port + async gate via fire-and-forget.** When you
  need to insert an async check in front of a sync-void interface
  without breaking 15+ call sites, a decorator that spawns a
  floating promise (`void this.gated(...)`) is the minimum-change
  shape. The cost is that you give up "we definitely captured
  before the request returned" — but with `flushAt: 1` on the
  PostHog adapter, that guarantee wasn't there anyway.
- **Server-rendered banner avoids the entire "consent flash"
  category of bugs.** The root layout already awaits theme; adding
  two more parallel awaits costs nothing.

## Follow-ups

- **Per-category modal toggles.** Today's banner only has Accept /
  Decline (both flip the `analytics` axis; `marketing` stays
  denied). When a third-party ad-tech pixel lands, replace the two
  buttons with a small modal that toggles each axis independently.
  The cookie shape already supports it.
- **"Manage cookies" link in the footer.** Once the user has
  decided, the banner disappears forever. A footer link that calls
  a server action to clear the cookie (or opens the modal above)
  would let users revisit their choice.
- **Persist consent into the authenticated profile.** Right now the
  decision is cookie-bound, so it doesn't follow a signed-in user
  across devices. Adding a `profiles.consent_state jsonb` column
  and reading it as a fallback when the cookie is missing would
  fix that. Defer until per-category toggles land — both touch the
  same surface.
- **Explicit early-return in `/api/web-vitals`.** Currently the
  route relies on the gated singleton no-op'ing when consent is
  denied. That's correct, but skipping the `getViewer()` lookup
  too would save a Supabase round-trip per denied beacon. Low
  priority — when consent is denied we also don't mount
  `<WebVitalsClient />`, so the beacon shouldn't fire in the first
  place.
