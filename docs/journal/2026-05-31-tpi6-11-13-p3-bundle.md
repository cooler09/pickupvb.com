With these the audit is fully remediated (only TPI-7's live dev verification

## Decisions

- **TPI-6 (webhook orphan) — dedupe on `processed_at`, not row existence; not a
  sweep.** The Stripe webhook claims an event by inserting its id, runs the
  handler, then stamps `processed_at`; on a crash between the claim and the
  handler completing (no chance to run delete-on-error) the row was stuck at
  `processed_at IS NULL` and the retry was deduped against it — a silent loss on
  the payments path. Considered a daily sweep (lowest hot-path risk) but its
  re-drive latency is up to 24h; chose the dedupe-on-`processed_at` change
  instead, which re-drives on Stripe's _next retry_ (minutes). The tradeoff it
  introduces — a rare concurrent double-delivery now both process — is safe
  because webhook handlers are idempotent at the data layer (a stated invariant,
  AGENTS.md). Extracted the decision to a pure `decideWebhookProcessing` so the
  orphan-re-drive semantics are unit-tested without mocking the route's Supabase
  - Stripe coupling (and route files can't export helpers anyway).
- **TPI-11 (Sentry Replay bundle) — keep + lower the on-error rate, don't
  lazy-load.** Investigated `Sentry.lazyLoadIntegration` and rejected it: on-error
  replay must buffer from page load to capture the _pre-error_ session, so
  deferring the load loses the feature — it's keep-vs-drop, not keep-vs-lazy. User
  chose to keep on-error replay (a debugging tool) and trim
  `replaysOnErrorSampleRate` 1.0 → 0.3, which is the actual cost-at-scale lever
  (Sentry bills per replay; 1.0 records _every_ error session, so an error spike
  could burn the quota). The ~40-50KB bundle weight is accepted.
- **TPI-13 (PostHog `flushAt: 1`) — closed working-as-intended, no code change.**
  `flushAt: 1` is the documented serverless fix for events dropped when the lambda
  freezes (the bundle-101 fix, guarded by `analytics.test.ts`). Request-level
  batching would risk re-introducing that silent drop for a negligible gain —
  PostHog bills per event ingested, not per request, so the only "cost" is a few
  extra outbound requests on the rare multi-capture request. The regression risk
  outweighs it.
