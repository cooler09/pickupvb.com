# Bundle 121 — Free-division price-unit exemption (amends ADR 0012) (2026-05-27)

## Context

A host hit the create-event boundary with a free (price 0) division
configured as ad-hoc + per-player and got
[`Team-registered divisions require per-team pricing…`](../../packages/domain/src/events/volleyball-event.ts).
The error is correct under ADR 0012's stated rule (Rule 2 — team-led
divisions require per-team pricing) but the _rationale_ in that rule is
explicitly about payment routing: "the captain pays for the team; the
platform does not split a captain's payment across teammates." When
`priceCents = 0` no payment is routed at all — Stripe is skipped per
[features.md#L104](../features.md#L104) — so the per-player vs.
per-team distinction is meaningless for free divisions. The host's
question ("why can't a division be free?") was the right question.

The rule existed mainly to keep stored `(price_unit, price_cents)`
pairs coherent in case the host later charged money. That goal is
better served by normalizing the unit at the write boundary than by
rejecting the host's submission.

## Decision

- **Free divisions skip the price-unit check** in both
  `VolleyballEvent.assertRegistrationConfigValid` and the boundary
  mirror `validateTeamPricing`. Composition and mode invariants
  (Rules 1, the composition halves of Rules 2 and 3, and Rule 4
  for non-zero prices) remain unconditional.
- **The write boundary normalizes the stored unit** to match the
  team-registration mode whenever `priceCents <= 0` (or absent):
  team-led → `per_team`, individual → `per_player`. Persisted rows
  stay coherent without forcing the host to think about a field
  that has no semantic content yet.
- **The UI hides the "Charge" select on free divisions.** The picker
  was already mode-clamped (single option per mode); hiding it
  entirely when free removes a meaningless control and removes the
  source of the original error.
- **Off-platform payments are not a separate axis.** The relaxation
  is keyed on `priceCents`, not `payments_off_platform`. A
  _paid_ off-platform division still has to pick a unit that matches
  its mode — Rule 4 of ADR 0012 is unchanged for non-zero prices.

Rejected alternatives:

- **Reject as before, surface a better error.** Doesn't address the
  underlying point: there's nothing for the host to fix because the
  field is irrelevant when free.
- **Strip the picker entirely and always derive unit from mode.**
  Tempting, but the unit _does_ matter once the host charges money
  (a host may run roster + per-team vs. roster + per-player — the
  latter is rejected by Rule 2 specifically). Keeping the picker for
  paid divisions preserves the existing explicit-choice ergonomics.

## Patterns surfaced

- **"Invariant rationale → invariant scope" alignment.** ADR 0012
  Rule 2 was written about payment routing but enforced
  unconditionally. That's a category of bug worth scanning for:
  whenever an invariant's docblock says "because money…" but the
  guard fires regardless of `priceCents`, the guard probably
  over-applies. Worth a future pass through `application/` and
  `domain/` to look for similar shapes (e.g. fee-split rules that
  apply on free events, refund-window guards that apply when no
  charge exists).
- **Normalize-on-write instead of reject-on-write for
  meaningless-field combinations.** The form had no way to omit
  `priceUnit` even when it was meaningless. Normalizing on the
  server keeps the persisted shape coherent without forcing the
  host to twiddle a field they shouldn't have to think about. Cheap
  pattern to reach for any time a UI control's value doesn't change
  observable behaviour.
- **Controlled state to make a gate reactive on an uncontrolled
  field.** The host-divisions-manager used `defaultValue` for the
  price input — fine until we needed to gate sibling UI on it.
  Switching just that field to controlled state (`useState` +
  `value` + `onChange`) was the minimal change; the rest of the
  form stayed uncontrolled.

  `(price_unit, team_registration_mode)` pair is now misaligned —
  but until then there are no rows to touch.
- **Symmetric "invariant rationale" sweep.** Per the pattern above,
  worth a quick scan of other "because money…" guards (fee-split,
  refund-window, processing-fee allocation) for the same
  over-application shape.
