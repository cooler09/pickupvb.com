# 2026-05-24 — Bundle 13a: ISR listings-Suspense (players / groups / teams)

## Context

After Bundle 12 closed out the remaining P2 / P3 small-wins, the
performance audit's only architectural item was P1 #1 — `force-dynamic`
removed but the public listings still implicitly dynamic via `cookies()`
in the RSC body. The audit's prescription:

> drop `force-dynamic`; use ISR (`export const revalidate = 60`) and call
> `revalidatePath()` from join/leave/edit actions. The auth-aware bits
> (viewer's RSVP state, "Manage" button) belong inside a small Suspense
> boundary or a Client Component that fetches per-user state separately.

PPR isn't on, and turning it on for this just to keep server-rendered
viewer chrome would widen the bundle considerably. The pragmatic shape is
the client-component-overlay variant: page renders the public listing
with a sessionless Supabase client; viewer chrome lives in a
`'use client'` component that fetches its own session after hydration.

## Scope

Three of the four listing pages — `/players`, `/groups`, `/teams`. The
fourth (`/events`) and all seven `/[id]` detail pages are deferred:

- `/events` has the friends list, following-feed default tab, and
  per-card friend badges. Drawing the right line between
  "shell + Suspense" and "everything is viewer-specific" is its own
  decision; this bundle stays focused.
- Detail pages have RSVP / manage / member chrome that interleaves with
  the public data they're rendering. Same logic — its own bundle.

## What shipped

### 1. `createSupabaseAnonClient()` — sessionless reads

[packages/supabase/src/anon.ts](../../packages/supabase/src/anon.ts).
Wraps `@supabase/supabase-js`'s `createClient` with the publishable
anon key and `persistSession: false`. Exported as
`@pickupvb/supabase/anon`. No cookies, ever; RLS evaluates as anonymous.

We deliberately did not reuse `createSupabaseServerClient` with a stub
cookie store — keeping a separate factory makes the "this is the
cookie-free read path" intent explicit at the call site.

### 2. `/players` → fully ISR

[apps/web/src/app/players/page.tsx](../../apps/web/src/app/players/page.tsx).
The page never used the viewer's session anyway (it's a public profile
directory). Replaced `getServerSupabase()` with `createSupabaseAnonClient()`,
added `export const revalidate = 60`. No new components needed.

### 3. `/groups` → ISR shell + `<NewGroupButton />`

[apps/web/src/app/groups/page.tsx](../../apps/web/src/app/groups/page.tsx)

- [`_components/new-group-button.tsx`](../../apps/web/src/app/groups/_components/new-group-button.tsx).
  Page swapped to sessionless reads. The "+ New group" CTA — the only
  viewer-conditional element on the page — moved into a tiny client
  component that calls `supabase.auth.getUser()` and renders the link
  only for authenticated, non-anonymous users.

### 4. `/teams` → ISR shell + `<MyTeamsPanel />` + shared `<TeamCard />`

[apps/web/src/app/teams/page.tsx](../../apps/web/src/app/teams/page.tsx)

- [`_components/my-teams-panel.tsx`](../../apps/web/src/app/teams/_components/my-teams-panel.tsx)
- [`_components/team-card.tsx`](../../apps/web/src/app/teams/_components/team-card.tsx).

The biggest of the three changes. Public "discover" query (paginated,
filtered by `q` / `format`) now runs against the anon client at
`revalidate = 60`. The viewer-specific sections (pending invites,
captained, rostered) plus the create-team / sign-in-to-create CTA moved
into `<MyTeamsPanel />`, a client component that:

1. Calls `supabase.auth.getUser()` on mount.
2. Branches three ways: loading skeleton, anonymous (renders the sign-in
   CTA), authenticated (parallel `Promise.all` of captained + member
   queries, then renders the three sub-sections).

`<TeamCard />` was extracted into its own file so it can be safely
imported from both the server `page.tsx` (public list) and the client
`<MyTeamsPanel />` (viewer sections). It only renders `<Link>` + a
badge span, no client-only state, so the same component works in both
contexts.

Existing mutating actions (`createTeam`, `acceptInvite`, etc.) already
call `revalidatePath('/teams', ...)`, so the ISR cache invalidates
correctly on member/captain changes.

## Decisions

- **Client overlay vs PPR.** Without `experimental.ppr`, any
  `cookies()` access during render — even inside a `<Suspense>` boundary
  — marks the whole route dynamic. Enabling PPR for three listing pages
  was strictly larger blast radius than moving the viewer chrome to a
  client component, which works today on the current Next 16 setup.
  Trade-off: brief flicker between "loading skeleton" and "+ New group"
  for signed-in users on `/teams`. That's a small, contained UX cost on
  routes where the win is for anonymous traffic anyway.

- **No `getServerSession` on the page boundary.** We could have read the
  session server-side and conditionally rendered the client component
  with an `initialSession` prop, but that defeats the entire point —
  the page must not read `cookies()` to stay ISR-cacheable.

- **Why a separate `anon.ts` instead of overloading the server client.**
  Two cleaner names beats one client with a "noCookies" flag. Call
  sites read like prose: "this page uses the anon client" ⇒ obviously
  ISR-safe.

- **Why `revalidate = 60` and not longer.** Sixty seconds matches the
  pattern Next docs use for "fresh enough, but mostly cached." Any
  mutation (new team, new group, profile update) calls `revalidatePath`
  on the listing — so the TTL is just a safety net, not the primary
  freshness signal.

## Patterns observed

- **Sessionless anon Supabase client** is the right primitive for any
  public RSC read that needs to stay ISR-cacheable. Worth reaching for
  whenever a page only renders publicly-readable data. Promoted to the
  package's named exports + subpath export so the pattern is grep-able.

- **Client viewer chrome** as a way to keep the shell static. The
  `<NewGroupButton />` shape (~40 LOC, single `useEffect` calling
  `getUser()` + an `onAuthStateChange` listener) is the minimal version.
  `<MyTeamsPanel />` is the heavier version — same pattern, but the
  component also owns the data fetches that previously lived in the
  page body.

- **Extract shared cards before splitting client/server.** `<TeamCard />`
  needed to be importable from both the server page and the client
  panel; extracting it first kept the JSX in one place.
