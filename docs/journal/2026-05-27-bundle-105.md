# Bundle 105 — Bracket: realtime updates for spectators

## Why

Picking up the next bracket item after bundle 104 (walk-in team
escape hatch). User chose "live updates: when the host enters a score
on one device, every viewer's bracket page refreshes without manual
reload." Today the page is a server component that only re-renders
when the submitter's own `revalidatePath` fires — anyone else viewing
the bracket has to refresh by hand.

The repo already has the right primitive: `useEventAttendees` in
[apps/web/src/hooks/use-event-attendees.ts](../../apps/web/src/hooks/use-event-attendees.ts)
subscribes to `postgres_changes` on `event_attendees` to keep the
spot count live on the event detail page. Same idea applies here:
subscribe to the bracket tables, call `router.refresh()` on any
change, let the server component re-render.

Two options were on the table:

1. **Server-side broadcast.** After every successful mutation in
   `bracket/actions.ts`, send a Realtime `broadcast` event on
   `bracket:${bracketId}` and have a client island listen for it.
   Decoupled from Postgres replication, but requires explicit
   broadcast calls at the end of every mutation (eight of them) and
   misses any out-of-band edits (e.g. SQL fixes from the dashboard).
2. **Postgres CDC.** Add the bracket tables to the
   `supabase_realtime` publication and subscribe via
   `postgres_changes` filtered by `bracket_id` / `division_id`.
   No application-layer wiring beyond the subscriber; out-of-band
   writes are picked up automatically; mirrors the existing
   `event_attendees` pattern.

Picked #2 — it's the pattern already in use, and the bracket page
is a server component so `router.refresh()` does the right thing
without any per-mutation hook.

## What changed

### 1. Add bracket tables to the realtime publication

**NEW migration** [supabase/migrations/20260704000000_bracket_realtime.sql](../../supabase/migrations/20260704000000_bracket_realtime.sql)
adds `tournament_brackets` and `bracket_matches` to
`supabase_realtime`. Both already have a uuid PK so the default
`REPLICA IDENTITY` works — no replica-identity backfill needed (the
contrast case is
[20260626000000_event_co_hosts_replica_identity.sql](../../supabase/migrations/20260626000000_event_co_hosts_replica_identity.sql)
where the table had no PK).

Deliberately did **not** publish `bracket_seeds` or
`bracket_match_sets`:

- The host doing seed reordering / per-set score entry already sees
  their own refresh via the server action's `revalidatePath`.
- Any remote viewer who needs to see the result will receive a
  `bracket_matches` event a beat later (winner assignment, status
  change) and the subsequent `router.refresh()` reloads the whole
  page including seeds + sets. One refresh, not three.

Skipping these two tables also keeps WAL volume down on big
tournaments where set scores fly in fast.

### 2. Client refresher

**NEW** [apps/web/src/app/events/[id]/bracket/\_components/realtime-refresher.tsx](../../apps/web/src/app/events/[id]/bracket/_components/realtime-refresher.tsx).
Single client island. On mount:

- Subscribes to `tournament_brackets` filtered by
  `division_id=eq.${divisionId}` — catches create, regenerate,
  reset, status transitions.
- If a `bracketId` exists, additionally subscribes to
  `bracket_matches` filtered by `bracket_id=eq.${bracketId}` —
  catches winner assignment and slot fills as teams advance.
- Both handlers call `router.refresh()`.

When there's no bracket yet (`NoBracketView` state), the matches
subscription is skipped (no bracket id to filter on); the brackets
subscription alone catches the moment a bracket gets created.

### 3. Mount in the page

[apps/web/src/app/events/[id]/bracket/page.tsx](../../apps/web/src/app/events/[id]/bracket/page.tsx)
renders `<BracketRealtimeRefresher divisionId={...} bracketId={bracket?.id ?? null} />`
once, outside the view-state conditionals. The component itself
returns `null` — pure side effect.

## Patterns observed

- **Reach for the pattern that already exists.** The choice between
  server-broadcast and postgres-CDC was made in five minutes by
  searching for `.channel(` in `apps/web/src/` and finding
  `useEventAttendees`. The pattern was already proven in
  production; copying it costs one migration + one component.
  Server-broadcast would have been ~150 LOC across eight mutations.
- **Publishing fewer tables ≠ losing fidelity.** `bracket_matches`
  is a chokepoint — every meaningful state change for a viewer
  (winner set, team advanced) updates a row there. Subscribing
  there is enough to drive a full-page refresh that pulls fresh
  seeds and set scores too. The instinct to subscribe to every
  related table would have tripled the WAL noise for zero added
  signal.
- **REPLICA IDENTITY is a footgun, but only for tables without a
  PK.** Worth a 5-second check on any future "add this to the
  realtime publication" — if there's no PK, you need a
  replica-identity migration first or DELETE events will fail
  silently. Both bracket tables already had PKs so this was a
  no-op, but the
  [event_co_hosts replica-identity migration](../../supabase/migrations/20260626000000_event_co_hosts_replica_identity.sql)
  is a cautionary tale.

## Follow-ups deferred

- **Debounce the refresh.** A burst of bracket_matches updates
  (e.g. tournament generation writes ~30 matches in one
  transaction) will trigger one `router.refresh()` per event.
  Next.js coalesces refresh calls reasonably well, but if it ever
  visibly flickers, wrap the handler with a 200ms trailing
  debounce.
- **Optimistic UI on score entry.** Today the host sees their own
  refresh via the server action, which is already snappy. A
  proper optimistic update would render the new winner immediately
  on submit and reconcile on the server response — out of scope
  for this bundle, but worth a look if score entry feels laggy
  during real tournament use.
- **Connection-state indicator.** The scoreboard tool shows a
  "connected / reconnecting" pill; the bracket page silently
  reconnects. Add a tiny indicator (or `useConnectionState`
  helper) if hosts ever ask "is this thing actually live?"
- **Apply migration locally.** Local Supabase wasn't running
  during verify (`pnpm db:migrate` failed with connection
  refused). The migration only alters the publication — no schema
  changes, so `pnpm typecheck && pnpm lint && pnpm test && pnpm build`
  passed clean against existing generated types. Run
  `pnpm db:migrate && pnpm --filter @pickupvb/supabase gen:types`
  next time the local stack is up; nothing should change in
  `packages/supabase/src/types.ts`.
