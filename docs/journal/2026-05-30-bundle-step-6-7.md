# 2026-05-30 — Bundle: P2 #6.7 (collapse event_attendees + event_free_agents)

**Audit item:** P2 #6.7 from
[docs/audits/event-data-model.md](../audits/event-data-model.md).

## What shipped

A single migration —
[supabase/migrations/20260802000000_collapse_attendees_free_agents.sql](../../supabase/migrations/20260802000000_collapse_attendees_free_agents.sql)
— collapses the two parallel child tables into:

- `event_participants` — one row per (division, user, role) where
  `role ∈ ('attendee','free_agent')`. Surrogate `id` UUID PK,
  `user_id` nullable (preserves attendee PII semantics from the 5a/5b
  era), partial unique on `(division_id, user_id) WHERE user_id IS NOT
NULL` — this is the **mutual-exclusion guarantee** the audit was
  asking for: a user can no longer be both an attendee and a free agent
  in the same division.
- `event_participant_payments` — 1:1 with attendee participants, mirrors
  the Step 5b `event_team_payments` shape exactly.

`event_attendees` and `event_free_agents` are recreated as
`SECURITY INVOKER` views over the canonical tables with INSTEAD OF
INSERT/UPDATE/DELETE triggers, so every existing
`.from('event_attendees')` / `.from('event_free_agents')` call in the
app + repo + webhook surfaces keeps working unchanged. The only
app-layer edit was the realtime hook
([apps/web/src/hooks/use-event-attendees.ts](../../apps/web/src/hooks/use-event-attendees.ts))
— views can't sit in the supabase_realtime publication, so the hook now
subscribes to `event_participants` and filters payload rows by
`role === 'attendee'`.

## Why bridge with views (and not a full retarget)

The audit's recommended fix is "collapse to event_participants and
retarget all readers." A clean version of that would touch ~30
call sites — both repos, the Stripe webhook, the reminder cron, CSV
export, refund/pricing/loadAttendeePayments, manage-payments,
checkout-actions, broadcast-actions, edit/cancel actions, profile
billing analytics, hook + realtime, plus rebuilding three views
(events_view / metro_health_weekly / host_activity_monthly) and one
RLS policy (events_select friends_of_attendees branch) inline.

Going through "bridge with views" thread once:

- **Schema gets the audit win immediately.** Mutual-exclusion is enforced
  at the canonical layer the moment the migration runs; capacity trigger
  now lives on a single table; one set of RLS policies; one foreign-key
  target for cross-cutting joins. The "two parallel everything" pattern
  is gone at the storage level even though it's still visible at the
  SQL-call-site level.
- **App-layer churn becomes a follow-up that can land incrementally.**
  Each call site can migrate to `event_participants` independently as
  it's touched for other reasons. No big-bang retarget PR.
- **The capacity trigger had to land on `event_participants` regardless**
  — INSTEAD OF triggers on the view fire after capacity should have
  rejected the row. So the capacity rewrite isn't "saved" by the bridge;
  it just happens once in the migration, same as it would in the
  full-retarget approach.
- **One client-layer edit was unavoidable** (the realtime hook), because
  realtime watches base tables and the view bridge can't be in the
  publication. That one file was the limit of TS churn.

Rejected approach: **keep the two tables and add a deferred-constraint
trigger for mutual-exclusion.** Hits one of the audit's complaints (the
biggest one) but leaves all the "parallel everything" plumbing in place
— parallel RLS, parallel host-view joins, parallel capacity wiring. The
collapse is the point, not the constraint alone.

## INSTEAD OF triggers — sharp edges to remember

- `event_attendees_bridge_insert` always materialises a row in
  `event_participant_payments` (default `payment_status='pending'`) even
  if the caller didn't supply payment columns. This keeps the bridge
  view's LEFT JOIN trivially non-null on the columns app code already
  treated as non-null in the generated types (e.g. `amount_paid_cents:
number`). Don't lose this default — if it goes, every consumer that
  destructures payment columns assuming non-null breaks silently.
- `event_attendees_bridge_update` `coalesce(new.payment_status,
'pending')`s the payment column. PostgREST `.update({...})` calls that
  omit the field will overwrite to `'pending'` because the trigger
  receives `NEW` with the column unset → `NULL` → `pending`. Today every
  webhook + admin path that touches payment columns sets `payment_status`
  explicitly, so this is fine. If a future caller does
  `.update({reminder_24h_sent_at: …})` without specifying payment_status,
  the payment row will be reset to pending. Two ways out when that
  surfaces: switch that caller to `.from('event_participants')` (the
  right long-term answer), or split the bridge into per-column UPDATE
  routing. Mentioned here so the next agent doesn't have to re-derive
  it from a Stripe race.
- INSTEAD OF triggers run with INVOKER privileges, so RLS on the
  canonical tables applies to the caller. The new policies mirror the
  prior posture exactly — public read, own-row insert/delete, host
  insert/update via `is_event_host`. The free-agent branch keeps the
  `not is_anon_session()` + `allow_free_agents` + tournament + published
  checks from the 20260710 / 20260730 sequence.
- The capacity trigger fires `WHEN (NEW.role = 'attendee')` on
  `event_participants` and counts attendees-only — preserves the
  pre-existing "free agents don't count toward fixed capacity" semantic.

## Backfill notes

- Attendees inserted first, preserving `event_attendees.id` as
  `event_participants.id` so external references (Stripe checkout
  metadata, webhook lookups by row id) keep resolving. Every attendee
  gets a matching `event_participant_payments` row.
- Free agents inserted second with fresh UUIDs, skipping any
  `(division, user)` pair already present as an attendee — the partial
  unique index would otherwise reject the row. Production data isn't
  expected to contain such overlaps (the audit called it a theoretical
  gap), but the `WHERE NOT EXISTS` keeps the migration idempotent on
  mixed snapshots.
- `event_free_agents` had a composite PK, no surrogate id. The bridge
  view doesn't expose one either, so no external references depend on
  per-free-agent ids.

## Follow-ups deferred (P3 backlog)

- **Retarget call sites off the bridge.** Each
  `.from('event_attendees')` / `.from('event_free_agents')` call should
  migrate to `.from('event_participants')` with an `.eq('role', ...)`
  filter and (for attendee payment data) an embedded
  `payment:event_participant_payments(*)` join. ~30 sites; do
  opportunistically when each is next touched. Repository adapters in
  `packages/infrastructure/src/supabase-event-repository.ts` are the
  highest-value ones since they're the canonical layer.
- **Eventually drop the bridge views + INSTEAD OF triggers** once every
  caller is retargeted. The mutual-exclusion guarantee + capacity
  trigger + RLS posture live on `event_participants` so dropping the
  bridge changes nothing semantically.
- **Mirror the `attach_team_to_division` SECURITY INVOKER RPC pattern**
  for any future participant upsert that needs to target the partial
  unique index. PostgREST `onConflict` can't target partial unique
  indexes; the 5b.ii precedent (`attach_team_to_division`) shows the
  right shape.
- **The `event_attendees_bridge_update` payment-coalesce sharp edge**
  above — promote to a code comment in the migration if it ever bites
  someone in the future. Not worth pre-emptively making the trigger
  smarter until it does.
