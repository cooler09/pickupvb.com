# 2026-05-24 — Bundle 88: Opas audit remediation for Bundles 84–87

## Context

The monetization audit's remediation log (2026-05-24) called for an Opas
audit of Bundles 84–87 before resuming higher-impact monetization features.
This bundle is the result of that audit: five fixes across the sponsor-slot
and host-analytics surfaces.

See [docs/audits/monetization.md](../audits/monetization.md) for the
validated-gate context.

## Decisions

- **Chose to enable all sponsor form inputs for non-Pro users** rather than
  keeping them disabled and adding a separate "enter details after paying"
  post-checkout flow. The checkout action already embeds form data in Stripe
  session metadata; requiring a separate post-payment edit step would add a
  second redirect without gaining anything.
- **Chose per-event-with-capacity scoping for fill rate** rather than a
  per-event breakdown table. The aggregate view is what a host wants at a
  glance; drilling into per-event fill is already covered by the Recent
  Events table.
- **Chose an early return for the non-Pro analytics path** rather than
  conditional query wrapping. The early return reads clearly and eliminates
  dead queries without adding nesting.
- **Removed `as never` casts** rather than narrowing types. The generated
  `database.types.ts` already had correct Insert types for both tables;
  the casts were defensive noise from the prior session, not a real type
  mismatch.

## Patterns observed

- **Disabled form inputs silently drop their values on submit.** When an
  input is `disabled`, the browser excludes it from `FormData`. If a server
  action reads that field (especially as a required field), it will always
  fail validation for users who see the disabled state. Prefer server-side
  gating + enabled inputs over client-side `disabled` to communicate access
  state.
- **Fill-rate aggregation must scope its numerator to the same event set
  as its denominator.** Mixing all-attendee counts against a
  capacity-only denominator produces rates > 100% and is misleading. Always
  build the capacity event set first, then filter attendees to match.
- **`as never` casts on Supabase upserts are a sign of missed type
  regeneration, not a real type gap.** Check `database.types.ts` before
  reaching for a cast — the generated Insert type is almost always correct.
