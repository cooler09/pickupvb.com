# 2026-05-24 — Bundle 78: Public numbers page + marketable rollup views

## Context

Bundle 77 closed the last P1 on the analytics audit. The user asked
"what's the next hot integration?" and the recommendation was P2 #7 —
the missing marketable / sponsorable public surface. Today the only
external answer to "how big is PickupVB?" is "go read the events
list and count" — useless for sponsorship outreach, press inquiries,
and host-acquisition copy. P2 #7 was also the cheapest remaining P2
to ship (two views + a single read-only page; no new domain plumbing).

## Decisions

- **Two views, security_invoker=on.** `metro_health_weekly` rolls
  every published-public event by `(city, week)` and exposes events,
  attendees, GMV, and average fill. `host_activity_monthly` rolls
  the same shape per host-per-month, filtered by `auth.uid() =
host_id` inside the view body. `security_invoker=on` so the
  underlying-table RLS still applies — no service-role detour, no
  risk of leaking unpublished events to anon callers.
- **Regular views, not materialized.** At current event volume a
  view evaluated every 30 minutes (page ISR) is fine. Materialized
  views + a cron refresh adds operational surface area (pg_cron job,
  refresh failure handling) for a problem we don't have yet. Easy
  to swap later.
- **Read capacity from `event_divisions where sort_order=0`, not
  `events`.** `events.capacity_kind` / `events.max_spots` were
  dropped in the Phase 9d migration when capacity moved to
  `event_divisions`. First migration attempt failed with
  `column e.capacity_kind does not exist`; fix was to use the
  primary-division pattern the rest of the codebase already uses.
- **Page uses `getAdminSupabase()` + `revalidate = 1800`.** The
  view is anon-grantable, but `getServerSupabase()` reads
  `cookies()` which would force the page dynamic. The admin client
  keeps the page statically renderable so ISR works. Bonus: matches
  the audit guidance to never call `cookies()` from a cached read.
- **Press-kit CSV is a footer line, not a route.** "Available on
  request" buys us time to see whether anyone actually asks before
  we build the download. If a sponsor asks twice we'll ship it.
- **`position_demand_weekly` view skipped.** The audit asked for
  position-level supply/demand, but `event_free_agents` doesn't
  carry a "position requested" column today. That's a schema change,
  not a view, and out of scope for this bundle.

## Patterns surfaced

- **`security_invoker=on` is the right default for marketable
  rollup views.** It lets a view filter to "what the caller can see"
  without re-implementing RLS in the view body. Saves us writing
  parallel policies on every aggregate.
- **For viewer-independent ISR pages, prefer `getAdminSupabase()`
  over `getServerSupabase()`.** Cookies make the page dynamic and
  silently kill ISR. The admin client + an RLS-respecting view is
  the cleanest combo.
- **Capacity lives on `event_divisions`, not `events`.** Anyone
  writing new SQL that touches event capacity should hit
  `event_divisions where event_id = ... and sort_order = 0` for the
  primary, or aggregate across all rows for the whole event. Worth
  promoting into AGENTS.md if it bites a third time.

  The view is in place; no `/profile/host-activity` page consumes
  it yet. Pick up when we have host-retention questions to answer.
- **Materialized-view refresh cron.** Only worth doing if the
  rollup query gets slow at scale; current event volume makes the
  30-min ISR plenty.
- **Sponsor / press CTA copy.** The page links `hello@pickupvb.com`
  — we should make sure that inbox actually has someone on it
  before we drive traffic to the page.
