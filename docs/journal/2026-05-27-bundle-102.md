# Bundle 102 — ship PostHog browser SDK (and the consent / docs pivot it requires)

## Why

Bundle 101 fixed the **server-side** PostHog flush race. With that
fix landed, the audit's diagnostic question came back: why does
PostHog show zero visitors and zero page views? Static answer:
because we have no browser instrumentation. Server-side `capture()`
only fires on requests that reach our handlers — marketing-page
bouncers, scroll-only visitors, and the `$pageview` signal in
general were all invisible.

Bundle 82 (three days ago) explicitly retired Vercel Analytics +
Speed Insights with a follow-up to "ship a `$pageview` replacement
later." Later was now. Three options to close the gap:

1. **Custom server-side `$pageview` beacon.** Cheap, but
   re-implements the PostHog browser SDK badly and still misses
   autocapture / session stitching / bounce.
2. **Re-add Vercel Analytics + ship PostHog browser.** Two
   dashboards again. Marginal coverage ≈ zero over PostHog's own
   Web Analytics tiles. Directly reverses Bundle 82's "two
   analytics surfaces" pattern without buying anything.
3. **Ship PostHog browser SDK only.** One vendor, one dashboard,
   server `capture()` and browser autocapture stitch into one Person
   via the salted-hash distinct id. Preserves Bundle 82's posture.

Picked option 3. Full rationale in
[docs/adr/0015-browser-analytics-posture.md](../adr/0015-browser-analytics-posture.md).

## What changed

### 1. Browser SDK provider

- **NEW** [apps/web/src/components/posthog-provider.tsx](../../apps/web/src/components/posthog-provider.tsx)
  — consent-gated client component. Dynamically imports `posthog-js`
  inside the effect (kept out of the entry chunk for users who
  decline), initializes with `person_profiles: 'identified_only'`,
  `capture_pageview: 'history_change'`, `disable_session_recording:
true`. Pure decision function `shouldInitPostHog({ allowed, apiKey })`
  exported so the gating logic can be regression-tested without
  rendering React.
- **NEW** [apps/web/src/lib/server-distinct-id.ts](../../apps/web/src/lib/server-distinct-id.ts)
  — server helper that recomputes the same
  `sha256(POSTHOG_DISTINCT_ID_SALT + ':' + userId)` hash used by the
  server adapter. Raw Supabase id never reaches the browser.
  Returns `null` for anonymous (`is_anonymous`) users so they stay
  on PostHog's cookie distinct id until they claim a real account.
- **NEW** `posthog-js` dependency in
  [apps/web/package.json](../../apps/web/package.json) (~50–60 KB
  gzipped, loaded only after consent grant).

## Patterns surfaced

- **Extract the audit-relevant invariant as a pure function.** The
  provider's two-condition gate (consent + key) is the thing that
  must never silently flip. Pulling it out as `shouldInitPostHog`
  keeps the regression test 4 lines and zero deps — no
  `@testing-library/react`, no jsdom environment. Same trick used
  by the analytics test in Bundle 101.
- **Browser consent revocation needs a synchronous signal.** A server
  action that writes the cookie + `revalidatePath('/')` doesn't
  remount client components on the current navigation; the SDK
  would keep capturing until the next hard nav. The `CustomEvent`
  pattern (banner → window → provider) gives an immediate
  `opt_out_capturing()` + `reset()` without a reload.
- **Bumping the consent cookie version is a forcing function.** Any
  time the disclosure changes — new SDK, new vendor, new data
  category — bump the version. Cheaper than retroactively arguing
  whether the old consent still applies.

## Follow-ups

- Add a persistent "Manage cookie preferences" affordance (footer
  link → modal that re-uses `setConsentDecision`). Right now the
  only way to revoke after dismissing the banner is to clear the
  `pickupvb_consent` cookie manually.
- Reconsider `disable_session_recording: true` after launch traffic
  warrants it — requires a separate consent surface.
- Wire PostHog feature flags for the A/B framework slot in the
  analytics audit (P3 #11) — the browser SDK is the natural place
  for variant assignment.
- Once production traffic confirms identify-stitching works end-to-end,
  consider promoting `signup_completed` from a server-only capture
  to a browser-emitted event too, so we can see the anonymous-→
  -identified handoff in PostHog's funnels view.
