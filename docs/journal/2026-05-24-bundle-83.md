# 2026-05-24 — Bundle 83: Pass Stripe processing fee to the buyer

## Context

The monetization audit landed earlier today. P1 #2 was the cheapest,
highest-leverage finding in the backlog: today, when a host runs a
$20 paid event in buyer-paid mode, they receive **$19.09** — Stripe's
2.9% + 30¢ processing fee comes out of the destination charge
silently. The 5% PickupVB platform fee is already visible in the
checkout breakdown ("Service fee: $1.00"); the processing fee is
not, and that asymmetry shows up on the first payout as a hidden
tax. Every comparable ticketing platform (Eventbrite, ClubExpress,
TeamSnap, LeagueApps) bills the processing fee as a separate line
item on the buyer's checkout and routes the gross to the host.

The audit graded this P1 because the cost is per-ticket, host
churn risk grows with their second event when they re-check the
payout, and the fix is a single new flag on `events` plus three
checkout sites + the price-breakdown panel. No new pricing tier,
no new vendor.

## Decisions

- **Per-event opt-in, not a global Pro perk.** A host running a
  $5 hat-passing pickup night doesn't want a $1.45 processing-fee
  line item — the optics are wrong at low ticket prices. A host
  running a $35 tournament team entry does. New events default
  the flag to `true` (the new desirable behavior); existing rows
  backfill to `false` so we don't silently re-price events already
  advertised to buyers.
- **Gate on `host_absorbs_fee = false`.** When the host opted into
  absorbing the platform fee, they've also implicitly opted into
  "what you see is what you pay" pricing. Stacking a processing-fee
  line on top would contradict that promise. Code rule:
  `buyerProcessingFeeCents()` returns 0 when `hostAbsorbs ||
!passToBuyer`.
- **Simple one-pass formula, not exact gross-up.** Stripe's fee is
  taken on the gross the buyer pays, so a strictly accurate
  pass-through requires solving a fixed-point equation. We use
  `ceil(0.029 * (ticket + platformFee)) + 30` (computed on the
  pre-processing-fee subtotal) and accept the sub-cent recursion
  loss to the host. Matches every other platform that does this
  pass-through. Eventually-correct gross-up is a P3 follow-up.
- **No change to refund behavior.** Stripe doesn't return the
  processing fee on a refund regardless of who paid it on the
  front end — the host eats ~$0.91 on a refunded $20 ticket either
  way. This was already the case before this bundle. Documented in
  the helper's JSDoc and in `docs/payments.md` so the next reader
  doesn't try to "fix" refund parity.
- **No `application_fee_amount` change.** PickupVB's cut is still
  `PLATFORM_FEE_BPS` (or `PRO_PLATFORM_FEE_BPS`) applied to the
  ticket subtotal — the processing-fee line is collected through
  the destination charge and nets against Stripe's actual fee on
  the connected account. We don't take a cut of the processing
  fee.

## Patterns surfaced

- **Backfill-to-old-behavior, default-to-new-behavior.** The new
  column DEFAULT is `true` (good for everything created from now on)
  but the migration explicitly `UPDATE`s every existing row to
  `false` so live events don't shift price under buyers who already
  see them. Same pattern as ADR 0007's team-mode default. Worth
  promoting into AGENTS.md if it shows up a third time.
- **Per-team checkouts duplicate the attendee-flow pricing read.**
  All three checkout actions (`checkout-actions`, `team-checkout-actions`,
  `roster-team-checkout-actions`) re-select `events` for the
  fee-flag columns instead of going through `getEventPricing`.
  That's because team flows need the per-division `price_cents`
  off the aggregate, not the first-division shortcut
  `getEventPricing` uses. The duplication is fine for now (three
  selects, identical columns) but if a fourth column joins
  `host_absorbs_fee` + `pass_processing_fee_to_buyer` we should
  promote the read to a shared helper.
- **The `as never` cast on Supabase `.update()` payloads hides
  schema drift.** Typecheck passed against the new column even
  before regenerating `database.types.ts` because all three update
  sites use `as never`. That's a known compromise (otherwise every
  Supabase write needs a full row-shape cast), but it means the
  _real_ schema validation is at `pnpm db:migrate && gen:types`
  time, not at editor-typecheck time. The verify chain doesn't
  catch this; remember to regenerate types as part of any
  schema-touching bundle.
