# Bundle 116 — Promote ad-hoc registrations to first-class teams (2026-05-27)

## Context

User-reported regression after bundle 115 walk-in form work: "i registered
some ad hoc teams but they don't seem to show up on the event page or in
the bracket page. It still shows 0." Traced to a structural gap that
bundle 104's journal had asserted away ("the new team lands in the
seeding list on the next render") without ever testing the end-to-end
path.

Root cause: ADR 0007 split team registration into two tables —
`event_team_registrations` (ad-hoc, with rich off-platform roster) and
`event_teams` (roster mode, FK to a real `teams.id`) — but never
reconciled them. The bracket reader
[`SupabaseBracketRepository.listRegisteredTeams`](../../packages/infrastructure/src/supabase-bracket-repository.ts#L287)
scans only `event_teams`, and `events_view.team_count` (defined in
`20260513001100_anon_auth_pivot.sql`) is the same `count(*) from
public.event_teams` expression. Ad-hoc rows were invisible to both
surfaces. Worse, `bracket_seeds.team_id` is a hard FK to `teams.id`
([20260514000400_tournament_brackets.sql#L39](../../supabase/migrations/20260514000400_tournament_brackets.sql#L39)),
so even after fixing the read, an ad-hoc registration could not be
seeded into a generated bracket without a backing `teams` row.

## Decisions

Three options were on the table (see prior chat):

- **A. Backing-team-row in the walk-in action only.** Smallest patch.
  Rejected because it would diverge ad-hoc vs. walk-in registration
  semantics inside the same table — half the rows would have backing
  teams, half wouldn't, and the bracket count would still be wrong for
  captain-submitted ad-hoc registrations.
- **B. Schema polymorphism on `bracket_seeds`.** Add
  `registration_id` alongside `team_id`, make both nullable with a check
  constraint. Cleanest at the schema level but spreads a discriminator
  through every bracket generator, the seed writer, the playoff writer,
  and the read model. Probably ~150 LOC across packages + a migration
  - a test sweep.
- **C. Auto-promote every ad-hoc registration to a `teams` row at save
  time** (ADR 0013 Option B). **Chosen.** Single materialization point
  (the infrastructure adapter), zero changes to the bracket layer, and
  it discharges the open question in ADR 0013 about whether ad-hoc
  teams should be first-class on profiles — they now are.

Two sub-decisions inside C:

- **Materialize in the repo, not the handler.** The domain aggregate
  stays free of two-table awareness. `EventTeamRegistration` doesn't
  know its `teams.id`; only the Supabase adapter does. Symmetry with
  the existing `RegisterTeamHandler` → `attachTeamToDivision` pattern
  (which also lives in the infrastructure adapter rather than the
  handler).
- **Preserve the `teams` row on withdraw; only delete the `event_teams`
  link.** Aligns with ADR 0013 ("history-preserving"): the captain's
  profile keeps a record that they fielded a team for the event, even
  after withdrawing. The `event_teams` row goes so the count is
  accurate and capacity is freed.

## Changes

- **New migration**
  [20260705000000_promote_ad_hoc_registrations_to_teams.sql](../../supabase/migrations/20260705000000_promote_ad_hoc_registrations_to_teams.sql)
  adds `event_team_registrations.team_id uuid references teams(id) on
delete set null`, a partial index, and a backfill DO block that walks
  every active ad-hoc registration without a backing team, creates the
  `teams` row (captain + event format + registration name), links it
  back via `team_id`, and inserts the `event_teams` row keyed on the
  registration's `division_id`. Soft-deleted registrations are skipped
  on purpose — re-materializing them now would inflate counts.
- **Repo:** [`SupabaseEventTeamRegistrationRepository`](../../packages/infrastructure/src/supabase-event-team-registration-repository.ts)
  gains two private methods:
  - `ensureBackingTeam(registration)` — called at the end of every
    `save`. Idempotent: SELECTs `team_id` first; if set, only renames
    the `teams.name` when the registration name changed; if null,
    fetches event format, inserts `teams`, updates the link, inserts
    `event_teams`.
  - `detachBackingTeamLink(id)` — called at the start of `delete` and
    `softDelete`. Reads `event_id` + `team_id`, deletes the
    `event_teams` row. The `teams` row is left in place.
  - The `if (members.length === 0) return` early-return in `save`
    became `{ await ensureBackingTeam(...); return; }` so walk-ins
    with empty rosters still get a backing team.
- No domain / application / page changes. The bracket reader, the
  bracket-seeds writer, the events_view count, and the host-tools
  panel all start working correctly the moment the migration applies.

## Verification

`pnpm typecheck && pnpm lint && pnpm test && pnpm build` — 15/15 tasks
green, all cached on second run. One typecheck fix during the loop:
`(evtRow as { format: string }).format` had to become `as unknown as
{ format: string }` because the stubbed Supabase types don't list
`events.format` (per [supabase-types-stub.md](../../packages/supabase/src/database.types.ts)
convention — the types file is intentionally a 12-line stub).

Migration was **not** applied locally — Supabase isn't running on this
machine right now. Production CI will pick it up on deploy. Recommend
spinning up local Supabase and running `pnpm db:migrate` once before
manually exercising the walk-in flow to confirm the backfill behaves
on real data.

## Patterns observed

- **Cross-table reconciliation always finds you eventually.** Bundle
  104 split the registration model but never traced the read path back
  through `event_teams`. The fix wasn't expensive once the gap was
  named, but the gap was hidden for ~12 bundles. Next time a new
  parallel table lands (ADR-style), audit every existing read that
  scans the sibling table and decide explicitly: UNION, materialize,
  or polymorphic FK.
- **The repo is the right place for materialization invariants the
  domain doesn't care about.** The aggregate doesn't carry `team_id`
  and shouldn't — promoting at the adapter layer keeps the domain
  pure and matches the existing `attachTeamToDivision` pattern.
- **Idempotency by SELECT-then-decide is cheap when the write is rare.**
  An ad-hoc registration `save` happens once per registration and
  again on rename/member edit. The extra round-trip for the team_id
  lookup is invisible alongside the existing member-clear-and-insert.

## Follow-ups deferred

- **`team_members` for ad-hoc captains.** Currently the synthesized
  `teams` row has no `team_members` entry (not even the captain). For
  roster mode, captain is implicit via `teams.captain_id`; for the
  profile teams list and friends-of-friends discovery, ad-hoc teams
  show up as zero-member teams. Decide whether to backfill the
  captain into `team_members` (low cost) or leave them implicit. Not
  blocking the bracket fix.
- **Idempotency under concurrent `save` of the same registration.**
  Two parallel calls could both SELECT `team_id is null` and both
  insert. Extreme edge case for ad-hoc; would be solved by a unique
  index on `event_team_registrations(id) where team_id is null` or by
  wrapping the materialization in a `with` CTE + conditional insert.
  Skipped for v1.
- **Promote-on-rehydrate of soft-deleted registrations.** A captain
  who withdraws then re-registers gets a _new_ registration row and
  therefore a new `teams` row (the soft-deleted row stays
  un-promoted). That's the correct behavior for the count, but
  callers reading historical registrations will see two distinct
  `team_id`s for "the same" team. Document in ADR 0013 if needed.
- **Audit log update.** [docs/audits/registration-workflow.md](../audits/registration-workflow.md)
  has a remediation log; add an entry pointing at this bundle so
  next-audit doesn't re-flag the count gap.
