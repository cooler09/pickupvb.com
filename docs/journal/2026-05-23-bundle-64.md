# Bundle 64 — 2026-05-23 — Friend-edges mapper extracted (Architecture P2 mapper extraction, partial close)

## Context

Bundle 63 closed the small half of the Registration workflow UX P3
(free-agent list groups by division) and left the captain-claim
affordance open. With that out of the way the next clean target on
the audit backlog was the long-standing Architecture P2 **"duplicated
snake_case → camelCase row mapping"** finding — open since the
2026-05-17 audit, deferred at Bundle 49 with the note "needs a design
call, not a mechanical extract."

The deferral was correct for the three row shapes the audit
originally named (`attendee`, `group-member`, `event-summary`):

- `group-member`: the two consumers `groups/[id]/page.tsx` and
  `groups/[id]/members/page.tsx` want different DTO shapes
  (`avatarUrl` vs. `joined_at`) and select different columns. Still
  blocked on the design call.
- `attendee`: the 13 `event_attendees` query sites are all narrow
  projections — `select('user_id, status')` etc. — not full
  row→DTO renders, so there's no obvious unified mapper shape yet.
- `event-summary`: never surveyed; the audit named it from memory.

What the audit didn't name, but which is the exact same pattern, is
the **friend-edges row shape**. `apps/web/src/app/profile/page.tsx`
and `apps/web/src/app/friends/page.tsx` both inline:

- The same `friendships` select string with the embedded `profiles`
  join: `'friend_id, profiles:profiles!friendships_friend_id_fkey(id, handle, display_name, first_name, last_name, avatar_url, home_city)'`.
- The same local `type FriendProfile` declaration.
- The same `OutRow` narrowing cast on the Supabase result.
- The same null-filter on the embedded `profiles` join.
- A second identical query for incoming edges (`select('user_id')` on
  `friendships` where `friend_id eq userId`) used to build a
  `Set<userId>` of mutual friends.

Two callsites, four duplicated pieces. Pure mechanical extract —
exactly the case the original audit was written for. Worth shipping
as a proof-of-pattern for the directory the audit prescribed
(`apps/web/src/lib/mappers/`), and to leave one fewer thing in the
backlog when the group-member design call eventually happens.

## What shipped

New mapper + two callsite collapses.

### `apps/web/src/lib/mappers/friend.ts` (new)

- Exports `FriendProfile` (`id`, `handle`, `display_name`,
  `first_name`, `last_name`, `avatar_url`, `home_city` — all
  nullable except `id` to match the underlying schema).
- Exports `loadFriendEdges(supabase, userId): Promise<{ friends: FriendProfile[]; mutualIds: Set<string> }>`.
- `SupabaseClient` is typed as
  `Awaited<ReturnType<typeof getServerSupabase>>` to match the
  pattern already in
  [apps/web/src/lib/server-auth.ts](../../apps/web/src/lib/server-auth.ts#L13).
- Internally runs both queries through `Promise.all` — the inlined
  versions in the two pages `await`'d them sequentially, so this is
  a small extra perf win on every profile / friends page render.
- Returns `{ friends: [], mutualIds: new Set() }` on error from
  either query, matching the prior inlined behaviour (the pages
  silently fell back to empty lists rather than surfacing a Supabase
  error).
- Pure: no Next.js, React, or `revalidatePath` imports. Lives in
  `lib/mappers/` per the original audit fix.

### Callsite collapses

- [apps/web/src/app/friends/page.tsx](../../apps/web/src/app/friends/page.tsx):
  deleted the local `FriendProfile`, both `select` blocks, the
  `OutRow` narrowing, the null-filter, and the mutual-edge `Set`
  construction. Replaced with
  `const { friends, mutualIds } = await loadFriendEdges(supabase, user.id);`.
  `excludeIds` calculation unchanged.
- [apps/web/src/app/profile/page.tsx](../../apps/web/src/app/profile/page.tsx):
  same collapse. Local `FriendProfile` type block (was lines 40-49)
  removed; both query blocks + `OutRow` + null-filter + mutual-set
  replaced with the same one-line destructure.

## Why this is partial, not full close

The audit's P2 is the entire "duplicated row mapping" pattern, not
just friend edges. Three row shapes remain:

- **attendee** — mechanical when a real renderer surfaces. The
  current `event_attendees` consumers are all narrow projections
  (status counts, user-id sets), so there isn't a row→DTO renderer
  to consolidate yet. Worth re-checking when the next attendee-list
  view lands.
- **group-member** — still the design-call case from Bundle 49.
  Two consumers want different DTO shapes; need either a
  maximal-shape DTO with optional fields or two named mappers.
  Friend-edges doesn't unblock this; the call still needs to
  happen.
- **event-summary** — survey not done this bundle. The audit named
  it from memory; the actual duplicated callsites need to be
  enumerated before the mapper shape is obvious.

Net: `lib/mappers/` directory now exists and has one example. The
header on the audit finding moved to 🟡 Partial.
