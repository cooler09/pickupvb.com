# 2026-05-22 — Bundle 37: database operations doc

## Context

After Bundle 36 closed monitoring, only two P2s remained on the docs
audit: JSDoc backfill (gated on the architecture audit's
bracket-generators P1 reclassification per the finding's own fix
note) and the database operations guide. DB-ops is unblocked, so it's
next.

The audit framed this as "AGENTS.md covers the migration commands
but nothing covers: how to inspect production data safely, how to
run a one-off SQL fix, how RLS interacts with the SQL editor, how to
track storage growth." Migration mechanics are already in
[AGENTS.md → Migrations](../../AGENTS.md#migrations) and
[packages/supabase/README.md](../../packages/supabase/README.md), and
bad-migration recovery is in [runbook.md](../runbook.md) — the new
doc shouldn't duplicate any of that. It's the four gaps and nothing
else.

## What shipped

**[docs/database-operations.md](../database-operations.md).**
Structure:

- **Top "where to look first" pointer table.** Routes migration
  mechanics → AGENTS.md + packages/supabase README; bad-migration
  recovery → runbook; incident dashboards → monitoring; client
  factories + nested-join + anon-auth conventions → packages/supabase
  README. Explicitly says "this doc covers what those don't" so a
  reader who lands here for a migration question gets pushed back to
  the right place.
- **Environments table** — local / staging / prod and how you
  connect (the dashboard SQL editor is the canonical entry point; no
  separate admin CLI surface).
- **Inspecting production data.**
  - The non-obvious fact that the dashboard SQL editor runs as
    `service_role` by default and therefore bypasses RLS — a query
    returning rows in the editor may return nothing for the app.
  - The `begin;` / `rollback;` wrap as the default exploratory shape.
  - The `set local role authenticated` + `set local "request.jwt.claims"`
    recipe for simulating a real user, including the
    `"is_anonymous": true` claim variant since the app gates
    "real account required" actions on that flag.
- **One-off SQL fixes.**
  - Data-fix-vs-schema-fix rule: schema is always a migration; data
    is OK in the SQL editor with a paper trail.
  - Safe-edit checklist (`begin;` → SELECT → UPDATE → re-SELECT →
    `commit;` and bail to migration when bulk).
  - Stripe-specific: don't synthesize the row by hand — use Stripe
    Dashboard "Resend webhook" so the signature verification +
    dedupe path from [ADR 0011](../adr/0011-stripe-webhook-dedupe.md)
    actually runs.
- **RLS surprises in the editor.** Four traps: editor bypass, NULL
  `auth.uid()`, OR-stacked policies, `security definer` skipping
  RLS. The `security definer` callout includes the existing
  [search_events_rpc](../../supabase/migrations/20260513000300_search_events_rpc.sql)
  as the in-repo example.
- **Storage growth & performance.** Reports → Database for sizes,
  Query Performance for slow queries, cross-ref to
  [perf_indexes migration](../../supabase/migrations/20260520000000_perf_indexes.sql)
  before adding indexes since the obvious ones are already there.
  Honest TTL table for `notifications_outbox` (30d sent /
  indefinite failed) and `stripe_webhook_events` (90d, past
  Stripe's retry window) noting that **no prune job exists today** —
  follow-up flagged.
- **Connecting from outside the dashboard** — pooler vs direct
  connection string, read-only role recommendation, local-dev port.
- **When you really do need to bypass RLS in code** — short rule:
  `getServerSupabase()` wherever possible; admin client only in
  infrastructure adapters or `'server-only'` lib modules, with a
  comment explaining why.
- **See also** cross-links.

## Pattern notes (worth keeping in mind)

- **The audit gap was conventional knowledge, not config.** Nothing
  about how the DB is set up was missing — what was missing was the
  set of "things every operator learns the hard way the first time
  they run a query in prod" (service_role default, `auth.uid()`
  NULL, where to set the JWT claims). Worth treating those as the
  body of the doc rather than padding with config readers can find
  themselves.
- **Cross-doc routing matters more than content.** Half the value
  here is the top pointer table — without it the next person will
  duplicate migration content because they read this doc first
  rather than AGENTS.md.
- **High-churn table TTLs are deferred-by-design.** Calling out
  `notifications_outbox` and `stripe_webhook_events` as needing
  pruning eventually, but documenting "no prune job today" rather
  than writing one preemptively, matches the project's general
  posture (ship the smallest useful thing, capture the follow-up
  honestly).
