# Bundle 108 — Bracket: public spectator view

## Why

Pre-this-bundle, the only way to watch a tournament bracket update
was to open `/events/[id]/bracket` — a page designed for hosts and
team captains. It carries reset-bracket controls, generate-playoff
forms, edit-result detail panels per match, host notice flashes,
and `export const dynamic = 'force-dynamic'` because it depends on
auth cookies for `canManage` / captain checks.

A spectator (parent in the bleachers, ref between matches, friend
checking the score from home) doesn't need any of that and
shouldn't have to log in. We needed a dedicated public surface
that:

- Anyone with the link can open — no auth required.
- Updates live via the same realtime channel hosts use (bundle 105).
- Hides every control that wouldn't do anything for a non-host /
  non-captain.
- Doesn't poison the host page with spectator hacks (separate
  route, not a query param flag).

## What changed

### New `/bracket/watch` route

**NEW** [apps/web/src/app/events/[id]/bracket/watch/page.tsx](../../apps/web/src/app/events/%5Bid%5D/bracket/watch/page.tsx).
Server component, no `force-dynamic`. Calls `getEventDetail` with
`viewerId = null` (no `getViewer()` call at all), reads bracket
state directly from `repositories.bracketRepo`, and renders the
same `BoardView` the host page does — with `isHost={false}` and
`viewerId={null}`.

That prop choice does all the work: `BoardView`'s "Reset bracket"
details panel is gated on `props.isHost && props.status ===
'active'`, the "Generate playoff" CTA branches to a spectator
copy ("Pool play is complete. Waiting for the host to generate
the playoff."), and `MatchCard.canEdit` becomes false because
neither the host nor any captain branch is reachable. No
spectator-specific copy paths were needed inside the shared
components — the existing gates already covered the read-only
case.

For the setup state (bracket exists but isn't generated yet, or
no bracket at all), the watch page short-circuits to a neutral
"Seeding is in progress" / "Host hasn't created the bracket yet"
panel. No exposure of the host's seeding workspace.

Realtime: `BracketRealtimeRefresher` from bundle 105 is mounted
the same way as on the host page — anon subscriptions work
against the existing `supabase_realtime` publication because
`tournament_brackets`, `bracket_matches`, and
`bracket_match_sets` all have `for select using (true)` RLS.

A small ● LIVE pill in the header and "Updates automatically"
microcopy tell the spectator the page is self-refreshing so they
don't pull-to-refresh.

### Discoverability link

[apps/web/src/app/events/[id]/bracket/page.tsx](../../apps/web/src/app/events/%5Bid%5D/bracket/page.tsx)
header now carries an "Open public spectator view →" link
underneath the registered-teams count. Hosts copy the URL out of
the address bar and share it with the gym / parents / scoreboard.

## Patterns observed

- **A "spectator" mode is best modelled as a separate route, not
  a query flag, when the existing component tree already has the
  right gates.** BoardView's `isHost` / `viewerId` props were
  already used everywhere a host or captain control rendered,
  because that's how the same component already serves
  non-captain logged-in users on the host route. Re-using those
  gates for an entirely unauthenticated viewer was free — the
  expensive part would have been weaving "is this the spectator
  page?" booleans through every sub-component, which we avoided.
- **RLS `select using (true)` is the seam that makes anon read
  pages cheap.** Because the bracket tables were already public
  for reads (and bundle 105's realtime publication relies on
  that), the watch page didn't need an admin client, didn't
  need a separate API route, didn't need RLS migration. The
  same `SupabaseBracketRepository` used by hosts works for
  spectators.
- **Two routes that share 90% of their rendering tree is fine
  when the 10% is "is this user allowed to mutate."** A single
  flag prop (`isHost`) plus the absence of an authed viewer
  cleanly separates the two surfaces without a bunch of
  conditional branches at the page level. The host page keeps
  its host-specific noise (notice flashes, setup view, reset
  controls) and the watch page stays a clean read-only mirror.

## Follow-ups deferred

- **True caching.** The watch page is still effectively dynamic
  because `getServerSupabase()` transitively calls `cookies()`.
  To make it CDN-cacheable for anon viewers we'd need to route
  reads through `getAdminSupabase()` inside an `unstable_cache`
  block tagged with `bracket:${bracketId}`, and have mutating
  actions call `updateTag()` on that tag in addition to their
  existing `revalidatePath`. The realtime refresher gives
  near-instant freshness already, so this is purely a CDN cost
  win — defer until traffic justifies it.
- **Share button on host page.** Copy "Open public spectator
  view →" is fine for now; a one-click "Copy link" with a clipboard
  API call would be friendlier on mobile where address-bar copy is
  awkward. Cheap follow-up.
- **OG image for the watch URL.** The watch page falls back to
  the event's existing `opengraph-image.tsx`. A bracket-themed OG
  with the current leaders rendered server-side would be a nice
  Twitter/Discord embed when the link gets shared. Defer.
- **Auto-scroll to the latest completed match.** When a spectator
  loads the watch page mid-tournament, the bracket is wide and
  the most recent action might be off-screen. A small "Jump to
  latest" affordance, or a scroll-into-view effect when realtime
  fires and a new winner is set, would be a nice polish. Defer.
- **`<meta name="robots" content="noindex">` on early-stage
  brackets.** Once a tournament is over we probably _do_ want
  Google to index the result page. While in setup it's just
  noise. Skip indexing until status hits `active`. Defer until
  someone notices SERP weirdness.
