# 2026-05-24 — Bundle 80: Analytics outbox at the handler boundary

## Context

Bundle 79 closed P2 #8 (web-vitals → PostHog). The last architectural
item on the analytics audit was P2 #6: "no server-side capture from
domain events." Bundles 75 and 76 wired the typed `AnalyticsPort` and
the first wave of captures, but every call site lived in the
**action layer** — `joinEvent` and `joinEventAtPosition` in
`events/[id]/rsvp-actions.ts` each fanned out into a Supabase metadata
read, then called `analytics.capture(...)` after the handler returned.
That worked, but it (a) duplicated the join/leave bookkeeping in two
places, (b) hard-coded `waitlist: false` even when the aggregate
actually pushed the user to the waitlist, and (c) ran
`analyticsFromEnv()` three times per request because the action and
the composition root each instantiated their own adapter. The
hexagonal answer is an **outbox** at the application-handler boundary:
the aggregate raises domain events while applying the command; the
handler drains them after `repo.save(...)` and forwards them through
a pure mapper to `AnalyticsPort`.

## Decisions

- **Scope = `SpotFilled` + `SpotReleased` only (v1).** These are the
  two domain events whose current analytics counterparts
  (`event_joined`, `event_left`) can be derived entirely from
  aggregate state. `event_published` needs the publish-time pricing
  / division shape, which the create-event action mutates after the
  aggregate save; checkout / payout / signup captures depend on
  Stripe side-channel data. Promoting them would either require
  carrying side-channel data through the aggregate (leaks
  infrastructure into the domain) or adding a second-shape "context
  payload" to the outbox (premature). The mapper returns `null` for
  every other `DomainEvent`, so we can grow the mapping without
  touching the dispatcher.
- **Mapper + dispatcher live in `packages/application/`.** The mapper
  imports `VolleyballEvent` to read aggregate state — it can't sit
  in `domain` (the domain doesn't depend on analytics) and it can't
  sit in `infrastructure` (the handler doesn't depend on
  infrastructure either). Application is the right seam.
- **`AnalyticsPort` arg is optional on the handler constructor.**
  Existing handler tests pass `(repo)` only. Making the dispatcher a
  noop when `analytics` is `undefined` keeps the test surface
  unchanged and lets the composition root opt-in without touching
  the test fixtures.
- **Hoist the singleton in `apps/web/src/lib/handlers.ts`.** Before
  this bundle, `analyticsFromEnv()` ran three times per request (once
  in the composition root for the previously action-layer-only
  captures, once in `joinEvent`, once in `joinEventAtPosition`).
  After: one `export const analytics = analyticsFromEnv();` above
  the `handlers` object, threaded into all three handler
  constructors.
- **Keep the refund-path capture inline.** The Stripe
  `charge.refunded` webhook deletes the `event_attendees` row
  directly via the admin client — it never traverses
  `LeaveEventHandler`, so the outbox can't see it. The refund branch
  of `rsvp-actions.ts` keeps `captureEventLeft` with an updated
  docstring explaining why; the unpaid-leave branch loses its inline
  capture because that path _does_ run through the handler.
- **Fail-quiet, per event.** `dispatchAnalyticsOutbox` wraps each
  `analytics.capture(...)` in its own try/catch. One bad mapping
  must not block the others, and analytics errors must never
  propagate to the request.

## Changes

- **NEW** `packages/application/src/analytics/event-analytics-mapper.ts`
  — pure `mapDomainEventToAnalytics(de, aggregate)`. `SpotFilled` →
  `event_joined` (carries truthful `waitlist` + `position` from the
  aggregate); `SpotReleased` → `event_left`. Shared helper
  `eventScopedProps()` reads host id, type, metro, default-division

  `VolleyballEvent`.

  — `dispatchAnalyticsOutbox(aggregate, analytics)` drains
  `aggregate.pullEvents()` and forwards each mapped capture.

- **NEW** `packages/application/src/analytics/event-analytics-mapper.test.ts`
  — pins SpotFilled / SpotReleased props (price, metro,

## Patterns surfaced

- **Outbox at the application handler boundary is the right home
  for analytics that can be derived from aggregate state.** The
  pattern is small: `pullEvents()` → mapper → `port.capture()`.
  Reach for it whenever a new domain event has a matching
  taxonomy entry.
- **Action-layer captures are the right home for analytics that
  depend on infrastructure / side-channel data.** Don't try to
  drag Stripe ids into the aggregate just to put the capture in
  the outbox; the seam is the wrong one.
- **`analyticsFromEnv()` is a process-level singleton, not a
  per-request factory.** The composition root in `lib/handlers.ts`
  is the right place to construct it once.

## Follow-ups

- **Webhook-driven refund leave** still captures inline because the
  Stripe webhook deletes `event_attendees` directly. Next time we
  refactor the webhook, route it through a `LeaveEventCommand` so
  the outbox catches it and we can drop the inline `captureEventLeft`
  - its `loadEventAnalyticsContext` helper.
- **`event_published`** lives at the create-event action because
  publish-time pricing / division mutations aren't on the
  aggregate. Once create-event collapses the post-save mutations
  into the aggregate (or once we raise `EventPublished` with the
  needed payload), promote the capture to the outbox.
- **Expand the taxonomy.** `TeamRegistered`, `TeamWithdrawn`,
  `FreeAgentJoined`, `FreeAgentLeft` all raise domain events the
  mapper currently sends to `null`. Add analytics counterparts
  (`team_registered`, `free_agent_joined`, etc.) before
  rostered-tournament hosting becomes the primary funnel.
- **Positional `waitlist` parity.** The outbox now reports the
  aggregate's truthful waitlist flag for `JoinEventWithPosition`
  overflow — old PostHog dashboards filtering by
  `waitlist == false` will see a small uplift in waitlist joins
  on the `event_joined` event. Heads-up for the analytics review.
