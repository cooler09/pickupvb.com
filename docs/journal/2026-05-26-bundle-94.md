# 2026-05-26 — Bundle 94: ad-hoc team registration soft-delete

## Goal

Third slice of the data-lifecycle audit
([docs/audits/data-lifecycle.md](../audits/data-lifecycle.md)). Bundle
92 was the cron infra, Bundle 93 was groups/teams/broadcasts soft-delete
UX. This bundle takes the "cleanest one-migration + one-action-update"
remaining backlog item:

- **P2 #5** — `event_team_registrations` should soft-delete after Stripe
  checkout (currently hard-deletes through every path that touches it).

Out of scope (deferred to later bundles): P3 #2 hero-orphan Storage
walker, broadcast history UI, account-deletion app path, slug
reclamation, undelete UX, admin "view deleted" surfaces.

## Context

The only delete path for an ad-hoc team registration today is
`hostForceWithdrawTeamRegistration` in
[apps/web/src/app/events/[id]/host-team-registration-actions.ts](../../apps/web/src/app/events/[id]/host-team-registration-actions.ts).
It already gates on `payment_status ∈ {None, Refunded}` — if the team
has paid and hasn't been refunded, the host has to refund first.
After the gate, it `DELETE`s the row.

That's fine for `None` (the captain never started checkout, so the
row has no Stripe footprint to preserve). But for `Refunded`, the row
is the only place that ties a real Stripe `payment_intent_id` and
`amount_paid_cents` back to a roster, captain, and division. Once we
hard-delete it, refund reconciliation and dispute response have
nothing to query.

The audit recommended: HARD pre-checkout / SOFT post-payment.

## Changes

### 1. Schema — `deleted_at` column + SELECT-policy filter

[supabase/migrations/20260629000000_event_team_registrations_soft_delete.sql](../../supabase/migrations/20260629000000_event_team_registrations_soft_delete.sql)

Same shape as the profiles / groups / teams / broadcasts pattern:

- `event_team_registrations.deleted_at timestamptz` nullable, default
  NULL.
- Partial index `WHERE deleted_at IS NOT NULL` (cheap; lets the future
  account-deletion purge find tombstones without scanning live rows).
- Rewrote `event_team_registrations_select` to add `AND deleted_at IS
NULL`. The user supabase client (RLS in effect) automatically stops
  seeing soft-deleted rows on the captain page, public event detail,
  the division-winner picker, etc.

Members table (`event_team_registration_members`) is unchanged: its
SELECT policy is also `using (true)`, but joins through the parent
registration use the parent's policy via the join planner, so
soft-deleting the parent removes the roster from any read that goes
through the registrations table. Direct admin queries against the
members table aren't a real read path in the app.

### 2. Port — added `softDelete` alongside `delete`

[packages/domain/src/events/event-team-registration-repository.ts](../../packages/domain/src/events/event-team-registration-repository.ts)

Kept `delete` for the rare `None` case (no Stripe footprint, cleanest
to remove outright). Added `softDelete(id)` for the post-checkout
path. The aggregate itself doesn't need a domain method — soft-delete
is a persistence concern, not a state-machine transition (the row's
`payment_status` already records whatever payment terminus was
reached; `deleted_at` just hides it from product surfaces).

### 3. Repository — implementation + live-row filter on `exists`

[packages/infrastructure/src/supabase-event-team-registration-repository.ts](../../packages/infrastructure/src/supabase-event-team-registration-repository.ts)

- `softDelete()` issues `UPDATE … SET deleted_at = now() WHERE id = $1
AND deleted_at IS NULL` (idempotent — a second call no-ops).
- `existsForCaptainInDivision()` filters `deleted_at IS NULL` so a
  withdrawn captain can re-register in the same division. The "one
  team per captain per division" invariant only applies to live rows.
- `findById`, `findByCheckoutSessionId`, `findByPaymentIntentId`
  **intentionally do not filter**. The webhook handler chain
  (`charge.refunded`, `checkout.session.expired`, late retries) must
  still resolve the row even after soft-delete; otherwise we'd
  500-loop on the retry curve. The downstream state-machine guards
  are already idempotent, so finding a soft-deleted row and re-running
  `markRefunded` is a safe no-op.

### 4. Action — fork on `payment_status`

[apps/web/src/app/events/[id]/host-team-registration-actions.ts](../../apps/web/src/app/events/[id]/host-team-registration-actions.ts)

`hostForceWithdrawTeamRegistration` now:

```ts
if (reg.paymentStatus === RegistrationPaymentStatus.None) {
  await eventTeamRegistrationRepo.delete(reg.id);
} else {
  await eventTeamRegistrationRepo.softDelete(reg.id);
}
revalidatePath(returnPath);
updateTag(`event:${eventId}`);
```

`updateTag` was missing from this action entirely before this bundle —
the event detail loaders cache reads with `tags: ['event:${id}']`, so
without it the page wouldn't reflect the withdrawal until the 60s
revalidate window. Added on the way through; trivial correctness fix.

### 5. Admin-client read filters

[apps/web/src/app/events/[id]/\_loaders/load-event-detail.ts](../../apps/web/src/app/events/[id]/_loaders/load-event-detail.ts)

Two `unstable_cache` loaders (`loadAdHocPublicRowsCached`,
`loadAdHocRowsCached`) use the admin client, which bypasses RLS, so the
SELECT-policy filter doesn't apply. Both now `.is('deleted_at', null)`
explicitly.

Left as-is on purpose:

- The user-client read of the eligible-team picker at line 659 — RLS
  filters automatically.
- The `record-division-winner-actions.ts` registration lookup — user
  client, RLS applies.
- `SupabaseEventRepository`'s winner-label lookup — admin client, but
  we _want_ soft-deleted registrations to still resolve here so
  historical winner attribution survives team withdrawal after the
  bracket has been recorded.

## Patterns surfaced

- **Per-table read-side audit on every soft-delete bundle.** With RLS
  rewritten on the table, every admin-client read path (admin clients
  bypass RLS) becomes a regression risk. Today there were only three
  admin reads of `event_team_registrations` and one of them (winner
  labels) intentionally must _not_ filter. The "RLS filter + explicit
  `.is('deleted_at', null)` on admin reads + don't-filter on webhook
  lookups" triad is the same pattern that landed in Bundle 93. Worth
  promoting into the AGENTS.md "Patterns surfaced by audits" section
  if a fourth soft-delete table comes up.
- **Webhook lookups must skip the `deleted_at` filter.** Soft-deleted
  rows still receive Stripe webhook traffic (late `charge.refunded`
  retries, account-suspension `transfer.reversed`, etc.). The
  idempotent state-machine guards on the aggregate (`markRefunded` is
  a no-op when already refunded) make this safe; filtering at the
  lookup layer would 500-loop the retry curve.
- **`payment_status === None` does _not_ need a tombstone.** This is
  the only `delete()` call site left in the repo for this aggregate
  and it'll stay — pure pre-checkout abandonment shouldn't litter the
  table.
- **No domain command needed for "flip a flag."** AGENTS.md explicitly
  warns against over-engineering server-action-only changes. The
  application layer already has handlers that touch registrations
  (`event-team-registration.handler.ts`) but none own a "withdraw"
  workflow today, so adding `WithdrawTeamRegistrationCommand` would be
  a speculative abstraction. Inline server action wins.

## Follow-ups deferred

- **Host UI affordance for the soft-delete path.** Today the form-bound
  action shows the same `team_force_withdrawn` flash whether the row
  was hard- or soft-deleted. A future bundle could distinguish refund
  → soft-delete in the UI so the host knows the row is still on the
  books for reconciliation. Low priority; the audit trail is the
  important bit and that's live now.
- **`hostForceWithdrawTeamRegistration` `updateTag` call** was missing
  before this bundle. Other actions in the same file (`hostMark…`,
  `hostRefund…`) likely have the same gap. Not in scope — separate
  cache-coherency sweep, probably bundled with the next event-host
  audit pass.
- **Soft-delete adoption on `events` itself** is still open (audit
  inventory recommends "SOFT — host-initiated true delete"). The
  current cancellation flow uses `status='cancelled'` which is a
  different lifecycle than deletion. Not part of P2 #5.
- **Account-deletion purge** of soft-deleted registrations still lives
  in privacy.md P1 #1–#3. The tombstones this bundle creates need to
  be honored by that purge.

## Addendum — Bundle 95: hero-images orphan walker (P3 #2)

Follow-on slice completed the remaining open data-lifecycle backlog item
for hero-image storage cleanup.

### Goal

Close data-lifecycle P3 #2 by replacing the stale "DELETE FROM
hero_images" recommendation with the real storage-layer implementation
(`hero_images` is not a table in this codebase).

### Changes

- Added
  [supabase/migrations/20260630000000_hero_images_orphan_cleanup.sql](../../supabase/migrations/20260630000000_hero_images_orphan_cleanup.sql).
- Introduced `public.purge_hero_image_orphans(grace_hours int default 24)`
  as a `SECURITY DEFINER` helper that:
  - scans `storage.objects` in bucket `hero-images`,
  - parses path segments
    `{user_id}/{entity_type}/{entity_id}/hero.{ext}` via `storage.foldername`,
  - keeps only objects still referenced by a live owner row + matching
    `hero_image_url`,
  - purges everything else.
- Scheduled daily pg_cron job:
  `hero_images_purge_orphans` at `0 6 * * *`.

### Notable implementation detail

Supabase Storage ships a guard trigger (`storage.protect_delete`) that
blocks direct SQL deletes unless the session setting
`storage.allow_delete_query = 'true'` is enabled. The helper sets this
inside the function (`set_config(..., true)`) before deleting from
`storage.objects`.
