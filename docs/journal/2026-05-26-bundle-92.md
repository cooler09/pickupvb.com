### 1. Retention cron jobs migration

[supabase/migrations/20260627000000_retention_cron_jobs.sql](../../supabase/migrations/20260627000000_retention_cron_jobs.sql)

Five pg_cron jobs, idempotent by name (`cron.schedule(name, ...)` upserts
on re-apply), staggered 04:00–05:00 UTC to keep IO concentrated in a
quiet window:

| Job                                    | Predicate                                             |
| -------------------------------------- | ----------------------------------------------------- |
| `notification_outbox_purge_sent_90d`   | `sent_at IS NOT NULL AND sent_at < now() - '90 days'` |
| `notification_outbox_purge_failed_30d` | `status='failed' AND created_at < now() - '30 days'`  |
| `notifications_purge_read_30d`         | `read_at IS NOT NULL AND read_at < now() - '30 days'` |
| `notifications_purge_unread_180d`      | `read_at IS NULL AND created_at < now() - '180 days'` |
| `marketing_attribution_purge_24mo`     | `captured_at < now() - '24 months'`                   |

`create extension if not exists pg_cron;` precedes the schedules.
Applied locally clean (`pnpm db:migrate` → "Local database is up to
date."). CI/CD picks up the file and applies on next deploy per the
AGENTS.md migration policy.

The migration documents in a comment block why the hero_images orphan
sweep is deferred — see Decisions below.

### 2. E2E fixture cleanup helper

[apps/web/tests/e2e/\_helpers/cleanup.ts](../../apps/web/tests/e2e/_helpers/cleanup.ts)

Centralizes admin-Supabase plumbing for `afterAll` hooks that need to
hard-delete rows the suite created when the app exposes no UI delete.

Opt-in via dedicated env vars (`E2E_CLEANUP_SUPABASE_URL` +
`E2E_CLEANUP_SUPABASE_SECRET_KEY`) — **not** the app's `SUPABASE_URL` /
`SUPABASE_SECRET_KEY`. This is deliberate: a contributor running e2e
against a project they don't own (e.g. local-only dev with prod env
loaded) can't accidentally drop rows. When the env vars are absent,
every helper is a no-op and the helper warns once.

Exports:

- `getCleanupClient()` — memoized; returns `null` when disabled.
- `deleteGroupBySlug(slug)`, `deleteTeamBySlug(slug)`,
  `deleteEventById(id)`, `deleteCommunityListingBySlug(slug)` — targeted
  per-spec deletes.
- `sweepLeakedE2EFixtures()` — broader name-prefix sweep
  (`name LIKE 'E2E Test Group %'` etc.) for a future maintenance script
  or `globalTeardown`. Not wired anywhere yet.

## Decisions

### Hero-orphan scope correction — recommendation in original audit was wrong

The data-lifecycle audit listed P3 #2 as an XS one-line cron:
`delete from hero_images where resource_id not in (...)`. Verification
during implementation found:

- There is no `hero_images` table. `hero_image_url text` is a column on
  `events`, `groups`, and `profiles`.
- Actual image bytes live in the `hero-images` Storage bucket, keyed by
  `{user_id}/{entity_type}/{entity_id}/hero.{ext}` per the upload action.

Genuine orphan cleanup therefore requires walking `storage.objects`,
parsing the path components, and cross-checking the entity id against
`events` / `groups` / `profiles`. Possible (and worth doing — Storage
costs accumulate) but it's a `plpgsql` function + cron schedule + tests,
not a one-line DELETE. Re-graded as S–M; left open.

### Opt-in env vars for the cleanup client (not `SUPABASE_SECRET_KEY`)

The natural plumbing is `createSupabaseAdminClient` from
`packages/supabase/src/admin.ts`, which reads `SUPABASE_URL` +
`SUPABASE_SECRET_KEY`. Rejected, because:

- The dev e2e command (`pnpm --filter @pickupvb/web e2e:ui` against
  `dev.pickupvb.com`) ships with a local Supabase env loaded in `.env.local`.
  Reusing those vars would make `afterAll` delete from the **local**
  database while the tests were running against **dev** — silent and
  confusing.
- An app-name-collision env var (`SUPABASE_*`) invites accidental
  loading via shared `.env` files. Dedicated `E2E_CLEANUP_SUPABASE_*`
  forces an explicit operator decision.

Helper degrades to no-op + one-time warn when env is unset, so the
ad-hoc contributor case is "leak as before" (status quo) rather than
"crash the test run".

### Why a helper rather than a `globalTeardown`

A `globalTeardown` running `sweepLeakedE2EFixtures()` would close the
loop in one place. Skipped this bundle because:

- A bulk name-prefix delete in teardown couples the fixture-naming
  convention to the cleanup mechanism; future specs that pick a
  different naming pattern silently leak. Per-spec `afterAll` makes
  ownership explicit.
- `globalTeardown` only fires when the runner exits cleanly. Repeated
  Ctrl-C runs during iteration would still leak. Per-spec `afterAll`
  fires per-spec.

`sweepLeakedE2EFixtures` is exported for a future maintenance script
that an operator can run by hand against `dev` to clear historical
debris (the 27 leaked groups the audit found).

### `cancelled` events left as soft-state

`event-host.authed.spec.ts` already cancels via UI in `afterAll`. That
leaves the row with `status='cancelled'` — product-correct (hosts can
review past cancelled events; refunds/audit trail need the row). Not
treated as a fixture leak. If the spec ever fails before the cancel,
the operator-run sweep would need an explicit `deleteEventById` call;
deferred until that surface area matters.

## Patterns surfaced

- **Audit recommendations need verification before grading.** The
  hero_images miss is the second time this audit cycle (cf. the
  `event_co_hosts` replica-identity finding) that a "one-line fix"
  estimate didn't survive contact with the schema. When grading
  effort on an audit, the rubric should require opening the
  referenced file/table, not just trusting the name.
- **Test fixtures need namespaced env vars, not app env vars.** Same
  reason `'use server'` + `server-only` exist for app code: anything
  that can write to a database should make the writer's identity
  unambiguous at the call site. Worth lifting into AGENTS.md if a
  second e2e helper needs admin creds.
- **pg_cron idempotency by name is a quiet win.** Re-running
  `cron.schedule('foo', '...', '...')` upserts on the jobname — no
  guard clause needed in the migration. Worth noting in
  [docs/database-operations.md](../database-operations.md) when next
  touched (a future-agent reading the migration may assume they need
  a `delete from cron.job where jobname = ...` first).
