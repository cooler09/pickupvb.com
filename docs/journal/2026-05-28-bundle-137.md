# Bundle 137 — Density scale (2026-05-28)

Ninth M3-adoption bundle. Closes the vocabulary + reference call
sites of audit **P2 #15 "No density / responsive density"** by
introducing three M3 density utilities, a `.md-table` consumer, and
migrating the two tables the audit explicitly called out — receipts
and earnings — to compact-on-mobile / comfortable-on-desktop. Group
member list and other dense lists are deferred as opportunistic
follow-ups using the same primitives. The M3 data-table primitive
(P3 #18) stays deferred per original audit guidance ("until a third
table appears").

See [docs/audits/m3-alignment.md § Bundle 137](../audits/m3-alignment.md#bundle-137--density-scale-2026-05-28)
for the line-by-line decision log.

## Context

[P2 #15](../audits/m3-alignment.md#15-no-density--responsive-density)
flagged that every list, table, card uses one set of paddings —
specifically receipts and earnings tables cram on mobile while
group-member lists are sparse on desktop. The audit prescribed the
M3 density scale (`comfortable` / `standard` / `compact`) with a
4 dp step between rungs, applied per-breakpoint.

The 10-bundle adoption plan slots density as Bundle 9 — after the
Radix primitives (Bundles 4/6/8) and after the structural primitives
(Bundle 5 BottomNav, Bundle 7 TextField) so it lands as a
"polish-the-edges" pass without competing for design-decision
attention.

## Decisions

- **Cascading CSS custom properties.** `--md-row-py` and
  `--md-row-px` live on `:root` (effectively) by virtue of being
  set on a parent (`<table>`). Descendant cells consume them via
  the `.md-table > section > tr > cell` selector. The alternative
  (per-cell `md-cell` modifier class) would force the migration to
  touch every `<td>` with a new className and would lose the
  "set density once per surface" ergonomic that lets a responsive
  variant on the parent (`md-density-compact md:md-density-comfortable`)
  ramp every cell simultaneously.
- **M3 vocabulary verbatim.** `comfortable` / `standard` /
  `compact` are the names the M3 spec uses; the same names appear
  in Figma and in design-system discussions. Coining local names
  (`tight` / `roomy` / `airy`) would force a glossary lookup every
  time someone moved between Figma and the codebase.
- **Compact on mobile, comfortable on desktop.** M3's default is
  `comfortable` for desktop, but the audit's evidence was
  cram-on-mobile, so we ramp down on small screens rather than up.
  `md-density-compact md:md-density-comfortable` is the canonical
  ramp. The reverse (`comfortable` on mobile, `compact` on desktop)
  would lose ~30% of visible rows on the smallest viewport.
- **`.md-table` is opt-in.** A blanket `table { ... }` selector
  would silently change spacing on every existing `<table>` in the
  codebase (host panels, embedded tables in markdown renderers,
  etc.). Opt-in via class is the migration-safe boundary.
- **`.md-table` baseline is `standard`.** If a caller forgets a
  density utility, they get 8 px / 12 px padding (the M3
  `standard` row), not zero. The density utility class overrides
  via CSS variable specificity — both declarations target the same
  custom properties; the later one wins.
- **The selector chain is the API contract.**
  `.md-table > thead > tr > th, .md-table > tbody > tr > th,
.md-table > tbody > tr > td, .md-table > tfoot > tr > td` is
  explicit about which cell positions get padding. Tables without a
  section wrapper (raw `<table><tr><td>` chain) intentionally don't
  get styled — that pattern is rare and indicates either a
  semantic-table bug or a non-data-table use case.
- **No per-cell density utility.** The audit's evidence was tables;
  lists are a different layout primitive where M3 density mapping
  is less obvious (line-height + leading dominate the visual
  density on `<ul>`/`<li>`, not just padding). Wait for concrete
  dense-list pain before designing the list utility.

## Patterns observed

- **CSS custom properties are the right token transport for
  layout that needs to compose with responsive variants.** Density,
  spacing scales, even color roles all benefit from "set the var
  on a parent, descendants consume it" rather than per-element
  utility classes. The Bundle 134 dialog motion class
  (`md-dialog-motion`) followed the same pattern with
  `--radix-dialog-content-transform-origin`.
- **`@utility` shorthand in Tailwind v4 participates in
  responsive variants.** `md-density-compact md:md-density-comfortable`
  works without any extra setup; same compose pattern as
  `flex md:grid`. Worth remembering for future M3 utilities that
  need to vary per-breakpoint.
- **Migrating a table to density is mechanical.** Every `<th>` /
  `<td>` loses its `px-3 py-2` and keeps everything else
  (`text-right`, `text-muted`, `whitespace-nowrap`,
  `hidden sm:table-cell`). The diff is large but uninteresting —
  ideal candidate for codemod if more tables surface.

## Follow-ups deferred

- **Dense lists** (group-member list, walk-in list, host roster).
  Open audit-side: `.md-list` consumer parallel to `.md-table` vs.
  per-item utility. Wait for concrete need.
- **M3 data-table primitive (P3 #18)** — still two tables in the
  codebase, audit guidance stands ("defer until a third table
  appears").
- **`<table>` audit for non-section-wrapped tables** — the
  selector chain skips them by design, but if any are intended to
  be data tables, they need a quick refactor to wrap in
  `<thead>` / `<tbody>`.
- **`tap-target` interaction with compact rows.** No icon-only
  cells in the migrated tables (action cells are text links), so
  no current collision. Re-check if a future migration introduces
  icon-only cell affordances at compact density.
- **Horizontal-scroll sanity scan.** Earnings page wraps the
  `<table>` in `overflow-x-auto`; receipts does not. Both work on
  iPhone SE at compact density, but worth a visual pass on the
  smallest viewport before declaring P2 #15 fully closed.
