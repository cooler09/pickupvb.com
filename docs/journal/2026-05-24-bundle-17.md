# 2026-05-24 — Bundle 17: FormData hard cap + Turnstile freshness

## Context

Bundle 16 landed the last open security P2 (rate limiting on
email-sending paths). The remaining security-audit backlog was P2 #3a
(CSP enforcement promotion — needs a production soak window observing
the Report-Only header shipped in Bundle 15 before flipping it on) and
the P3 trifecta:

- **#8** Audit-log coverage gaps (group roles, co-host, Stripe account
  mutations, subscription state).
- **#9** No global hard cap on `FormData` field length.
- **#10** Turnstile tokens accepted without checking `challenge_ts`,
  permitting replay of a pre-generated token.
- **#11** Preemptive file-upload hardening (no upload endpoints exist).

Bundle 17 picks **#9 and #10** because they're both surgical one-file
hardening with concrete attack surface today, and they pair well in a
single change-bundle. #3a still needs more soak time. #8 deserves its
own bundle (new table + migration + writes at multiple call sites). #11
stays deferred until uploads exist.

## Decisions

- **Apply the cap at `rawValue()` rather than each public helper.**
  Single chokepoint → every consumer (`field`, `fieldOrNull`,
  `fieldOrUndefined`, `bool`) inherits the ceiling automatically and
  there's no way to forget the cap on a new helper added later.
- **Truncate rather than reject.** The audit's wording is "enforce a
  global hard cap." Truncating to 4 KB is the minimally disruptive
  shape: legitimate fields (longest in tree is `business_address` @ 400
  chars) are unaffected, while an attacker who tries to ship a 1 MB
  `first_name` ends up with 4 KB of `a` — downstream length validations
  (e.g. `fieldOrNull(formData, 'first_name', 60)`) then narrow further
  and reject the truncated junk on their own terms. A reject-at-cap
  approach would also work but would surface as opaque empty-string
  fields with no diagnostic — worse for legitimate edge cases where
  someone genuinely typed too much.
- **4 KB chosen as the global ceiling.** Comfortably above every
  existing per-call `maxLen` (400 max in `business_address`), well below
  Next.js's default 1 MB body limit, and matches typical HTTP-header /
  cookie-size norms — a value any reviewer recognizes as "enough for
  any text input, not enough to weaponize."
- **Per-call `maxLen` keeps narrowing semantics.** Smaller caps still
  apply; only larger ones are silently clamped. No call-site changes
  needed.
- **Turnstile: 2-minute freshness window.** Cloudflare tokens are
  server-valid for ~5 min, but our actual flows (signup, RSVP, claim,
  checkout) involve the user solving the widget then submitting within
  seconds. 2 min is comfortable headroom for a slow network round-trip
  but tight enough to defeat realistic replay.
- **Missing `challenge_ts` accepted.** Cloudflare returns it on every
  success response, so the absence path is only hit on a malformed /
  mocked response. Accepting (rather than rejecting) the success
  payload keeps backward-compatible behavior if Cloudflare ever changes
  the response shape; the rejection is keyed only on _stale_, not on
  _missing_.
- \*\*Use `Date.parse()` + `Number.isFinite()` rather than `new Date()`
  - `getTime()`.\*\* Same result, but `Date.parse()` returns `NaN` (which
    `Number.isFinite()` excludes) for bad input without throwing — keeps
    the freshness check a no-op if Cloudflare ever returns a non-ISO
    string.
