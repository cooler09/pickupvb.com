# 2026-05-24 — Bundle 74: Community listing moderation queue (Stage A)

## Context

Bundle 73 hardened community-listing claims with three layers (UI filter
to eligible events, app-layer same-day + same-city match check, partial
unique index on `claimed_event_id`). That removed the easy abuse path
but still allowed a host who satisfied the match check to silently redirect
a listing they didn't post — the original submitter had no say. The next
step on the security trajectory was a moderation queue: claims become
`claim_pending` and only become live after the original submitter (or a
platform admin) approves.

Stage A (this bundle) ships the pending state + propose/approve/reject
flow + in-product UI. Stage B (email notifications via Resend + a
7-day auto-approve cron) is deferred.

## Decisions

- **Two reviewer roles, not one.** Both the original submitter and any
  platform admin can approve or reject. The submitter has the closest
  context (they posted the source); platform admins are a fallback for
  dead-submitter cases. The claimant cannot self-approve.
- **Public view is unchanged while pending.** A pending claim doesn't
  alter what an anonymous visitor sees — the listing still links out to
  the external page. Only the submitter, admins, and the claimant
  themselves see a "pending" surface. This avoids leaking moderation
  state to the public and keeps the listing useful while review is
  in flight.
- **Reuse the existing claim columns for the proposed state.** Rather
  than introducing `proposed_event_id` / `proposed_by_user_id`, the
  `claim_pending` status reuses `claimed_event_id`, `claimed_by_user_id`,
  and `claimed_at` (as "proposed at" while pending; reinterpreted as
  "approved at" once the claim is approved). The partial unique index
  shipped in bundle 73 then naturally covers both states, which is
  exactly the desired semantics: one event id can back at most one
  outstanding claim, pending or approved.
- **Edits are blocked while pending.** A submitter who could mutate the
  listing mid-review could bait-and-switch the claimant. `update()` now
  rejects `claim_pending` in addition to `claimed` / `removed`, and the
  `/edit` page guard mirrors it.
- **Three flash codes, not two.** `claimproposed` (the new claim
  outcome), `claimapproved`, `claimrejected`. The legacy `claimed` code
  stays in the banner map for older browser histories but is no longer
  emitted.

## Changes

- New migration `20260613000000_community_listings_claim_pending_status.sql`
  expands the status check constraint to include `claim_pending`.
- `packages/domain/src/community-listings/community-listing.ts`
  - `CommunityListingStatus` gains `'claim_pending'`.
  - `markClaimed` is split into `proposeClaim` / `approveClaim` /
    `rejectClaim`, each with its own state guard.
  - `update()` now also rejects `claim_pending`.
- `packages/domain/src/community-listings/community-listing-repository.ts`
  - `CommunityListingDetailReadModel` gains `claimedByUserId` so the
    page can recognize the viewer as the claimant.
- `packages/infrastructure/src/supabase-community-listing-repository.ts`
  - `getDetail` now selects + maps `claimed_by_user_id`.
- `packages/application/src/messages.ts`
  - New `ApproveCommunityListingClaimCommand` and
    `RejectCommunityListingClaimCommand`.
- `packages/application/src/commands/community-listing.handler.ts`
  - `ClaimCommunityListingHandler.execute` now calls `proposeClaim`
    instead of `markClaimed`.
  - New `ApproveCommunityListingClaimHandler` and
    `RejectCommunityListingClaimHandler`, both authorizing
    "submitter OR platform admin".
- `apps/web/src/lib/handlers.ts` registers the two new handlers.
- `apps/web/src/app/community/[slug]/listing-actions.ts`
  - `claimListing` success redirect changed from `claimed` to
    `claimproposed`.
  - New `approveListingClaim` / `rejectListingClaim` actions and
    matching `*FromForm` wrappers, mapping `UnauthorizedError` →
    `notallow`, `ConflictError` → `claimfail`, `NotFoundError` →
    `notfound`.
- `apps/web/src/app/community/[slug]/page.tsx`
  - Banner messages added for `claimproposed`, `claimapproved`,
    `claimrejected`.
  - `robots` rule now allows `claim_pending` (still indexable; public
    sees the original listing).
  - New "Pending claim — review required" block visible to
    `canManage` viewers, with a link to the proposed PickupVB event,
    the claimant's display name, and Approve / Reject buttons. A
    single supabase round-trip fetches the event title/slug and
    claimant display name, guarded behind `status === 'claim_pending'`.
  - Claimant-only informational banner ("Your claim is awaiting
    review").
  - "Edit" button in the manage card is now hidden while
    `claim_pending`.
- `apps/web/src/app/community/[slug]/edit/page.tsx` extends the
  status redirect guard to include `claim_pending`.

## Follow-ups

- **Stage B — notifications.** Add `community.claim.proposed`,
  `community.claim.approved`, `community.claim.rejected` notification
  kinds to `packages/notifications/src/kinds.ts` and wire the
  application handlers to emit via the existing `notify()` pipeline
  (`apps/web/src/lib/notify.ts`). Pair with Resend templates so the
  submitter gets an email on `proposed` and the claimant gets one on
  `approved`/`rejected`. Pattern lives in
  `apps/web/src/lib/email-resend.ts`.
- **Stage B — 7-day auto-approve cron.** Add a Vercel cron route at
  `apps/web/src/app/api/community/claims/auto-approve/route.ts`
  (model on `apps/web/src/app/api/notifications/reminders/route.ts`)
  that finds `claim_pending` rows older than 7 days where the
  submitter has not acted and calls `approveClaim` via the application
  handler with a system identity. Register it in `vercel.json`.
- **Unit tests for the three new handlers.** No tests were added
  this bundle (matches the bundle-73 precedent of leaving claim-flow
  test coverage as a follow-up). Worth at least:
  `proposeClaim` from each starting status (active → ok, pending →
  Conflict, claimed → Conflict, removed → Conflict, hidden →
  Conflict); `approveClaim` / `rejectClaim` authorization (submitter
  ok, admin ok, third party Unauthorized); `update()` blocked while
  `claim_pending`.
- **Audit prod data before deploy.** Production may have legacy
  `claimed` rows; the migration is additive so they're fine, but worth
  a one-liner check before deploy to confirm no row is in an
  unexpected state.
