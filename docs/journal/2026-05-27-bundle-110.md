# Bundle 110 — Walk-in team form: capture roster inline

## Why

The phase-1 walk-in / ad-hoc team form was deliberately
name-only: a host running a bracket at the venue could type
"Court 3 Spikers" and get a team into the bracket immediately,
but to record who was actually on that team they had to leave
the bracket page and edit the team elsewhere. In practice that
second step gets skipped, and the bracket ends up with named
shells and no idea who played.

Goal for this bundle: let the host capture the starting roster
inline on the same form, without making roster fields required.
Empty rows are still valid (you can still type a name and click
Add team) but if the host wants to type "Jamie / [email protected]" in
the same gesture, they can.

## What changed

### New `WalkInTeamForm` client component

**NEW**
[apps/web/src/app/events/[id]/bracket/\_components/walk-in-team-form.tsx](../../apps/web/src/app/events/%5Bid%5D/bracket/_components/walk-in-team-form.tsx).
`'use client'` because the row list is variable-length and the
host can Add / Remove rows before submit. Renders:

- Team name (required, unchanged from the previous version).
- A list of player rows, each with a player name + optional
  email. Starts with two empty rows; "+ Add player" appends one;
  per-row ✕ removes it (hidden when only one row is left).
- Submit button "Add team" bound to the existing
  `addAdHocTeamFromForm` server action via `.bind()`.

Row identity is tracked with a monotonically increasing id kept
in `useState<number[]>`. The new id is derived **inside the
state updater** from the previous row list:

```ts
setPlayerRows((rows) => [...rows, (rows[rows.length - 1] ?? -1) + 1]);
```

The first attempt used a `let nextRowId = ...` captured by the
handler and mutated on click, which the React Compiler rejected
("Cannot reassign variable after render completes"). The
functional-updater shape is the only safe pattern under the
compiler — there's no captured mutable to flag.

### Server action parses variable-length player rows

[apps/web/src/app/events/[id]/bracket/actions.ts](../../apps/web/src/app/events/%5Bid%5D/bracket/actions.ts)
— `addAdHocTeamFromForm` now scans the FormData for keys
matching `^player_name_(\d+)$`, pairs each with the matching
`player_email_<i>`, and builds a `members` array passed to
`RegisterAdHocTeamCommand`. Empty-name rows are skipped so the
host can leave blank rows. Email is set conditionally with the
spread pattern so `exactOptionalPropertyTypes` stays happy:

```ts
members.push(email ? { displayName, email } : { displayName });
```

No hidden `player_count` field needed — the regex sweep handles
any number of rows the client decided to render.

### Setup view rewire

[apps/web/src/app/events/[id]/bracket/\_components/setup-view.tsx](../../apps/web/src/app/events/%5Bid%5D/bracket/_components/setup-view.tsx)
— dropped the inline `AddAdHocTeamForm` (name-only) function and
its `addAdHocTeamFromForm` import; the setup view now renders
`<WalkInTeamForm eventId={...} divisionId={...} />`. The action
import moves into the client component along with the form.

## Patterns observed

- **Regex sweep of FormData beats a hidden count field.** For
  variable-length forms (Add/Remove rows on the client), the
  cleanest server adapter is `for (const [k, v] of formData.entries())`
  with a `^name_(\d+)$` regex — no client/server contract for
  "how many rows did you submit", no off-by-one bugs when a
  middle row is removed. The action stays robust to whatever
  the form layer chose to render.
- **React Compiler reminder: no captured mutables.** The
  `let nextRowId = ...` + `nextRowId += 1` pattern is a textbook
  React-Compiler violation. Anything that looks like "I want a
  stable counter inside a handler" should be derived from state
  via the functional updater (`setX((prev) => ...)`), not from a
  captured local. This is the second time this rule has bitten
  in the bracket area — worth keeping at the front of the mind
  when writing new client components.
- **Spread-vs-undefined for optional fields.** Building DTOs to
  hand to a domain command is the place where
  `exactOptionalPropertyTypes` is loudest. The pattern
  `email ? { displayName, email } : { displayName }` is the
  idiomatic shape; never assign `email: undefined`.

## Follow-ups deferred

- **Enter-to-add.** Pressing Enter inside the last row's name /
  email field could auto-append a new row, so a host can type a
  whole roster keyboard-only without reaching for "+ Add player".
- **Duplicate detection across rows.** Today nothing stops the
  host from typing the same name (or email) into two rows; the
  action will happily pass both to the domain. A pre-submit
  client check + a server-side de-dupe inside the handler would
  catch typos.
- **Account autocomplete by email.** If the typed email matches
  an existing profile, we should offer to link it (so the player
  shows up in their own "my events" list) rather than always
  creating a string-only roster entry.
- **Paste-multiple bulk add.** Pasting a newline-separated list
  into the first name field could split it into rows. Common
  ask once a host has a roster sitting in Notes / Sheets.
- **Mobile layout.** Per-row name + email + ✕ is fine on
  desktop; on a phone the row probably wants to stack name/email
  and keep ✕ inline with the name.
