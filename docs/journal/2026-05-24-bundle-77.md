# 2026-05-24 — Bundle 77: First-touch UTM attribution

## Context

Bundle 76 closed every other P1 on the analytics audit. P1 #3 — UTM /
attribution capture — was the last one blocking "spend a dollar on
acquisition and know if it worked." Without it we can't answer "did the
$500 Instagram test bring any signups?" with anything but a guess from
Vercel Analytics referrer rollups (which break the moment the visitor
takes a second click before signing up).

The user asked to "implement the UTM attribution."

## Decisions

- **First-touch only.** The audit recommended first-touch as the
  starting point. Multi-touch needs either a per-touch log table or
  last-write-wins, both of which open up "did the second touch
  actually convert?" questions that need a real attribution model to
  answer well. Better to ship first-touch now and learn whether we
  actually need more.
- **Capture at the edge, persist at signup.** Stamping the cookie in
  the proxy (Next 16's `apps/web/src/proxy.ts`, the renamed
  `middleware.ts`) catches every entry point — landing pages, deep
  links to events, the short-code redirect — with one piece of code.
  Writing to `marketing_attribution` only at signup avoids cluttering
  the table with anonymous browsers who never convert.
- **HttpOnly cookie, JSON payload.** No client-side JS needs to read
  attribution. HttpOnly closes off the XSS exfil path and the JSON
  blob keeps the cookie self-describing for the auth-callback
  consumer. Fields are truncated to 256 chars defensively against
  crafted long-form UTMs.
- **`ON CONFLICT (user_id) DO NOTHING`.** Enforces first-touch at the
  database. If the auth callback ever re-runs (it can, on retried
  OAuth code exchanges) it won't clobber the original row. The cookie
  is also cleared on successful capture so a returning user with a
  new UTM doesn't reset attribution.
- **Three UTM traits on PostHog identify, not all seven fields.**
  PostHog has first-class chart-grouping for `utmSource` / `utmMedium`
  / `utmCampaign` and that's what dashboards will pivot on. `content`
  / `term` / `referrer` / `landingPath` live in the DB for
  spot-checks; they don't need to be person properties.
- **Off-domain referrer counts as a "touch."** Otherwise a paste of
  our URL into Twitter (which strips UTMs) shows up as "direct" and
  we lose the signal. The proxy stamps the referrer host into the
  same cookie even when no UTM is present.

## Patterns surfaced

- **Edge runtime + JSON cookies is fine if you bound the payload.**
  Next 16's `proxy.ts` runs on the edge runtime; `request.cookies` /
  `response.cookies.set` work directly. Truncate inputs at the
  boundary rather than trusting the URL, otherwise a 4KB cookie limit
  is one crafted link away from breaking navigation.
- **`HttpOnly` + parser at the consumer.** Even with a first-party
  HttpOnly cookie, the consumer (`auth/callback/route.ts`) should
  defensively re-validate types before forwarding into a third-party
  SDK like PostHog. Cheap insurance against a future cookie format
  change.
- **`ON CONFLICT DO NOTHING` is the right idiom for first-touch.**
  More honest than putting the guard in app code; the DB is the
  source of truth for "we already attributed this user."

## Follow-ups deferred

- **Multi-touch / last-touch attribution.** Needs per-touch log table
  and an attribution model (linear? time-decay?). Revisit after we
  have enough signups for a single source to dominate noise.
- **`signup_completed` with `method: 'anon_claim'`.** Requires
  prior-state tracking through the anon → email upgrade flow; deferred
  from Bundle 76, still open.
- **Consent banner integration (audit P2 #5).** Once we ship a banner,
  the attribution cookie + PostHog identify should be gated on
  consent.
- **Surfacing attribution in admin dashboards.** Table now exists but
  no UI consumes it; PostHog covers the dashboard need so app-side UI
  is low priority.
