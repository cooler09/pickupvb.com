# Bundle 69 — 2026-05-24 — ADR 0012: registration paradigm invariants (price unit × team mode × composition)

## Context

Host feedback during a manual pass over the event-create flow surfaced
that three knobs that read as independent in the form were actually
entangled at the product level:

- `team_registration_mode` (`null` / `ad_hoc` / `roster`)
- `team_composition` per division (`solo` / `team` / `pair_draw` / `partner_required`)
- `price_unit` per division (`per_player` / `per_team`)

Concretely:

- `per_player` pricing on an `ad_hoc` or `roster` event undermines the
  captain-pays model — the captain registers the team, but Stripe is
  then asked to bill each roster slot individually.
- `team_composition` was dead metadata on most paths. A `team` /
  `pair_draw` / `partner_required` composition only makes sense when
  the event is team-led; a `solo` composition only makes sense when
  the event is individual-signup.
- The off-platform escape hatch (`paymentsOffPlatform = true`) was
  treated by the previous `assertPaymentConfigValid` invariant as a
  blanket bypass — "no Stripe, no rules". That let hosts publish
  configurations the product can't actually run (e.g. an ad-hoc
  tournament charging per player, settled off-platform).

Pre-launch, so this is a clean policy reset rather than a backfill
problem.

## Decision

Codify the canonical matrix in [ADR 0012](../adr/0012-registration-paradigm-invariants.md):

| Event type   | Team mode           | Allowed composition                       | Allowed price unit |
| ------------ | ------------------- | ----------------------------------------- | ------------------ |
| `open_play`  | must be `null`      | `solo`                                    | `per_player`       |
| `tournament` | `null` (individual) | `solo`                                    | `per_player`       |
| `tournament` | `ad_hoc` / `roster` | `team` / `pair_draw` / `partner_required` | `per_team`         |

Four rules drop out:

1. Open-play is always individual signup (`team_registration_mode === null`).
2. Team-led events (ad_hoc / roster) cannot have a solo-composition
   division and cannot charge `per_player`.
3. Individual-signup events cannot have a non-solo composition and
   cannot charge `per_team`.
4. Off-platform payments do **not** relax any of the above. The
   off-platform flag controls _settlement_, not _registration shape_.

## The factory null-coercion fix

The new "individual-signup tournament" case (Rule 3, valid path)
exposed a latent bug. The factory previously contained:

```ts
if (props.type === EventType.Tournament && extensions.teamRegistrationMode === null) {
  extensions.teamRegistrationMode = TeamRegistrationMode.AdHoc;
}
```

Because `resolveExtensions` always materializes `teamRegistrationMode`
as `null` when omitted, this branch swallowed both "host didn't
specify" and "host explicitly chose individual signup" — silently
upgrading every individual tournament into ad_hoc. The form
([apps/web/src/app/events/new/actions.ts:152](../../apps/web/src/app/events/new/actions.ts#L152))
already translates the host's `'none'` choice to an explicit `null`,
so this was wrong end-to-end.

Fix: gate the auto-default on `props.extensions?.teamRegistrationMode === undefined`
so an explicit `null` survives. The form's `'none'` choice now
produces a real individual-signup tournament instead of being
quietly coerced.

## Follow-ups deferred

Documented as open items in ADR 0012; tracked here so the next
agent can pick them up:

1. **UI gating** in
   [apps/web/src/app/events/new/\_components/divisions-repeater.tsx](../../apps/web/src/app/events/new/_components/divisions-repeater.tsx) and
   [apps/web/src/app/events/[id]/\_components/host-divisions-manager.tsx](../../apps/web/src/app/events/[id]/_components/host-divisions-manager.tsx).
   The user's stated preference is "hide invalid options entirely
   based on selected mode": when `team_registration_mode === null`
   force/lock `composition=solo` + `price_unit=per_player`; when
   `ad_hoc` / `roster` hide the `solo` and `per_player` options.
   Also coerce divisions when the mode toggles in the parent form so
   the boundary validator never has to reject what the UI showed as
   valid.
2. Pair-draw / partner-required signup flows are unimplemented today
   — the divisions can be created but no team-formation UI exists.
3. Multi-division events that mix individual + team-led divisions
   are not addressed by these rules (current invariant runs per
   division; the cross-division constraint, if any, is open).

## Patterns to remember

- **Auto-defaults that read `null`/`undefined` identically are
  hazardous.** Whenever the form has an explicit "none" choice, the
  domain factory must distinguish "host didn't specify" (default it)
  from "host chose none" (respect it). Use
  `props.extensions?.field === undefined` for the former.
- **Off-platform is a settlement decision, not a registration
  decision.** Any invariant that early-exits on `paymentsOffPlatform`
  is suspect — re-read it with that lens.
- **Stale enum references resolve to `undefined` and fall through
  defaults silently.** `TeamComposition.Roster` typechecks as
  `undefined` (no such key), and Division.create's `??` default
  hides the bug. New invariants that exercise previously-defaulted
  fields will surface these — fix at source rather than relaxing
  the invariant.
