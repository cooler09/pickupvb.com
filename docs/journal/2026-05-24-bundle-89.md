# 2026-05-24 — Bundle 89: PII audit P1 remediation — soft-delete and FK nullability

## Context

Three migrations implementing the P1 findings from
[docs/audits/privacy.md](../audits/privacy.md). These are the
structural prerequisites for a future "Delete my account" feature —
without them, deleting a user's `auth.users` row either (a) fails due to
`ON DELETE RESTRICT` on `events.host_id` / `groups.created_by` /
`broadcasts.sender_id`, or (b) cascades and destroys tax-relevant
financial records.

## Decisions

- **Chose surrogate UUID PKs for `host_stripe_accounts` and
  `host_subscriptions`** rather than a soft-delete marker or a separate
  archive table. The `stripe_account_id` / `stripe_customer_id` values
  on those rows are the Stripe-side reconciliation keys for 1099-K
  issuance; the row must survive user deletion. Making `user_id`
  nullable is the minimal structural change. The new surrogate PK does
  not break any existing lookup because queries use `.eq('user_id', …)`
  or the existing unique indexes on `stripe_account_id` /
  `stripe_customer_id`.
- **Chose surrogate UUID PK for `event_attendees`** for the same
  reason. The composite PK `(event_id, user_id)` enforced NOT NULL on
  `user_id`; a surrogate id removes that dependency. The partial unique
  index `(event_id, user_id) WHERE user_id IS NOT NULL` preserves the
  one-RSVP-per-live-user invariant, and the capacity-enforcement
  trigger is unaffected.
- **Left `profiles_select using (true)` policy in place** in Migration 2. Steps 2 + 3 of P1 #4 (switch app queries to `profiles_public`,
  then tighten base-table policy to owner-only) require an app-wide
  query refactor that belongs in a separate bundle. The view ships
  now so future bundles have a stable target to migrate reads to.
- **Used a security-definer-equivalent view** (no `security_invoker = on`)
  for both `profiles_public` and `event_team_registration_members_public`.
  This lets anon/authenticated clients query the narrow views even after
  the base-table policies are tightened in future bundles.
- **Mirrors the existing UPDATE/DELETE policy shape** for the new
  `event_team_registration_members_select` policy (captain-or-host-or-self).
  The `loadAdHocRowsCached` loader uses the admin client and is
  unaffected; the policy change only blocks direct Supabase REST API
  queries from non-authorized callers.

## Patterns observed

- **`user_id primary key` tables require a surrogate PK before `user_id`
  can become nullable.** The PK constraint enforces NOT NULL; you must
  drop the PK constraint, then `alter column … drop not null`, then add
  a new PK on the surrogate column. The FK constraint is a separate
  drop-and-readd step.
- **Composite PKs with a FK column have the same problem.** `(event_id,
user_id)` as PK means user_id cannot be nullable without adding a
  surrogate id first.
- **Partial unique indexes replace the uniqueness guarantee of a
  nullable PK column.** `CREATE UNIQUE INDEX … WHERE user_id IS NOT
NULL` enforces uniqueness for live users while allowing multiple
  SET-NULL rows from deleted users to coexist.
- **Security-definer-equivalent views let narrow projections bypass
  base-table RLS.** Once the `profiles` base-table policy is tightened
  to owner-only (future step), anon clients can still query
  `profiles_public` because the view runs as the postgres user
  (bypasses RLS). Grant on the view is the access-control point.

## Follow-ups

- **P1 #4 step 2:** switch all public-facing query sites (player pages,
  attendee chips, host chips, search) to read from `profiles_public`
  instead of the base `profiles` table.
- **P1 #4 step 3:** tighten `profiles` SELECT policy to owner-only +
  platform-admin (after step 2 ships).
- **P1 #5 step 3 (app-layer):** update `loadAdHocRowsCached` to select
  from `event_team_registration_members_public` for the `allRegistrations`
  public projection and from the base table (admin client) for captain /
  host projections — the admin-client join fetch currently also loads
  `email` and `user_id` into the in-memory result, even though the app
  projection doesn't expose them.
- **Soft-delete application path:** the `deleted_at` / `deletion_reason`
  columns are in place; the application-layer deletion flow
  (`DeletionRequestAggregate`, cron handler, profile scrub) remains open.
- **`deleted_at is null` query filters:** public-reading queries
  (player page, profiles in joins) should filter soft-deleted rows.
  Not enforced at RLS level yet; part of the step-2 bundle.
