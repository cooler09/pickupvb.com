# 2026-05-23 — Bundle 52: Team format mismatch reclassified as `ValidationError`

Closes the last open **Model P3** on the
[registration workflow audit](../audits/registration-workflow.md) — and
fixes a misleading user-facing flash message as a free side-effect.

## Context

The 2026-05-22 remediation log row in `registration-workflow.md` claimed
that `RegisterTeamHandler` "now throws `ValidationError` when
`division.format !== team.format`." The code that actually shipped
threw `UnauthorizedError` for both the cross-event format check and the
new cross-division check. Two consequences:

1. **Wrong error classification.** Per
   [AGENTS.md](../../AGENTS.md#domain-errors), `UnauthorizedError` is
   for permission failures ("caller lacks permission"). A team format
   mismatch is a validation failure — the request is well-formed but
   violates an invariant of the chosen division. `ValidationError` is
   the correct subclass.
2. **Wrong UX flash.**
   [team-signup-actions.ts](../../apps/web/src/app/events/%5Bid%5D/team-signup-actions.ts)
   routes `UnauthorizedError` to `?team=forbidden` → "Only the team
   captain can do that." and `ValidationError` to `?team=invalid` →
   "Team format doesn't match the event." (the latter wired in
   `tournament-signup-panel.tsx`). A captain trying to register a 6s
   team in a 4s division was being told they weren't the captain.

The P3 finding header was also still untagged in the audit, even though
the underlying division-format check has been in the codebase since the
divisions wiring landed (Bundle 1).

## Pattern notes

- **Audit remediation rows can drift from code.** The 2026-05-22 row
  was a forward-looking promise that the implementer didn't match. When
  re-touching an audit-noted area, spot-check that the code matches the
  log — if it doesn't, ship the correction in the same bundle and call
  it out in the new log row (as this bundle does). Don't silently
  edit the old row to match reality.
- **Picking the right `DomainError` subclass changes user-visible
  behaviour, not just type narrowing.** Server actions branch on
  `instanceof` to pick flash codes; misclassifying an error sends the
  user to the wrong message even when the throw site "works." When
  adding a new throw, trace it to the nearest action's `catch` chain
  to confirm the surfaced message is the one you want.
- **A documented invariant + a wired-up flash code is a strong signal
  the original intent was `ValidationError`.** The `?team=invalid` →
  "Team format doesn't match the event." pair was already in
  [tournament-signup-panel.tsx](../../apps/web/src/app/events/%5Bid%5D/_components/tournament-signup-panel.tsx#L66);
  nothing else in the action could trigger it. That's the kind of
  dangling wiring that pinpoints a misclassified throw.
