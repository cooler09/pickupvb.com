# 2026-05-28 — Bundle 133 (BottomNav + FAB primitive)

Fifth installment of the M3 adoption plan from
[docs/audits/m3-alignment.md](../audits/m3-alignment.md). Bundle 129
shipped tokens, Bundle 130 swept touch targets, Bundle 131 introduced
the state-layer utility + button vocabulary, Bundle 132 migrated the
toast system to Radix; this bundle ships the mobile **bottom
navigation** primitive and the M3 **FAB** primitive with a single
reference call site.

## Context

Audit P2 #11 called this out as "the single biggest mobile UX win on
the table." The site shipped a desktop top nav that collapses on
mobile to a hamburger which hides every primary destination (Events /
Groups / Teams / Profile). M3 explicitly reserves the hamburger for
**secondary** destinations once a compact-screen viewport is in play —
the primary 3–5 destinations belong in a bottom navigation bar.

Audit P2 #10 is the FAB story: host-heavy pages bury their single
most-likely host action ("Add walk-in team", "Add division",
"Invite captain") below the fold. M3 prescribes one FAB per page,
56 dp, primary-container surface, anchored bottom-right with the
safe-area inset, surfacing that single action.

The two findings are bundled together because they share visual
geography (both fixed to the bottom of the mobile viewport) and
share the stacking story (FAB has to sit clear of the BottomNav,
both have to sit clear of the Toast viewport).

## Decisions

### 1. Server wrapper + client UI split for BottomNav

Mirrors the established pattern across the app: the visible widget is
`'use client'` (needs `usePathname()`, scroll listeners, `useState`),
but the auth gate that decides whether the 4th item is **Profile** or
**Sign in** needs `cookies()`. Solution is a tiny server component
([bottom-nav.tsx](../../apps/web/src/components/bottom-nav.tsx))
that calls `getCurrentUser()`, derives a single
`isAuthenticated` boolean (treating anon JWTs as signed-out per
AGENTS.md Supabase guidance), and forwards to the client
[bottom-nav-bar.tsx](../../apps/web/src/components/bottom-nav-bar.tsx).
Keeps the client surface free of any cookie reads and makes the
viewer-state contract explicit at the boundary.

### 2. 4 destinations, not 5

Audit prescribes 3–5. Picked 4 to keep the per-tab tap width comfortable
on a 390 px viewport (97 px per tab in a 4-col grid) and to leave one
slot of headroom for a future Notifications tab without retro-fitting
the layout. Order matches the existing site-header order (Events /
Groups / Teams) with the 4th slot adapting to viewer state.

### 3. Hide-on-scroll via rAF + jitter threshold (not always-visible)

M3 standard pattern, and reclaims 64 px of mobile viewport when the
user is actively scrolling a long feed. Two engineering nits worth
recording:

- **setState lives inside the `requestAnimationFrame` callback, not
  the effect body.** This dodges the `react-hooks/set-state-in-effect`
  lint rule (AGENTS.md Pattern 5) without resorting to
  `useSyncExternalStore`. The rule fires when setState is a direct
  child of the effect; pushing it through rAF satisfies both the
  linter and the perf goal (one render per frame, not per scroll
  event).
- **8 px jitter threshold + 80 px minimum scroll depth.** Without
  either, the bar twitches on momentum scroll micro-direction-changes
  and hides immediately on a 1 px finger movement at the top of the
  page. Both numbers are taste-tuned but mechanical to revisit.

The visible state is driven by a `data-hidden` attribute that a
Tailwind sibling variant animates with `transition-transform
duration-200 ease-out` — no JS animation framework, no extra render
on intermediate states.

### 4. FAB primitive is dumb; caller owns viewer-state gating

[fab.tsx](../../apps/web/src/components/fab.tsx) is a pure visual
primitive — a `Link` with M3 surface tokens. It does **not** check
auth, does **not** know about route context. Pages that need a FAB
gate it themselves (`{user && <Fab .../>}`). Reasoning:

- Different pages will need different gates (signed-in for
  `/events/new`, host of this group for `/groups/[id]`, captain of
  this team for `/teams/[slug]`).
- Keeps the primitive testable as a render-only component.
- Mirrors the contract `<PrimaryButton>` already has — visual
  primitive, caller owns semantics.

### 5. `/events` is the only call site this bundle

The audit lists `/events/[id]` host view, `/groups/[id]` admin view,
and `/teams/[slug]` captain view as the FAB target pages, with the
list pages (`/events`, `/groups`, `/teams`) as secondary candidates
("New event", "New group", "New team"). Shipped `/events` only because:

- `/groups` reads via `createSupabaseAnonClient()` inside ISR (no
  `cookies()`), so a viewer-gated FAB needs a client wrapper —
  rolling that out across multiple pages is its own bundle.
- `/teams` already has a prominent `+ New team` CTA in its header
  card and a redundant FAB would be noise without first deciding
  whether to remove the header CTA.
- One reference call site is enough to lock in the visual + the
  z-index story; the rollout can copy the shape.

### 6. MobileMenu trimmed to secondary destinations

Removed **Find events** / **Groups** / **Teams (top-line)** /
**Profile** rows from [mobile-menu.tsx](../../apps/web/src/components/mobile-menu.tsx).
Drawer now carries Host an event, Community feed, Players, Host tools,
Pricing — plus a single **Team invites** row that surfaces only when
`user && pendingTeamInvites > 0`. The pending-invite badge is the only
thing the BottomNav can't currently express, so it stays in the
hamburger until the badge gets a proper home (see follow-ups).

`pendingTeamInvites` prop signature stayed unchanged. Avoids a cascade
into [site-header.tsx](../../apps/web/src/components/site-header.tsx)
prop forwarding (and into the page that computes the count). When the
badge migrates onto the BottomNav Teams tab, the prop can move with it
in one bundle.

## Patterns observed

- **Server-wrapper + client-UI is the canonical shape** for any
  component that needs cookies-derived state in its visual logic.
  The split keeps `cookies()` out of `'use client'` and the visual
  surface mockable. Worth promoting into the AGENTS.md "Page
  composition conventions" section if a third example shows up.
- **`useHideOnScroll` is the canonical scroll-direction subscription.**
  rAF coalescing + jitter threshold + minimum scroll depth. If a
  second component needs the same behaviour (e.g. a sticky sub-nav),
  extract into `apps/web/src/lib/use-hide-on-scroll.ts` then.
- **`state-layer` + `tap-target` compose naturally** on bottom-nav
  items. The bar items are already `h-full` inside an `h-16 grid`,
  so they meet the 48 dp target without needing the `tap-target`
  utility — the `state-layer` overlay is what makes hover/focus/press
  read correctly.
- **z-index hierarchy is now explicit:** Toast viewport 50 >
  BottomNav 40 > FAB 30. Anything new that wants to sit fixed to
  the viewport needs to slot into this hierarchy.

## Follow-ups deferred

- **Multi-page FAB rollout.** Add `<Fab>` to: `/events/[id]` host
  view (action depends on event state — likely "Manage event" or
  "Start scoreboard"), `/groups` ("New group"), `/groups/[id]`
  admin view ("Invite member" or "Schedule event"), `/teams`
  (already has a header CTA — decide whether to replace),
  `/teams/[slug]` captain view ("Invite player"). `/groups` needs
  a client wrapper for the auth gate.
- **Promote the pending-team-invites badge** from the MobileMenu
  row onto the BottomNav Teams tab as a Material-style numeric
  badge. Needs a small client-state subscription (or a
  server-rendered initial count threaded through `<BottomNav>`)
  so the count stays fresh.
- **Extended FAB auto-collapse on scroll.** The primitive supports
  `extended` today but no call site uses it. Once a real page wants
  the extended variant, add the scroll-collapse behaviour per M3.
- **SiteHeader prop cleanup** once MobileMenu drops the
  `pendingTeamInvites` prop dependency — currently kept stable to
  avoid touching the header.
