## Scope

1. **CI hotfix — guard `withSentryConfig` on env presence** in
   [apps/web/next.config.mjs](../../apps/web/next.config.mjs). Vercel
   builds were failing with:

   ```
   TypeError: The "path" argument must be of type string. Received undefined
       at ignore-listed frames
   { code: 'ERR_INVALID_ARG_TYPE' }
   ```

   The Sentry Next.js plugin wraps the config unconditionally and passes
   `process.env.SENTRY_ORG / SENTRY_PROJECT / SENTRY_AUTH_TOKEN` through.
   When any of those are unset, the source-map upload pipeline calls
   `path.join(undefined, …)` and crashes. The existing comment on the
   wrap already claimed "Only active when SENTRY_AUTH_TOKEN +
   NEXT_PUBLIC_SENTRY_DSN are set" — but the code did not honor that. Now
   it does: all three vars present → wrap; otherwise export the bare
   `nextConfig`. The runtime SDK is already DSN-gated separately
   ([sentry.edge.config.ts](../../apps/web/sentry.edge.config.ts) and the
   server config), so dropping the wrap does not break runtime telemetry.

2. **Performance P2 #7 — push-subscription N+1 in the notification
   worker** in
   [apps/web/src/app/api/notifications/worker/route.ts](../../apps/web/src/app/api/notifications/worker/route.ts).
   Previously `processRow` issued a fresh
   `push_subscriptions … eq('user_id', row.to_address)` query for every
   push outbox row. A batch with 30 rows targeting the same user did 30
   identical lookups. The GET handler now collects the distinct push
   user-id set, fetches all subscriptions in one `.in('user_id', ids)`
   query, and builds a `Map<userId, Sub[]>` that's threaded into
   `processRow`. Per-batch lookups go from `O(rows)` to `O(1)`.

3. **Performance P2 #8 — narrow `event_attendees` select on event
   detail** is retro-logged. The select at
   [events/[id]/page.tsx:340](../../apps/web/src/app/events/%5Bid%5D/page.tsx#L340)
   already pulls only `(user_id, payment_status, payment_intent_id)` and
   the viewer-payment select pulls only `payment_status`. The fix landed
   in an earlier (un-bundled) change; this bundle just marks it resolved
   in the audit so the backlog matches reality.

4. **Performance P3 #12 — memoize `isPro()` and `isPlatformAdmin()`**
   with `React.cache()` in [lib/pro.ts](../../apps/web/src/lib/pro.ts)
   and [lib/admin.ts](../../apps/web/src/lib/admin.ts). The event detail
   page calls `hasProBenefits(user.id)` from a side-load branch, and
   downstream pricing/admin checks also hit `isPro()` — `React.cache`
   collapses the repeated `is_pro_host(uuid)` lookups into one per
   request. No call-site changes needed because `cache(fn)` returns a
   function with the same signature.

5. **Audit doc cleanup.** The 2026-05-22 status block on
   [performance.md](../audits/performance.md) was stale — it claimed P1
   #0 and the public-page `force-dynamic` regression were still open,
   but both shipped (in Bundle 2 and the 2026-05-22 quick-win bundle
   respectively). Added a `> 2026-05-24 follow-up:` blockquote pointing
   to the resolving bundles, plus a new Bundle 11 status block at the
   top. Section headers for P2 #7, #8, and P3 #12 now carry their

## Decisions

- **Pre-fetch shape: `Map<userId, Sub[]>` not `Map<userId, Sub>`.** Users
  can register multiple devices; the worker fans out to all of them. The
  pre-fetch must preserve all rows per user, not the first one. Loop
  builds the map by appending rather than `Map.set` clobbering.
- **Stale-subscription window inside the batch is acceptable.** If
  `processRow` prunes a subscription via the `gone` path partway through
  the batch, the Map still contains the deleted row. The next outbox row
  for the same user would attempt delivery again and re-detect `gone`.
  Acceptable because (a) the gone-list is collected and deleted again
  via `.in('endpoint', gone)` (idempotent), and (b) the next batch
  re-fetches fresh. Not worth complicating the loop for a one-batch
  staleness window.
- **`React.cache` over a module-level `Map` cache.** `React.cache` is
  per-request and is automatically invalidated between requests by React
  — a module-level map would leak across requests in long-lived Node
  workers and serve stale `is_pro` values after a subscription change.
- **Don't move the `withSentryConfig` guard into the plugin itself.**
  The Sentry team owns that surface — patching their plugin is out of
  scope and would break on the next upgrade. Gating at the call site
  is the supported pattern. The wrap comment is updated to match what
  the code now does.
- **`silent: !process.env.CI` stays.** It's the right knob for the
  Sentry plugin's verbosity. The lesson is that "silent in dev / loud in
  CI" creates an asymmetry where errors show up only in the place where
  they're hardest to debug (no local repro). Promoted into the
  "Patterns observed" section below so future work treats CI-only
  symptoms with suspicion.

## Patterns observed

- **`silent: !process.env.CI` is a local-vs-CI trap.** When a build
  fails on Vercel but works locally, check Sentry / source-map / OTel
  plugin configuration before assuming a transient infra issue. Local
  builds may be swallowing the error to keep the dev console quiet. If
  this recurs we should write it up into the AGENTS.md "Patterns
  surfaced by audits" section.
- **`React.cache(fn)` is a free win for any read-only "is X true?"
  helper called from multiple side-load paths in the same render.** No
  call-site changes; just wrap. Worth a quick sweep for other facades
  in `apps/web/src/lib` that fit the same shape.
- **Batch pre-fetch + Map lookup is the right primitive for any
  per-row sidecar fetch in the notification worker.** The push-sub
  case is the obvious one; if we add another channel (Twilio SMS,
  webhook URLs, etc.) the same pattern applies.
