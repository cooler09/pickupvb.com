# Bundle 10 — Infrastructure `getDetail()` JOIN consolidation

_Date: 2026-05-24_

## Context

[Bundle 9](2026-05-24-bundle-9.md) closed the page-level half of
[performance P1 #4](../audits/performance.md): the event detail page
now issues at most two parallel side-load waves on top of
`getEventDetail`. The infrastructure half — the
`SupabaseEventRepository.getDetail()` aggregator itself doing ~17
queries in two parallel rounds — was deferred. That's this bundle.

## Scope

All edits in [supabase-event-repository.ts](../../packages/infrastructure/src/supabase-event-repository.ts)
inside `getDetail`:

1. **JOINed co-host profile + group detail into the wave-1
   `event_co_hosts` select.** Replaced the bare
   `select('host_user_id, host_group_id')` with a nested PostgREST
   relation: `profiles:profiles(...), groups:groups(...)`. Both
   nullable, both single-row (FKs).
2. **JOINed team captain profile into the wave-1 nested `teams!inner`
   select** via `captain:profiles!teams_captain_id_fkey(...)`. The FK
   already existed (`teams.captain_id references public.profiles(id)`,
   migration `20260512000000_init.sql` line 62); just had to use the
   explicit relation name since `profiles` is referenced more than once
   in the surrounding query.
3. **Dropped three batched fetches from wave 2**: `coHostUsersRes`,
   `coHostGroupsRes`, `teamCaptainsRes`. Wave 2 shrinks from 9 → 6
   parallel queries. Removed the now-dead `coUserIds` and
   `registeredCaptainIds` extraction, the `captainProfiles` map, and
   the conditional `.in('profiles')` lookups.
4. **Updated row types** to reflect the nested shape: `CoHostJoinRow`
   carries `profiles` + `groups` directly; `TeamJoinRow.teams` carries
   `captain` directly. Downstream `coHostUsers`, `coHostGroups`, and
   `teams.captain` resolve in-place from the nested data.

## Decisions

- **JOIN at the PostgREST layer, not via a `view` / `rpc`.** The audit's
  original suggestion mentioned "consider a view or RPC for the whole
  detail bundle. Aim for ≤3 queries." The full collapse needs a SQL
  view (or `rpc`) returning a single composite row; that's a bigger
  diff with its own migration and RLS implications. Nested PostgREST
  selects buy 3 queries back today with no schema change. Pursuing the
  view-or-rpc collapse is a possible future Bundle X if the slow-query
  log still flags `getDetail` after these reductions.
- **Kept `team_members` count fetch separate.** PostgREST supports
  `team_members(count)` nested aggregates, but the query reads
  `member_count` per team and the count would need to honor RLS the
  same way the current `select('team_id').in(...)` does. The current
  batched fetch is one round-trip and runs in parallel; replacing it
  is real work for unclear gain. Left as a leaf optimization.
- **Kept `viewerCaptainedTeams → viewerTeamMemberCounts` follow-up
  serial fetch.** Same reasoning — it's a tiny tail-end query on a list
  that's almost always 0–3 ids. Eliminating it via `team_members(count)`
  nested aggregate is the cleanest fix but again unclear measurable
  win.
- **Used the explicit FK hint
  `captain:profiles!teams_captain_id_fkey(...)`** instead of the
  shorter `captain:profiles(...)`. The `teams` row already carries
  `captain_id`, so PostgREST could in principle infer the relation,
  but the `profiles` table is referenced in many other parts of the
  query (attendees, free agents, co-hosts) and explicit FK naming
  prevents ambiguity-resolution surprises across schema evolution.
  Same pattern Bundle 9 used for the ad-hoc captain JOIN.

## Patterns observed

- **"JOIN-at-the-edge" wins are usually one-line changes to a select
  string plus a row-type tweak.** The infrastructure code's shape didn't
  change — it's still "wave 1 fetches, wave 2 batches the ids, then
  build read model." The wins came from collapsing the wave-1 → wave-2
  data dependency, not from restructuring control flow.
- **PostgREST nested relations have a discoverability tax.** Each new
  JOIN needs to confirm: (a) the FK exists, (b) it's the only FK
  between the two tables, and (c) the chosen relation alias is
  unambiguous. Once confirmed, the change itself is small.
- **The audit's `≤3 queries` target wasn't reached** — we went 17 → 14.
  Going to 3 needs a database view or RPC. The audit framing ("collapse
  co-host + profile fetch into one query with `JOIN profiles`, batch
  captain fetches by team id list, consider a view or RPC for the whole
  detail bundle") let us do the cheap reads-first version without
  blocking on the view design.

## Follow-ups deferred

- **View / RPC collapse of `getDetail()` to ≤3 queries.** The remaining
  ~14 queries are: 7 in wave 1 (event row, attendees, co-hosts joined,
  primary host user, primary host group, teams joined, free agents,
  divisions — 8 actually) and 6 in wave 2 (friendships, viewer role,
  hostable groups, team-member rows, payments, viewer captained teams).
  A `event_detail_view` SQL view (or `event_detail(viewer_id)` RPC)
  could return everything in 1–2 round trips. Wants its own ADR + RLS
  review.
- **`team_members(count)` PostgREST nested aggregates** for the
  registered-team roster sizes and viewer-captained-team roster sizes.
  Would eliminate 2 more queries; needs verification that RLS shapes
  the count correctly.
- **Audit's instrumentation ask** — capture before/after timings from
  Supabase slow-query log on a real event. Bundles 9 + 10 together
  drop roughly 6–7 round-trips per detail render but we haven't
  measured the wall-clock impact in production.
- **Listings-Suspense refactor (P1 #1 architectural)** for actual CDN
  caching on the public listing pages. Still the highest-leverage open
  perf P1.
- **`force-dynamic` regression on `app/page.tsx`, `pricing/page.tsx`,
  `e/[code]/page.tsx`** — separate from this bundle.
