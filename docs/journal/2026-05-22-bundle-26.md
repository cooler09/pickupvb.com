# 2026-05-22 — Bundle 26: `/events/[id]` viewer-independent cache layer

## Context

Bundle 25 finished the ISR-shell refactor for three of the five P1 #1
detail pages: `/teams/[id]`, `/groups/[id]`, `/players/[id]`. The two
deferred routes were `/events` and `/events/[id]`. Both interleave
viewer-aware chrome (RSVP, waitlist, co-host controls, manage tools,
host-payment side loads, friend badges, tip flash banners) with public
event data in ways that don't fit a "one client island contains all
viewer state" recipe like the sibling detail pages did.

`/events/[id]` is also the heaviest read in the app — the page-level
loader fans out to a 6-way wave 1 and a 3-way wave 2 of Supabase queries
(post-Bundle 9), on top of the read model's own 14-query
`getDetail(id, viewerId)` (post-Bundle 10). Anonymous traffic (SEO
crawlers, link previews, logged-out browsing) pays that full cost on
every request and gets zero benefit from any viewer-specific data.

## Decision

Skip the full structural ISR refactor for this bundle. Instead, ship a
thin caching layer over the viewer-independent side-loads. That gives
anonymous viewers a "warm cache → zero Supabase" path without touching
the 17 viewer-aware subcomponents or the page's `searchParams` flash
banners. The big rewrite stays on the backlog for a future PPR-enabled
pass.

### Why pragmatic, not structural

- The structural rewrite is multi-bundle. The page has 7 `searchParams`
  flash banners (`rsvp`, `rsvp_msg`, `team`, `fa`, `created`, `tip`,
  `tip_msg`) and 17 viewer-aware subcomponents (sticky CTA, signup
  area, host tools, attendee panel, ad-hoc viewer team registrations,
  …). Lifting all of that into client islands is a real refactor, not
  a one-evening job.
- No PPR / `cacheComponents` flag is enabled in
  [apps/web/next.config.mjs](../../apps/web/next.config.mjs), so the
  partial-prerender escape hatch isn't available — we'd be choosing
  between "make the whole page client-rendered" and "keep the whole
  page dynamic". Neither is appealing without a wider plan.
- The repository runs on the admin client
  ([packages/infrastructure/src/supabase-event-repository.ts](../../packages/infrastructure/src/supabase-event-repository.ts)),
  so the public read model — `GetEventDetailQuery(id, null)` — is
  identical for every visitor. That makes it a clean
  `unstable_cache` target with no RLS-leak risk.
- The bulk of anonymous traffic value comes from SEO/preview crawlers
  and click-through-from-share-card visitors. Both are short-tail
  hits on warm cache: `unstable_cache(..., { revalidate: 60 })` is
  effectively free for them.

## What shipped

### 1. Cached side-load helpers in the page loader

Five `unstable_cache`-wrapped helpers added to
[apps/web/src/app/events/%5Bid%5D/\_loaders/load-event-detail.ts](../../apps/web/src/app/events/%5Bid%5D/_loaders/load-event-detail.ts):

- `loadEventReadModelPublic(id)` — exported. Cached
  `GetEventDetailQuery(id, null)` execution. Used both for anonymous
  page renders and for `generateMetadata`.
- `loadEventPricingCached(id)` — wraps the `getEventPricing()` helper
  from [apps/web/src/lib/event-pricing.ts](../../apps/web/src/lib/event-pricing.ts).
  That helper still uses `getServerSupabase()` internally, but the
  query reads public-equivalent rows (`events` + `event_divisions`
  pricing fields) so the cached result is safe to share across
  visitors.
- `loadEventTipTotalCached(id)` — wraps the `event_tip_total_cents`
  RPC.
- `loadPrimaryHostSocialCached(hostUserId)` — wraps the host's
  `profiles` row social-handles fetch. Refactored the existing
  `loadPrimaryHostSocial(event)` helper down to a
  `loadPrimaryHostSocialFresh(hostUserId: string)` so the cache key
  stays on the user id (5-minute revalidate, tagged
  `profile:{userId}`).
- `loadAdHocRowsCached(eventId)` — wraps the raw
  `event_team_registrations` + members fetch. Viewer-specific
  projections (`viewerRegistrations`, `hostRows`, the
  `isViewerCaptain` flag on `allRegistrations`) are derived against
  the cached snapshot in the uncached `loadAdHocBundle(event, user)`
  caller.

All event-scoped helpers use `revalidate: 60` and `tags: ['event:{id}']`.
The profile helper uses `revalidate: 300` and `tags: ['profile:{id}']`.

The Wave 1 `Promise.all` in `loadEventDetail()` now reads cached values
for pricing / tip / host social / ad-hoc rows. The two viewer-aware
entries (`viewerIsPro`, `loadEligibleTeamsByDivision`) stay uncached.

### 2. Read-model fetch fork (anonymous vs signed-in)

`loadEventDetail()`'s read-model fetch is now conditional:

```ts
event = user
  ? await handlers.getEventDetail.execute(new GetEventDetailQuery(id, user.id))
  : await loadEventReadModelPublic(id);
```

Anonymous viewers serve the read model out of `unstable_cache` (zero
Supabase RTT on warm cache). Signed-in viewers still pay the full
viewer-aware 14-query `getDetail()` cost — that path carries
`canManage`, `isAttending`, `viewerFriendIds`, `viewerHostableGroups`,
and `viewerCaptainedTeams`, which all depend on the viewer.

### 3. `generateMetadata` shares the cached helper

[apps/web/src/app/events/%5Bid%5D/page.tsx](../../apps/web/src/app/events/%5Bid%5D/page.tsx)'s
`generateMetadata` previously fired its own
`handlers.getEventDetail.execute(new GetEventDetailQuery(id, null))`.
It now calls `loadEventReadModelPublic(id)` so the metadata and page
renders dedupe through the same cache entry. Same-request dedupe is
already free via Next's per-request cache; the win is across requests.

## Tradeoffs accepted

- **60 s staleness for non-host viewers on `event:{id}`-scoped data.**
  Hosts use the uncached signed-in read-model path, so they see their
  own edits immediately. Other signed-in viewers and anonymous
  viewers see up to 60 s lag on pricing / tip total / host social /
  ad-hoc team rows / the read model itself. That matches the ISR
  cadence of `/teams/[id]`, `/groups/[id]`, `/players/[id]` (Bundle 25) and `/players`, `/groups`, `/teams` (Bundle 13a).
- **No `revalidateTag('event:{id}')` in the 16 mutating action files**
  under [apps/web/src/app/events/%5Bid%5D/](../../apps/web/src/app/events/%5Bid%5D/).
  If the 60 s budget starts producing user-visible bugs (e.g. a host
  edits the price and a non-host RSVP'er sees the old amount for up
  to a minute), the fix is mechanical: drop a `revalidateTag` call
  next to the existing `revalidatePath` in each action. Deferring
  that until we have evidence of a real complaint.
- **Page is still dynamically rendered.** `searchParams` flash banner
  reads + viewer cookie still force `cookies()` / `headers()` use, so
  the page remains dynamic. The win is on the side-loads, not the
  shell.

## Alternatives rejected

- **Full ISR shell refactor (drop `cookies()` from the page, anon
  client, lift all viewer chrome into a single client island).** Same
  recipe as Bundle 25 for the sibling detail pages, but the surface
  area is roughly 5× larger here. Multi-bundle change with an
  intermediate broken state.
- **Enable PPR / `cacheComponents` and use `'use cache'`.**
  Experimental flag, no other route in the app uses it, requires
  buy-in on a wider Next 16 strategy. Not the right place to land
  that decision.
- **Cache only `loadEventReadModelPublic` and leave the side-loads
  uncached.** Half the latency win lives in the side-loads — primary
  host social fetch alone is a 1-RTT read on every page load.

## Patterns surfaced

- **`unstable_cache` per-id wrapper factories.** When the cache key
  needs to vary by id but the tag also needs to vary by id, the
  pattern is to create the wrapper at call time:

  ```ts
  function loadEventPricingCached(id: string) {
    return unstable_cache(async () => getEventPricing(id), ['event-pricing', id], {
      revalidate: 60,
      tags: [`event:${id}`],
    })();
  }
  ```

  Next dedupes by `keyParts`, so re-creating the wrapper per call is
  free. The alternative — wrap once and accept `id` as an argument —
  forces tags to be static, which kills `revalidateTag` granularity.

- **Cache-safe boundary check.** An "is this safe to cache across
  visitors?" audit step: trace the underlying client. The
  infrastructure repo uses the admin client (RLS bypass) so the
  answer is "always". A helper using `getServerSupabase()` (cookie-
  bound) is only safe if the queried rows are public-equivalent
  regardless of caller — `getEventPricing` qualifies; a helper that
  reads `event_attendees` to compute viewer state does not.

## Follow-ups deferred

  / manage / waitlist / flash-banner chrome into client islands, drop
  the page's `cookies()`/`searchParams` dependency).
- `/events` listing ISR shell (needs friends/following per-card
  badge strategy).
- Per-action `revalidateTag('event:{id}')` evictions in the 16
  mutating action files, if/when the 60 s budget becomes a UX issue.
- Aggregating remaining repo sub-wave (viewer captained-team member
  counts) via a PostgREST `count` projection — leftover micro-
  optimization from Bundle 10.
