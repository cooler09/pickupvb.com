# 2026-05-22 — Bundle 25: ISR detail-page Suspense (teams / groups / players)

## Context

Bundle 13a (2026-05-24) made three of the four listing pages
ISR-cacheable for anonymous traffic by introducing
`createSupabaseAnonClient()` and moving viewer chrome into `'use client'`
islands. The matching detail pages — `/teams/[id]`, `/groups/[id]`,
`/players/[id]` — were explicitly deferred from that bundle. Bundle 25
finishes them.

`/events` and `/events/[id]` are still deferred. Both interleave
viewer-specific state (friends list, following feed, RSVP / waitlist /
co-host chrome, host-payment side loads) with the public data in ways
that need a wider redesign — the per-card friend badge on `/events`
alone would force a Suspense boundary per card today.

## Scope

Three detail pages plus the shared loaders they depend on. No
infrastructure changes, no schema changes.

## What shipped

### 1. Loader signature refactor

`loadVisibleHostedEvents()` and `loadVisibleGroupHostedEvents()` (in
[apps/web/src/components/hosted-events-list.tsx](../../apps/web/src/components/hosted-events-list.tsx)
and
[apps/web/src/components/group-hosted-events.tsx](../../apps/web/src/components/group-hosted-events.tsx))
now take the supabase client as their first argument, typed
`HostedEventsLoaderClient = SupabaseClient<Database>`. Callers can pass
either the cookie-bound server client (per-viewer visibility) or the
anon client (public events only). Both internal `await
getServerSupabase()` calls were removed. The only existing caller
outside the three detail pages —
[apps/web/src/app/profile/page.tsx](../../apps/web/src/app/profile/page.tsx) —
was updated to pass its already-resolved `supabase` instance through.

### 2. `/teams/[id]` shell + `<TeamViewerChrome />`

Page: dropped `export const dynamic = 'force-dynamic'`; added `export
const revalidate = 60`; swapped `getServerSupabase()` for
`createSupabaseAnonClient()`; removed all viewer-conditional logic
(`isCaptain`, `viewerMember`, `viewerHasPendingInvite`). Roster rows now
render with `viewerIsCaptain={false}` server-side.

New client island:
[apps/web/src/app/teams/[id]/\_components/team-viewer-chrome.tsx](../../apps/web/src/app/teams/%5Bid%5D/_components/team-viewer-chrome.tsx).
Single `useEffect` runs `supabase.auth.getUser()`, then branches on
`user.is_anonymous`, captain id, and pending-member status. Renders:

- nothing for anon / active-member viewers,
- `<InviteResponse />` for pending members,
- `<AddTeamMemberForm />` + `<ExtraMembersForm />` +
  `<CaptainBroadcastPanel />` + a new "Roster controls" subsection with
  per-member remove forms for the captain.

The "Roster controls" subsection is a slight UX shift — captain remove
buttons used to live inline on each `<TeamMemberRow />`; now they're a
separate list below the roster. Tradeoff accepted because it keeps the
public roster fully cacheable.

### 3. `/groups/[id]` shell + slot-pattern header + two client islands

Page: same ISR conversion. `loadVisibleGroupHostedEvents()` calls
updated to pass `supabase` first. Removed `getCurrentUser()`,
`group_followers` fetch, and `canManage` / `isFollowing` derivation.

`<GroupHeader />` was simplified: removed `canManage`, `isSignedIn`,
`isFollowing`, and `returnPath` props plus the inline action row;
replaced them with a single `actions: ReactNode` slot. Public header
stays server-rendered; the page passes a `<GroupViewerActions />` client
island as the slot.

`<MembersSection />`'s `canManage: boolean` prop became
`manageSlot?: ReactNode`; the page passes a `<GroupManageMembersLink />`
client island.

New client island file:
[apps/web/src/app/groups/[id]/\_components/group-viewer-actions.tsx](../../apps/web/src/app/groups/%5Bid%5D/_components/group-viewer-actions.tsx).
Exports two components: `GroupViewerActions` (resolves session, fetches
the follow edge, renders follow / unfollow / sign-in / Host event / Edit
buttons) and `GroupManageMembersLink` (resolves session, renders the
"Manage members →" CTA when the viewer is an owner/admin). Both take a
`managerIds` array from the page so the role check doesn't need an
extra round-trip.

### 4. `/players/[id]` shell + `<PlayerViewerActions />`

Page: same ISR conversion. `loadVisibleHostedEvents()` updated.
`isPro()` / `isPlatformAdmin()` calls left server-side — both are
backed by the admin client (not cookie-bound) and already memoized with
`React.cache()` per Bundle 11.

New client island:
[apps/web/src/app/players/[id]/\_components/player-viewer-actions.tsx](../../apps/web/src/app/players/%5Bid%5D/_components/player-viewer-actions.tsx).
Resolves session and, for non-self viewers, the `friendships` edge.
Branches on `loading | self | anon | other` and renders the appropriate
CTA + `<ShareLink />`.

## Decisions

- **Slot pattern for `GroupHeader`.** The header had four
  viewer-dependent props; replacing them with a single `actions` slot
  let the server-rendered header stay completely viewer-agnostic without
  forking the file. Same pattern for `MembersSection` (`manageSlot`).
  Considered an alternative where the header itself becomes a client
  component — rejected because the avatar + identity card is the heavy
  part of the render and should stay server.
- **Single client island per page.** For `/teams/[id]` I considered
  multiple islands (one for invite-response, one for captain forms);
  rolled them into one to share the single `getUser()` hydration RTT.
  `/groups/[id]` ended up with two because the manage-members CTA lives
  in a different section of the page and rendering it as a sibling of
  the header actions would have required prop-drilling the section's
  layout.
- **Anon-only public events tradeoff.** `loadVisibleHostedEvents()` /
  `loadVisibleGroupHostedEvents()` with the anon client see only public
  events. A signed-in viewer browsing someone else's profile or a group
  page won't see private events they'd otherwise be invited to. Matches
  the Bundle 13a listing-page tradeoff and was judged acceptable for the
  SEO / share-link cache win. If we want viewer-aware event lists back,
  the path forward is a Suspense boundary around the event lists with a
  client component that re-fetches with the browser client.
- **Captain "Roster controls" subsection.** Moving the inline per-row
  Remove buttons off the public roster preserves the cacheable
  server-rendered roster but slightly changes the captain's mental
  model. Acceptable for now; if it gets noisy we can re-introduce
  client-rendered remove buttons by hoisting `<TeamMemberRow />` into a
  thin client wrapper.

  underneath.
- `/events/[id]` ISR refactor — the largest detail page; RSVP / waitlist
  / co-host / manage chrome and host-payment side loads all sit on top
  of the public event data. Worth its own bundle.
- P3 #13 (notification worker cold-start monitoring) still open.

  `<TeamMemberRow />` (replace `viewerIsCaptain` + `returnPath` with a
  `controls?: ReactNode` slot) if we later want inline per-row Remove
  buttons back without losing cacheability. Not done in this bundle.
