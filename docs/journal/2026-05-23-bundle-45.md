# 2026-05-23 — Bundle 45: Position-fill math into the event detail read model

## Context

The architecture audit's "Still open" list carried a P2 (carried over
from Bundle 23's loader extraction): the event detail page's loader
still recomputed `filledByPosition` from `event.attendees` with a
dedicated `for` loop, even though the infrastructure repository already
walks attendees once to compute waitlist flags and was already
maintaining its own per-position running count internally. Two walks
for the same numbers, with the second one outside the layer that owns
the semantics.

## What shipped

Three files, all narrow:

- [packages/domain/src/events/event-repository.ts](../../packages/domain/src/events/event-repository.ts) —
  added `filledByPosition: Partial<Record<EventPosition, number>>` to
  `EventDetailReadModel`. JSDoc notes that the value mirrors the shape
  of `positionRoster` so the UI can render `filled / target` per slot
  without re-walking attendees.
- [packages/infrastructure/src/supabase-event-repository.ts](../../packages/infrastructure/src/supabase-event-repository.ts) —
  the existing local `filledByPosition` Map is now incremented
  unconditionally whenever an attendee has a position (previously it
  was only incremented when `positionRoster` was also set, because
  it was only needed for the waitlist comparison). Serialised at the
  bottom of `getDetail()` via
  `Object.fromEntries(filledByPosition) as Partial<Record<EventPosition, number>>`.
  Waitlist semantics unchanged — that branch still only runs when
  `positionRoster` exists.
- [apps/web/src/app/events/\[id\]/\_loaders/load-event-detail.ts](../../apps/web/src/app/events/%5Bid%5D/_loaders/load-event-detail.ts) —
  deleted the seven-line counting loop; replaced with
  `const filledByPosition = event.filledByPosition;` plus a comment
  pointing readers at where the counting now lives.

## Verification

`pnpm typecheck && pnpm lint && pnpm test && pnpm build` — all green.
8 tasks, 7 cached, ~31 s. Type compatibility from
`Partial<Record<EventPosition, number>>` →
`Partial<Record<string, number>>` (the loader's exposed field type and
the existing `event-signup-area` / `position-rsvp-panel` props) is
free, since `EventPosition` is a string subtype. No consumer signatures
needed to change.

## Pattern notes

- **"Compute it where the semantics live" beats "compute it where the
  consumer needs it."** The waitlist calculation and the
  filled-per-position projection are the same walk; splitting them
  across the infra repository and the page-side loader meant every
  schema change to attendees had two places to look. Consolidating
  into the layer that already owns the walk is a one-line addition on
  the producer side and a deletion on every consumer side — net
  negative LOC.
- **Surface domain projections on the read model, not on the page
  loader.** This is the same heuristic ADR 0001 sets for view models:
  the read model is the contract the application layer hands to the
  composition root, and any derivation that's pure-from-the-model
  should ride on the model itself. The page loader is for orchestrating
  side-loads (pricing, payments, ad-hoc rows), not for arithmetic over
  the read model.
- **Unconditional vs. conditional counting.** The infra Map was
  previously gated on `positionRoster` because the only consumer was
  the waitlist branch. Removing the gate gives every viewer a useful
  projection — the cost is one `Map.set` per attendee with a position,
  which is dominated by the join cost upstream. The waitlist branch
  still short-circuits as before; only the running count escapes.
- **`Object.fromEntries(map)` as the Map→Record bridge.** The cast
  `as Partial<Record<EventPosition, number>>` is needed because TS
  widens to `{ [k: string]: number }` otherwise; the `Partial<>`
  matches the existing `positionRoster` field shape.
