# 2026-05-28 — Bundle 138: system theme mode (M3 P3 #19, final M3 bundle)

## Context

[m3-alignment.md](../audits/m3-alignment.md) flagged ten bundles
across P1/P2/P3 for M3 adoption. Bundles 129–137 (change-bundle
numbers; audit Bundles 1–9) closed the P1 + P2 work plus the
density scale. This bundle (audit Bundle 10) was the audit's
opportunistic "P3 cleanup" slot. The session decision was to scope
it tightly: ship **P3 #19** (system theme mode) only, and defer
the other P3 items (#17 icons, #18 data-table, #20 tonal palette,
#21 Switch, #22 Chip) since each is either large, research-only,
or waiting on a real call site to standardize against.

## Decisions

- **Cookie-only design — no Supabase migration.** Migration
  `20260513000400_profiles_theme_preference.sql` defines
  `theme_preference text not null default 'dark' check (theme_preference in ('light', 'dark'))`.
  A "follow system" preference is conceptually device-scoped
  (people genuinely do want pinned dark on one device and system
  on another), so the right place to store it is the existing
  `pvb-theme` cookie, not the profile column. This sidesteps a
  production schema change for a P3 nice-to-have entirely.
- **Type split: `Theme` (resolved) vs. `ThemePreference` (chosen).**
  `Theme = 'light' | 'dark'` continues to mean "the value CSS
  reads from `data-theme`"; `ThemePreference = 'light' | 'dark' | 'system'`
  is the new user-facing choice. The split keeps every existing
  CSS rule untouched — the cascade still keys on `[data-theme=dark]` —
  and isolates the new union to the toggle + the cookie I/O.
- **Two attributes on `<html>`: `data-theme` + `data-theme-mode`.**
  The first is what CSS paints (always light/dark). The second is
  what the user picked (light/dark/system). Without the second the
  bootstrap script wouldn't know whether to subscribe to
  `prefers-color-scheme`.
- **Inline pre-paint `<script>` for system-mode resolution.** SSR
  has no access to `prefers-color-scheme`, so a `'system'`
  preference falls back to `DEFAULT_THEME` server-side. A tiny
  inline IIFE as the first child of `<body>` reads
  `matchMedia('(prefers-color-scheme: dark)')` and corrects
  `data-theme` before the first paint, then attaches a `change`
  listener so the page tracks OS dark-mode flips live without a
  reload. Inline (not `<Script>`) because the existing JSON-LD
  block in this layout already uses `dangerouslySetInnerHTML` —
  consistent with the codebase's pattern for very small, no-deps,
  must-run-before-paint scripts.
- **Profile write only for explicit light/dark.** The DB
  check-constraint forbids `'system'`, and we wouldn't want to
  store it there even if we could — see decision #1.

## Rejected alternatives

- **Add a migration to widen the check-constraint to
  `light|dark|system`.** Right answer if `'system'` were
  account-scoped, but it's not. Production deploy + types
  regeneration churn for a P3 fix didn't carry its weight.
- **Use `next-themes`.** Adds a runtime dep + a provider + a hook
  for what is effectively ~40 lines of hand-rolled code that
  already integrates with our server-rendered cookie. Not worth
  the dep.
- **Defer the entire bundle and call the M3 sequence "complete after
  9."** Decided against — #19 is the smallest user-visible P3 and
  closes the most obvious gap in the toggle UI. The other P3 items
  genuinely benefit from being opportunistic (e.g. P3 #22 Chip
  primitive should wait for a real chip call site rather than be
  speculatively designed).

## Patterns observed

- **The `Theme` / `ThemePreference` split is the same shape used by
  most theme libraries** (e.g. `resolvedTheme` vs. `theme` in
  next-themes). Worth remembering if a future bundle adds more
  enum-like preferences: the boundary is "what the engine paints"
  vs. "what the user chose," and they shouldn't be the same type.
- **AGENTS.md Pattern 5** (no sync `setState` in `useEffect` body)
  didn't bite this bundle — the bootstrap script runs once at parse
  time outside React. Worth noting because Bundle 136 hit it on a
  pathname effect.
- **Inline `<script dangerouslySetInnerHTML>` for pre-paint
  bootstrap** is a well-trodden pattern (Tailwind docs, Vercel docs,
  every theme library). It does trip ESLint's `react/no-danger`
  default, but our config already allows it since the JSON-LD block
  uses it.

## Follow-ups deferred

- **P3 #17 — Icon discipline.** Standardize icon weights/sizes;
  touches many files.
- **P3 #18 — Data-table primitive.** Original audit guidance: defer
  "until a third table appears." We have receipts + earnings; still
  two.
- **P3 #20 — Tonal palette exploration.** Research task; what would
  a tertiary-container surface buy us beyond the bracket flash?
- **P3 #21 — Switch primitive.** Radix Switch wrapper styled with
  M3 tokens. Own bundle when a switch call site shows up.
- **P3 #22 — Chip primitive.** Wait for a real chip call site.
- **Server-side profile read for non-cookie sessions.** Today, an
  authenticated user who clears their cookie sees `DEFAULT_PREFERENCE`
  (not their saved profile pref). The layout's `resolveTheme()`
  _does_ fall back to the profile, but only for the cookie-missing
  path; if a user picks `'system'` once and we don't write to the
  profile, signing in on a fresh device shows the default until
  they pick again. Acceptable tradeoff for the cookie-only design;
  flagged here because the next person to look at theme persistence
  will wonder.

## M3 adoption arc — closing note

This is the final bundle (audit Bundle 10) of the 10-bundle
adoption sequence that started with change-bundle 129. The arc
shipped: M3 token vocabulary (129), 48 dp tap targets (130),
state-layer overlay primitive (131), M3 Snackbar/Toast on Radix
(132), bottom-nav primitive (133), Dialog on Radix (134),
TextField primitive (135), DropdownMenu on Radix (136), density
scale (137), and system theme mode (138). All Radix primitives
preserved their pre-existing public APIs so call sites needed
zero edits. Motion is bridged via plain CSS `@keyframes`
consuming `--md-sys-motion-*` tokens — no `tailwindcss-animate`
dep. Per-bundle audit status blocks, remediation log entries, and
journal files are the durable record; the audits README's M3 row
is prefixed in shipped-bundle order so the most recent change is
visible at a glance.

The remaining P3 items live on as opportunistic backlog in
[m3-alignment.md](../audits/m3-alignment.md). No new bundle is
committed for them — they ship when a real call site or research
question forces the issue.
