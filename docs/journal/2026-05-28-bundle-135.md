# Bundle 135 — TextField primitive (2026-05-28)

Seventh M3-adoption bundle. Closes the primitive half of audit
**P2 #13 "Text fields lack M3 structure"** by shipping a single
`<TextField>` component covering the M3 outlined chassis +
supporting-text / leading-icon / trailing-icon / prefix / suffix
slots that the audit called for, plus a multiline variant. Migrates
one reference call site (the "Team name" input in
`new-team-form.tsx`) to prove the integration shape; defers the
surface-by-surface migration of the other ~20 forms to follow-up
bundles, matching the audit's plan.

See [docs/audits/m3-alignment.md § Bundle 135](../audits/m3-alignment.md#bundle-135--textfield-primitive-2026-05-28)
for the line-by-line decision log.

## Context

[P2 #13](../audits/m3-alignment.md#13-text-fields-lack-m3-structure-filled-vs-outlined-supporting-text-leading-icon)
flagged that every form in `apps/web/src/app/**/*-form.tsx` open-codes
the same `<label>` + `<input className={inputClass}>` + `<FieldError>`
trio, with the field-error wiring (`fieldA11y('name', state.fieldErrors)`)
threaded by hand at each call site. The audit recommended a single
primitive that owns the chassis + ARIA wiring so call sites become
one line and the M3 surface treatment (border, focus ring, supporting
text, adornments) lives in one place.

The earlier Radix bundles (132 Toast, 134 Dialog) gave us a working
pattern for primitive bundles: ship the primitive, migrate **one**
reference call site, document the slot semantics, defer the long-tail
migration. TextField fits that mold but doesn't need Radix — there's
no a11y-tricky behavior to delegate, just chassis styling + ARIA
plumbing.

## Decisions

- **Outlined, not filled.** Filled is M3's default but reads as "very
  Material app" — outlined matches the current chassis (`border` +
  `focus:ring`) closely enough that migrating a form doesn't visibly
  break the surface. Floating label support is the one remaining M3
  outlined feature missing and is a CSS-only follow-up.
- **Single primitive for `<input>` and `<textarea>`.** Discriminated
  on `multiline: boolean` so the prop types stay tight (input-specific
  vs textarea-specific HTML attributes). Splitting into `<TextField>`
  - `<TextAreaField>` would force every call site to remember which
    one to use; that's the same paper-cut the audit was trying to
    eliminate.
- **`useId()` for the DOM `id`.** Form fields in this codebase
  duplicate `name` slugs in nested sections (e.g. address blocks).
  Using `name` directly as `id` would silently break label/control
  association in those forms.
- **Extend `<FieldError>` semantics, don't replace.** The primitive
  takes the same `errors?: Record<string, string>` shape that
  `fieldA11y()` / `<FieldError>` already use, so a call site
  migrates by deleting the `<FieldError>` + `fieldA11y()` plumbing
  and rendering `<TextField errors={state.fieldErrors} />`. Call
  sites that stay on the legacy chassis (the format `<select>` in
  the reference form, for example) keep working unchanged — both
  patterns coexist for the duration of the migration backlog.
- **`role="alert"` only on error.** Helper copy doesn't preempt the
  screen reader; only error copy does. `aria-describedby` is wired
  in both states so the support line is always announced when the
  field takes focus.
- **forwardRef.** Future callers (focus management on a server-action
  redirect, programmatic select on validation) need refs into the
  underlying control.

## Patterns observed

- **Discriminated-union props are how to type "two controls, one
  chassis."** Naming the discriminator `multiline` keeps the type
  flag readable at the call site and lets TypeScript narrow `...rest`
  to the right HTML attribute set. The `as` cast inside the
  primitive (`...(rest as InputHTMLAttributes<HTMLInputElement>)`) is
  fine because the union has already gated which branch we're in.
- **Slot-first chassis.** Leading/trailing icons inside the bordered
  row, prefix/suffix as text adornments, supportingText below — all
  three slots fall out cleanly once you stop trying to compose them
  with a single `flex` row. Padding adjusts via a tiny helper
  (`inputPadding(hasLeading, hasTrailing)`) rather than per-slot
  CSS classes, which keeps the styling cohesive.
- **The Bundle 130 `tap-target` and Bundle 131 `state-layer`
  utilities don't fit text fields.** Text fields aren't tappable
  affordances — they're focus targets. The right primitive here is
  `focus-within:ring-2` + `focus-within:border-md-primary`, which is
  what M3 outlined defines.
- **Audit's "surface-by-surface" plan is the right cadence.** Each
  form migration is a small, reviewable diff. Trying to flip all 20
  forms in one bundle would have produced an unreviewable PR and
  risked regressing field-error wiring in subtle ways.

## Follow-ups deferred

- **SelectField primitive (next P2 #13 bundle).** The format `<select>`
  in the reference call site is the obvious second control. Open
  decision: wrap native `<select>` (cheap, keeps mobile native
  picker) vs. adopt `@radix-ui/react-select` (full styling control,
  loses mobile native picker UX). The reference form's `<select>`
  intentionally stays on the legacy chassis so this decision can be
  made in isolation.
- **Floating label variant** of TextField (M3 outlined notches the
  border around the label). ~30 lines of CSS + a state class. Wait
  until a surface actually needs it.
- **Migration backlog.** Each of these is a small PR on top of the
  primitive:
  - `apps/web/src/app/events/new/new-event-form.tsx` (largest,
    many fields)
  - `apps/web/src/app/community/[id]/edit/community-listing-edit-form.tsx`
  - `apps/web/src/app/groups/new/new-group-form.tsx`
  - Remaining inputs in `apps/web/src/app/teams/new/new-team-form.tsx`
    (just the format `<select>`)
  - Profile / settings forms
- **`<NumberField>` / `<DateField>`** as composed wrappers if a
  concrete need surfaces (formatting + validation built in).
