## Context

The architecture audit ([architecture.md](../audits/architecture.md))
listed "No automated test suite" as an open P1 with a 2026-05-22 status
update still claiming "no Vitest config for `packages/domain` yet."
That was stale. Reality on disk:

- [packages/domain/vitest.config.ts](../../packages/domain/vitest.config.ts) exists.
- 5 events-aggregate test files (90 cases) + 1 application-handler test
  file (6 cases) all passing.

The bootstrap had landed in an unrecorded earlier pass; only the audit
doc lagged. Caught it when prepping Bundle 22 because I almost burned a
bundle re-doing work that was already done.

This bundle does two things:

1. Close the P1 honestly in the audit doc.
2. Fill the actual remaining gap: the `Team` aggregate had zero coverage.

## Decisions

- **Reconcile the audit before adding code.** Tempting to skip straight
  to writing tests, but a stale audit is how phantom items end up
  re-prioritized turn after turn. Updated status block, marked finding
  resolved, added remediation-log row, removed the item from "Still
  open."
- **`Team` over backfilling `VolleyballEvent`.** The events aggregate
  already has 90 tests across capacity, rules, registration, and
  payments. `Team` had none and is genuinely complex: two-state member
  status (`pending` / `active`), captain-as-always-active invariant,
  roster cap = `playersPerSide(format) + 2`, plus `extraMemberCount`
  that counts toward the cap but never appears in the members map.
  Better return on test-writing effort.
- **No application-handler tests this bundle.** `team.handler.ts` would
  need in-memory `TeamRepository` + `UserRepository` fakes — bigger than
  fits cleanly here. `JoinEventHandler` is the existing reference for
  that pattern when someone picks it up next.
- **Test the rehydration quirks.** `Team.rehydrate` clamps negative
  `extraMemberCount` to 0 and forces the captain to `active` even if
  persistence says otherwise — those are silent normalizations the
  Supabase adapter relies on. Both are now pinned by tests.

## Patterns surfaced

- **Always re-run `pnpm test` and grep the test dir before believing
  the audit doc.** An audit that says "no tests exist" is a hypothesis,
  not a fact. The session-summary loop can carry stale claims forward
  across many bundles.
- **`Team.maxRoster` is `playersPerSide + 2`** across all formats —
  that "+2 subs" rule is encoded once in the aggregate and now pinned
  by tests. If product ever wants to change it (e.g. larger benches for
  sixes), the test file is the canonical place to update.
- **Captain-active is a re-hydration invariant, not just a constructor
  one.** Repositories load whatever the DB has; the aggregate fixes it.
  Same pattern any future aggregate with a "special always-present
  member" role should follow.
