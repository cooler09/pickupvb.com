# 2026-05-22 — Bundle 33: ADR backfill — open-in-new-tab + Stripe webhook dedupe

## Context

Bundle 32 closed the canonical-domain-apex ADR (landed at slot 0009
instead of the originally-suggested 0006 because the lower slots had
been taken by `event-divisions` and the team-registration ADRs in the
interim). Two backfills remained from the original 2026-05-17
documentation audit:

- The OpenInNewTab button pattern (Server Actions ignore
  `<form target="_blank">`, requires a sync `about:blank` placeholder
  to keep the popup blocker out of the way).
- The Stripe webhook dedupe table (`stripe_webhook_events` keyed on
  event id, `upsert ignoreDuplicates` semantics, no payload storage).

Both were documented in code comments and an inline doc but never
captured as ADRs. This bundle finishes the cluster.

## What shipped

**(a) [docs/adr/0010-open-in-new-tab-server-actions.md](../adr/0010-open-in-new-tab-server-actions.md).**

Documents the
[`apps/web/src/components/open-in-new-tab-button.tsx`](../../apps/web/src/components/open-in-new-tab-button.tsx)
pattern:

- Why `<form target="_blank">` doesn't work on Server Actions (submits
  via `fetch`, not a real form post).
- The sync `window.open('about:blank', '_blank')` placeholder trick —
  opened inside the `onClick` handler so the browser treats it as a
  user gesture and the popup blocker stays out of the way.
- The deliberate omission of `noopener` because passing it makes
  `window.open` return `null` in most browsers. Scoped to first-party
  Stripe URLs only — flagged as a "do not generalize without re-adding
  the guard" warning.
- Same-tab fallback if the placeholder gets blocked anyway, plus the
  `nullMessage` / throw handling.
- The three call sites
  ([profile/billing](../../apps/web/src/app/profile/billing/page.tsx),
  [profile/billing/pro](../../apps/web/src/app/profile/billing/pro/page.tsx),
  [pricing](../../apps/web/src/app/pricing/page.tsx)).
- Three rejected alternatives.

**(b) [docs/adr/0011-stripe-webhook-dedupe.md](../adr/0011-stripe-webhook-dedupe.md).**

Documents the receiver-level idempotency layer at
[apps/web/src/app/api/webhooks/stripe/route.ts](../../apps/web/src/app/api/webhooks/stripe/route.ts):

- The `public.stripe_webhook_events` table schema (id PK = Stripe
  `evt_…`, no payload column).
- The `upsert ignoreDuplicates` flow: non-empty returned rows ⇒ first
  sighting, dispatch + write `processed_at`; empty array ⇒ already
  processed, return `200 { deduped: true }` immediately.
- Signature verification happens **before** the dedupe insert.
- The **delete-on-handler-throw** branch — without it, a transient
  handler failure would dedupe the eventual Stripe retry. The
  performance audit's switch from `insert-and-catch-23505` to
  `upsert ignoreDuplicates` (P2 #9) preserved this exact semantics.
- Why we deliberately **don't** store the full payload (size + PII;
  Stripe Dashboard is the source of truth for payloads, this table is
  the source of truth for "did we process it?").
- Trade-off noted: per-receiver dedupe means a future Platform/Connect
  endpoint split would need namespace separation. Today both share one
  endpoint so it's moot.
- Four rejected alternatives (per-handler only, signature timestamp,
  Redis, full-payload storage).

## Patterns surfaced

- **ADR slot drift is now the norm.** Three of the four ADRs from the
  original 2026-05-17 backfill cluster ended up at different numbers
  than recommended (0009/0010/0011 vs. 0006/0007/0008). The
  remediation log entries record both numbers so chat-history searches
  for the original slot still find the right ADR.
- **Code-comment + inline-doc ≠ ADR.** Both ADRs document patterns
  that were already explained at length in source comments
  (`open-in-new-tab-button.tsx` has a 6-line NOTE block; the Stripe
  webhook route has a 20-line preamble + per-section comments). The
  ADR adds: the rejected alternatives, the cross-references to
  callers, and the trade-offs in one searchable place. Worth capturing
  even when the source is well-commented.
- **"Do not generalize without re-adding the guard"** is the most
  important sentence in ADR 0010. The `noopener` decision is safe
  only because every consumer is a first-party Stripe URL today; the
  next person who reaches for this component for an arbitrary user
  URL needs the loud warning.
