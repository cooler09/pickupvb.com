# Bundle 47 — split `groups/actions.ts` into per-concern files (2026-05-23)

## Context

The last remaining mechanical P2 from the 2026-05-17 architecture audit:
[`apps/web/src/app/groups/actions.ts`](../../apps/web/src/app/groups/actions.ts)
was a 166-LOC catch-all holding six unrelated server actions (group
create/update, follow/unfollow, member add/remove/role-change). The
sibling `events/[id]` route splits actions by concern
(`co-host-actions.ts`, `rsvp-actions.ts`, `members-actions.ts`,
`tip-actions.ts`, etc.); `groups/actions.ts` was the lone holdout, which
made grepping for a single action awkward and made it tempting to drop
unrelated logic into the same file on the next change.

## What shipped

- **Deleted** `apps/web/src/app/groups/actions.ts`.
- **Created** three per-concern files at `apps/web/src/app/groups/`:
  - [group-form-actions.ts](../../apps/web/src/app/groups/group-form-actions.ts)
    — `createGroupAction`, `updateGroupAction`, shared `GroupFormState`
    type, and the file-private `SLUG_RE` regex. Kept together because
    both actions share the form-state contract consumed by their client
    forms.
  - [follow-actions.ts](../../apps/web/src/app/groups/follow-actions.ts)
    — `followGroup`, `unfollowGroup`.
  - [member-actions.ts](../../apps/web/src/app/groups/member-actions.ts)
    — `addGroupMember`, `removeGroupMember`, `changeGroupMemberRole`.
- **Updated five importers** to point at the new paths:
  - [members-actions.ts](../../apps/web/src/app/groups/%5Bid%5D/members/members-actions.ts)
  - [edit-group-form.tsx](../../apps/web/src/app/groups/%5Bid%5D/edit/edit-group-form.tsx)
  - [group-viewer-actions.tsx](../../apps/web/src/app/groups/%5Bid%5D/_components/group-viewer-actions.tsx)
  - [member-row-item.tsx](../../apps/web/src/app/groups/%5Bid%5D/members/_components/member-row-item.tsx)
  - [new-group-form.tsx](../../apps/web/src/app/groups/new/new-group-form.tsx)

No behaviour changes — each function body was moved verbatim, including
existing `revalidatePath` calls and the `redirect` in `createGroupAction`.

## Pattern notes

- **`'use server'` files can't act as barrels.** A pure re-export
  `actions.ts` would lose the `'use server'` directive's effect for the
  re-exported symbols. The split has to update every importer; no
  shortcut. That's also why the events/[id] folder ended up with one
  file per concern in the first place.
- **Co-locating actions that share a `FormState` type** (the
  `createGroupAction` / `updateGroupAction` pair) reads better than
  splitting them across two files just to have one export per file —
  the shared type would have to be moved into a third `types.ts` or
  exported from one action file and imported by the other. The
  events/[id] convention is "one file per concern," not "one export per
  file," so the pair stays together.
- **The split makes the next bundle cheaper.** Any future P3 sweep that
  adds typed-error redirects (the `co-host-actions.ts` pattern from
  Bundle 46) or migrates `Promise<void>` actions to typed `Result`
  returns now operates on three focused files instead of one
  catch-all — easier to scope a PR and easier to grep call sites.
