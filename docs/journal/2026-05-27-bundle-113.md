# Bundle 113 — Bracket: auto-scroll + flash on realtime update

## Why

Bundle 112 gave the spectator a manual "Jump to latest" anchor.
The realtime refresher (108) already triggers a re-render every
time a match result lands — but the cursor didn't move, so the
spectator still had to notice the bracket updated and tap the
button to follow play. On a phone in a noisy gym that round-trip
is exactly the friction we want to remove.

Goal for this bundle: when realtime promotes a new "latest
match," draw the eye to it automatically. Centre the new card
in the viewport on the spectator route; flash a yellow ring on
both routes so the change is visible even when the card is
already on-screen. Keep the host page non-scrolling so a host
mid-score-entry isn't yanked away from the input they're
filling out.

## What changed

### New `LatestMatchTracker` client component

**NEW**
[apps/web/src/app/events/[id]/bracket/\_components/latest-match-tracker.tsx](../../apps/web/src/app/events/%5Bid%5D/bracket/_components/latest-match-tracker.tsx).
Tiny `'use client'` effect-only component (`return null`) that
watches a `matchId` prop across renders:

- Skips the first mount so a fresh page load doesn't jerk the
  viewport — the initial scroll position is the user's intent.
- On subsequent renders, when the id flips to a new value,
  finds `#match-{id}` in the DOM, optionally
  `scrollIntoView({ behavior: 'smooth', block: 'center' })`,
  and toggles `.match-flash` on the wrapper.
- Forces a reflow (`void el.offsetWidth`) between
  `classList.remove` and `classList.add` so the same element
  re-fires its animation when it's promoted twice in a row
  (e.g. two sets entered back-to-back on the same court).

Takes `autoScroll: boolean`. Spectator route passes `true`;
host route passes `false` (flash only).

### `.match-flash` keyframes in globals.css

**EDIT**
[apps/web/src/app/globals.css](../../apps/web/src/app/globals.css).
One-shot `box-shadow` pulse in amber (the same yellow used for
the "● LIVE" pill family), running the keyframes twice over
1.6s for a clearly-visible 3.2s flash. A
`prefers-reduced-motion` block swaps the animation for a static
ring so accessibility users still get the visual cue without
the pulsing.

### Both bracket pages render the tracker

- [apps/web/src/app/events/[id]/bracket/watch/page.tsx](../../apps/web/src/app/events/%5Bid%5D/bracket/watch/page.tsx)
  — `<LatestMatchTracker matchId={pickLatestMatchId(...)} autoScroll />`.
- [apps/web/src/app/events/[id]/bracket/page.tsx](../../apps/web/src/app/events/%5Bid%5D/bracket/page.tsx)
  — same, with `autoScroll={false}`.

Wrapped together with `BoardView` in a fragment under the
existing `bracket.status === 'active' | 'completed'` guard so
the tracker only mounts when there are matches to watch.

## Patterns observed

- **Effect-only client components beside server-rendered
  content is the right shape for "react to prop change without
  owning the markup."** `BracketRealtimeRefresher` already
  uses this pattern (returns `null`, subscribes to Supabase,
  triggers `router.refresh()`). `LatestMatchTracker` is the
  twin: returns `null`, watches a prop, mutates the DOM that
  another (server) component rendered. No need to lift
  `BoardView` to a client component just to add a side effect.
- **`void el.offsetWidth` is the canonical reflow trick.** CSS
  animations don't re-fire when the same class is added to an
  already-classed element; reading a layout property between
  remove + add forces the browser to commit the removal before
  the next paint. Cleaner than `requestAnimationFrame` chains
  for this one-frame need.
- **`prefers-reduced-motion` swap, not omission.** Users with
  reduced-motion still benefit from "where did the update
  happen?" — they just don't want the pulse. The fallback
  paints a static amber ring so the information density is
  the same; only the motion is removed.

## Follow-ups deferred

- **"Don't yank me" guard.** If the spectator has manually
  scrolled to inspect a different match, auto-scroll is
  unwelcome. An `IntersectionObserver` watching the previous
  latest could detect "user has navigated away" and downgrade
  to flash-only. Not worth shipping until someone complains.
- **Sound cue.** A short ding on result-landing would be nice
  for a projector setup with no eyes on it, but it needs a
  user gesture to unmute (browser autoplay policy) and a
  toggle. Deferred until a host asks.
- **Tracker as a `BoardView` sibling for `setup` status.**
  When seeding swaps land in setup mode, there's no `latest`
  match to flash — but it would be nice to flash the seeding
  row that changed. Different mechanism (no
  `pickLatestMatchId`), worth its own bundle if/when it
  comes up.
