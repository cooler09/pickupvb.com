# 2026-05-24 — Bundle 82: Retire Vercel Analytics + Speed Insights pre-launch

## Context

Bundle 81 closed the last P2 on the analytics audit (P2 #5 — consent
affordance). The remaining items were all P3. P3 #12 — "Vercel
Analytics + PostHog overlap to retire" — was authored with a
post-cutover 30-day parity window in mind, on the assumption we'd
already have production traffic in Vercel Analytics worth comparing
against. Pre-launch that assumption doesn't hold: there's no
historical data to lose, no parity to validate, and every day we
keep both running is a day we're paying the cognitive tax of two
analytics surfaces.

## Decisions

- **Drop both `@vercel/analytics` and `@vercel/speed-insights` now,
  not later.** Pre-launch the audit's "wait for parity data"
  rationale doesn't apply. Removing now also means the consent
  banner shipped in Bundle 81 has one fewer client component to
  conditionally mount, simplifying the layout.
- **Keep `<WebVitalsClient />`.** It's our own component (`useReportWebVitals`
  from `next/web-vitals`) that beacons to `/api/web-vitals` →
  `analytics.capture('web_vitals', ...)`. It's the PostHog bridge,
  not a Vercel package. No change here.
- **Don't ship a `$pageview` replacement in this bundle.** Vercel
  Analytics had auto page-view capture; PostHog today only fires
  custom events + web vitals. Pre-launch we don't need page-view
  funnels yet, and shipping a beacon-based `$pageview` deserves its
  own bundle (it touches every route via the layout, needs a route
  template masker, and has to integrate with the existing UTM /
  attribution cookie from Bundle 77). Documented as a follow-up.
- **Be honest in the docs.** `docs/monitoring.md` previously said
  "Vercel Analytics + Speed Insights"; the new section is "Product
  analytics (PostHog)" and explicitly calls out the unwired
  page-view capture as a known gap, rather than hand-waving over it.

## Patterns surfaced

- **"Wait for parity data" is meaningless pre-launch.** Several
  P3 items on this audit were scoped around a 30-day overlap window
  that only matters once we have production users. When walking the
  P3 backlog before launch, check each one for that assumption.
- **Two analytics dashboards is two analytics surfaces.** Even
  internally with a small team, every "where do I check that?"
  question costs more than the marginal coverage of a duplicate
  vendor.

## Follow-ups

- **`$pageview` capture via the existing beacon pattern.** Hook into
  the App Router via a small `<PageViewClient />` (or extend
  `WebVitalsClient`) that emits one `analytics.capture('$pageview',
{ route })` per navigation. Use the same masked-route templates
  the web-vitals beacon already uses. Wire only after launch traffic
  warrants it.
- **Remaining P3 items.** P3 #10 (distinct-id salt rotation runbook)
  and P3 #11 (A/B framework). Both stand alone — neither blocks the
  other.
