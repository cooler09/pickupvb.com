# Bundle 3 — Registration price-unit enforcement (2026-05-22)

## Context

[`docs/audits/registration-workflow.md`](../audits/registration-workflow.md)
left two P1 items open:

1. **UX P1** — pricing shown in `DivisionsSection` didn't match what
   checkout actually charged when divisions had different prices.
2. **Model P1** — `price_unit` (`per_team` / `per_player`) was "still not
   enforced; checkout reads the first division's price only. No
   captain-pays-team Stripe path."

Discovery during this bundle turned up that **both** lines of the audit
were partially stale:

- The **UX P1** was already mitigated by
  [`divisions-section.tsx`](../../apps/web/src/app/events/[id]/_components/divisions-section.tsx#L36-L51),
  which suppresses per-division price display when `divisions.length > 1`
  (per ADR 0007). The audit body just hadn't been annotated.
- The **Model P1** "no captain-pays-team Stripe path" was wrong for the
  **ad-hoc** team-registration mode — that path is fully implemented:
  [`team-checkout-actions.ts`](../../apps/web/src/app/events/[id]/team-checkout-actions.ts),
  [`webhooks/stripe/route.ts#L255`](../../apps/web/src/app/api/webhooks/stripe/route.ts#L255),
  [`team-checkout/success/route.ts`](../../apps/web/src/app/events/[id]/team-checkout/success/route.ts),
  with the full `EventTeamRegistration` aggregate state machine
  (`markCheckoutPending` → `markPaid` / `expireCheckout` / `refund`).
  What is **actually** missing is the captain-pays-team path for
  **roster** mode (where the captain picks an existing persistent team
  rather than creating one at signup).

The audit text was therefore at least one bundle out of date. **Lesson
captured below.** This bundle annotates the audit, ships the smaller
remediations, and leaves a complete spec for the roster-mode work.

## Scope

Four items were originally proposed for this bundle. Three landed; one is
deferred with a full spec.

### Shipped

1. **ADR 0007 §3 validation at create + edit boundaries** — reject the
   `(tournament + team-led mode + at least one per-player priced division +
on-platform payments)` combination with a user-facing error that names
   the three ADR-prescribed resolutions:
   - Switch the priced division(s) to per-team pricing.
   - Disable team registration (open per-player signup).
   - Set payments off-platform.

   Implemented as a shared validator
   ([`event-team-pricing-validation.ts`](../../apps/web/src/lib/event-team-pricing-validation.ts))
   called from both
   [`apps/web/src/app/events/new/actions.ts`](../../apps/web/src/app/events/new/actions.ts)
   and
   [`apps/web/src/app/events/[id]/edit/actions.ts`](../../apps/web/src/app/events/[id]/edit/actions.ts).

2. **`team_registration_mode` is now editable** — previously the field was
   only set at event creation, and **no UI control existed for it even
   there**. Added a select to both the create form
   ([`new-event-form.tsx` `PaymentSettingsSubsection`](../../apps/web/src/app/events/new/new-event-form.tsx))
   and the edit form
   ([`edit-event-form.tsx`](../../apps/web/src/app/events/[id]/edit/edit-event-form.tsx))
   with three options:
   - `ad_hoc` — captains create a team at signup (current aggregate default).
   - `roster` — captains pick an existing team.
   - `none` — individual signups only.

   The edit action writes `team_registration_mode` into the events row
   only for tournaments.

3. **Annotated [`event-pricing.ts`](../../apps/web/src/lib/event-pricing.ts)** —
   updated the "future scope" comment to reflect that per-team divisions
   now have their own checkout path
   ([`team-checkout-actions.ts`](../../apps/web/src/app/events/[id]/team-checkout-actions.ts))
   and to document why the first-division-only read is still safe under
   the new ADR 0007 §3 rule.

### Deferred — Roster-mode per-team captain checkout (spec below)

This was originally Task #4 in the bundle. Realistic surface:

- New migration (sidecar table `event_team_payments` plus a composite-key
  index on `event_teams` to support the FK).
- Either a new `EventTeamPayment` aggregate + repository port, **or**
  extending `EventTeamRegistration` with a `source_team_id` column to
  unify both modes.
- New server action `startRosterTeamCheckout` (or extension of
  `team-checkout-actions.ts`).
- New webhook branch in
  [`apps/web/src/app/api/webhooks/stripe/route.ts`](../../apps/web/src/app/api/webhooks/stripe/route.ts)
  for the new `metadata.kind`.
- New success/cancel routes (or shared with ad-hoc).
- UI on the event page: a "Pay $X" button next to the registered team
  when `priceUnit === 'per_team' && !paymentsOffPlatform && payment_status !== 'paid'`.
- Composition root wiring + types regen.
- Domain tests for the state machine.

Why deferred: ADR 0007's validation rule that landed in this bundle stops
**new** misconfigured events from being created — a free-tier host can no
longer save an event that would silently skip charging roster captains.
That removes the immediate money-loss risk. The remaining work is to
plumb the actual charging flow for roster captains who want it. Splitting
that into its own bundle keeps the migration + Stripe + webhook + UI
changes reviewable as a single unit instead of stapled to validation work.

## Decisions

### 1. Validation as `{ error }` return, not thrown `DomainError`

Matched the surrounding `editEventAction` / `createEventAction` style,
which already accumulates `{ error, fieldErrors }` from input validation
and never throws. A typed `ValidationError` would have been the
boundary-pure choice, but the action layer here is the boundary — it
already maps every other failure mode the same way. Promoting this one
check to a `DomainError` would have been inconsistent.

### 2. Validator lives in `apps/web/src/lib/` not in `@pickupvb/domain`

ADR 0007 §3 is a **boundary rule** (which combinations the platform can
collect on), not an aggregate invariant. The aggregate already allows any
combination of `teamRegistrationMode` + `priceUnit` + `paymentsOffPlatform`
because it has to load old data faithfully. Putting the rejection in the
action keeps the aggregate able to rehydrate legacy events without
exploding, while still preventing new bad rows.

### 3. Sidecar table for roster-mode payments (when implemented)

Three modeling options were considered for storing roster-team payment
state (asked of the human reviewer mid-bundle):

- **Extend `EventTeamRegistration` with `source_team_id`** — unify both
  modes under one aggregate.
- **Add payment columns directly to `event_teams`** — separate aggregate,
  separate state machine.
- **Sidecar `event_team_payments` table** — payment row references the
  `event_teams` row via composite FK.

Chose the **sidecar** route: keeps `event_teams` as a clean
registration-only row (so non-paid roster registrations still don't get
fake payment metadata), gives the payment record its own lifecycle for
refunds/disputes, and leaves the `EventTeamRegistration` aggregate
strictly for the ad-hoc model it was designed for. Trade-off: more
tables to query when rendering the captain dashboard.

### 4. `teamRegistrationMode` defaults remain unchanged

The aggregate still defaults a new tournament to `AdHoc` when the field
is unset (`volleyball-event.ts:343-344`). The form now exposes the value
explicitly so hosts can pick `roster` or `none` at creation, but
defaulting in the aggregate means **existing tournaments** keep their
current effective mode without a backfill migration.

### 5. Edit-form mode change is unguarded today

Switching `team_registration_mode` after registrations exist could strand
existing signups (e.g. ad-hoc teams disappear from the page if the host
flips to `roster`). The form has a copy warning ("change with care") but
no hard guard. Adding an attendee-count guard is a follow-up — it needs
to be done carefully so a host who's misconfigured an empty event can
still fix it, which is the primary reason mode became editable at all.

## Patterns observed

### Audit "Still open" text can lag actual code by a bundle or two

Both audit lines reviewed here turned out to be partially or fully
addressed already. **Before scoping work off an audit "Still open" entry,
read the actual code paths it references.** Update the audit body /
remediation log first if the text is stale, then scope. This bundle's
original estimate was 2-3× larger than the real remaining work.

A useful grep pattern: search for any of the symbols / file names called
out in the audit, then trace from there. If the matches show recent
modifications or extensive structure (aggregate, webhook handler, success
route), the audit is probably out of date.

### Validation rules that span boundaries belong in `apps/web/src/lib/`

This is the third boundary rule of this shape
(`host-paid-event-cap.ts`, `pricing-lock.ts`, and now
`event-team-pricing-validation.ts`). All three:

- Take primitive inputs (no aggregate dependency).
- Return `{ ok: true } | { ok: false, reason: string }` (or similar).
- Are called from server actions, never from the domain.
- Encode rules that are "policy" (could vary by tier / billing plan /
  release stage), not "invariant" (must always hold).

Worth promoting into AGENTS.md as a fourth "Pattern surfaced by audits"
entry once a fourth example shows up.

### `[id]`-path globs fail in custom search but work in shell

`file_search` / `grep_search` couldn't match files under the
`apps/web/src/app/events/[id]/edit/` directory because of how the brackets
are handled. Falling back to `run_in_terminal grep -rn` worked
immediately. Worth knowing for future agent runs — don't waste turns
re-querying with different glob patterns when the dir is bracketed.

## Follow-ups deferred

1. **Roster-mode per-team captain checkout** (spec above). Highest
   priority since the validation only blocks _new_ bad combos; existing
   events configured as `roster + per_team + on-platform` (if any exist
   pre-validation) still need the path to actually charge captains.

2. **Backfill audit** — query production for events matching the now-rejected
   combination. If any exist, follow up with a migration or a host-facing
   notification rather than silently breaking their signup flow when #1
   ships and adds the charge step.

3. **`team_registration_mode` change-guard** — block (or warn more
   loudly) when changing mode after team registrations exist. See
   "Decision 5" above.

4. **`PaidTicketPanel` two-button collapse** (existing audit P2) — still
   open; unrelated to this bundle but visible in the same UX area.
