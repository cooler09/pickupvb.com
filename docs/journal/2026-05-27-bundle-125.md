# Bundle 125 — Pool play: host-driven match reorder (Phase 1b of ADR 0018) (2026-05-27)

## Context

Bundles 122–124 shipped the bulk of [ADR 0018](../adr/0018-pool-play-configuration.md):
bestOf + schedule density (Phase 1), work-team assignment (Phase 2), and
courts + parallel-slot solver (Phase 3). The generator picks a
deterministic round-robin order, but real-world hosts always want to
nudge it — "Court 1 should start with the marquee teams," "this team
arrived late, push their first match back a slot."

Phase 1b adds the smallest viable affordance: **up/down arrow buttons
on each pool match card** that renumber the pool and re-run the
court/slot solver. No drag-and-drop yet; the buttons cover the
common cases (move one match by a position or two) with zero JS
client bundle.

## Decision

- **Domain: `Bracket.reorderPoolMatches(pool, newOrder)`**
  ([packages/domain/src/brackets/bracket.ts](../../packages/domain/src/brackets/bracket.ts)).
  Validates: bracket status is `active`, format is `pool_play_playoff`,
  `newOrder` length matches the pool's match count, no duplicates, every
  id resolves to a match in `pool`, and **no match in the pool has
  progressed past `pending` / `bye`** (`ConflictError` otherwise — once a
  result is recorded the slot/court assignments are real-world commitments
  and reordering would invalidate scoreboards already in use).
  Renumbers `matchNumber` 1..N in the new order, then — when
  `courtLabels` is non-empty — re-runs `assignCourtsAndSlots` over the
  full sorted pool list to keep court/slot consistent with the new
  numbering. `matchNumber` is `readonly` on the `Match` interface so
  the aggregate uses a localized `as { matchNumber: number }` cast;
  documented inline. Seven new aggregate tests
  ([packages/domain/src/brackets/bracket.test.ts](../../packages/domain/src/brackets/bracket.test.ts))
  bring the bracket suite to 41.
- **Application: `ReorderPoolMatchesCommand` + handler**
  ([packages/application/src/commands/bracket.handler.ts](../../packages/application/src/commands/bracket.handler.ts)).
  Loads the bracket + event, `assertHost(event, requesterId)`, calls
  the aggregate, saves. Standard CQRS shape — no new ports needed.
- **Web: `movePoolMatchFromForm` server action**
  ([apps/web/src/app/events/[id]/bracket/actions.ts](../../apps/web/src/app/events/[id]/bracket/actions.ts)).
  Takes the current sorted pool match-id list from repeated
  `<input type="hidden" name="match_id">` fields plus a `move_id` and
  `direction`. The action swaps the target id with its neighbor and
  hands the resulting array to the command. Edge cases (already at
  top/bottom, missing target) short-circuit without throwing. Catches
  `DomainError` via the existing `classify()` helper and bounces back
  with a `?notice=` flash param.
- **UI: inline `ReorderControls` in `PoolsView`**
  ([apps/web/src/app/events/[id]/bracket/\_components/board-view.tsx](../../apps/web/src/app/events/[id]/bracket/_components/board-view.tsx)).
  Two `<form>` elements (one ↑, one ↓) per match, rendered only when
  the viewer is the host **and** every match in the pool is still
  `pending` / `bye`. Disables the arrow at each pool boundary so the
  user can't submit a no-op. The hidden id list is the same sorted
  pool order the cards render in, so what you see is what you send.

## Rejected alternatives

- **Full drag-and-drop with `dnd-kit` or `react-beautiful-dnd`.** Would
  ship a ~30 KB client bundle for an action a host runs a handful of
  times during setup. Up/down buttons cover the same use case with
  zero JS and stay accessible by default. Revisit if hosts ask for it
  or if we want cross-round reordering (which the buttons can't
  express).
- **Edit-mode page where the host reorders all matches at once before
  submitting.** Heavier UI; the per-card buttons keep the bracket page
  as the single source of truth for both reading and editing.
- **Allow reorder after results are recorded.** Rejected as a
  `ConflictError`. Once a scoreboard has been issued for "Pool A match
  3," changing what "match 3" means breaks live state. Hosts who need
  to recover can `Reset bracket` and re-seed.
- **Slot-aware reorder (move within a slot without renumbering).** Out
  of scope. The current model treats `matchNumber` as the canonical
  order and lets the solver derive slots — that's enough for v1.

## Patterns surfaced

- **Aggregate methods can validate "no progress yet" as a hard
  precondition.** Useful escape hatch for editing-after-publish flows
  without inventing a separate "draft" status.
- **`readonly` interface fields are not a sealed door inside the
  aggregate.** Localized type-cast assignment is acceptable when the
  invariant being modified is one the aggregate owns. Document why
  inline so the next reader doesn't widen the interface.
- **Hidden-input "current order" snapshots are the simplest way to
  ship server-action reorder without DnD.** The action stays
  stateless and the UI stays plain HTML; the client never needs to
  know the previous-order list because the form carries it.

`pnpm typecheck && pnpm lint && pnpm test && pnpm build` — all green.

## Follow-ups

- Drag-and-drop UI if hosts ask. Same server action will work — DnD
  just produces the `match_id[]` list in a new order in one shot
  instead of by swap.
- Cross-round reorder (rare in round-robin pool play; punt until
  asked).
- Reorder analytics — none yet; if we see hosts mashing the arrows
  we may want to surface a "reorder all" page instead.
