# Bundle 63 — 2026-05-23 — Free-agent list groups by division on multi-division events (Registration workflow UX P3, partial close)

## Context

Bundle 62 closed Model P2 ad-hoc live-vs-dead audit and recommended
continuing on real-implementation findings rather than another
Wontfix/verification pass. The Registration workflow audit's
still-open list had three remaining UX P3 sub-items, the smallest
of which was "Free-agent list still has no division grouping or
captain-claim affordance."

That P3 is actually two findings glued together:

1. **Division grouping** — when the event has multiple divisions,
   render the free-agent list bucketed by division so captains
   scanning for "who's free in 6v6 open?" don't have to read the
   division pill on every row.
2. **Captain-claim affordance** — let a captain click a free agent
   to pull them into an `EventTeamRegistration` slot.

Bundle 5 already shipped the per-row division pill (so captains
_can_ tell which division a free agent picked, just inefficiently).
Bundle 63 closes the grouping half. The captain-claim affordance
needs new domain + server-action work (mutating
`event_team_registration_members` from outside the captain's own
roster flow) and is left open.

## Why grouping (and not the bigger claim affordance)

The claim affordance touches the domain layer: it needs either a
new `claimFreeAgent` port on `EventRepository` or a reuse of the
existing roster-mode "add member" path with the free-agent row as
the source. Either way it's a new command handler + Stripe
implication if the captain hasn't pre-paid + a `?fa=claimed` flash

- revalidation of the team panel as well as the free-agent panel.
  That's a multi-aggregate bundle, not a one-component UI tweak.

Grouping is the cheapest win that materially improves the UX a
captain sees today — they no longer have to read each row's pill
to filter to their bracket. Shipping it alone also keeps the
captain-claim work cleanly scoped when someone picks it up later.
