# 2026-05-22 — Bundle 23: events/[id] page diet via `loadEventDetail`

## Context

Bundle 22 closed the last "easy" P1 on the architecture audit (test
bootstrap). The only remaining architecture P1 was the
[`events/[id]/page.tsx`](../../apps/web/src/app/events/%5Bid%5D/page.tsx)
page diet — the file had grown from ~520 LOC at the 2026-05-17 audit
to 887 LOC, mixing metadata generation, viewer auth, two waves of
parallel side-loads, snake_case→camelCase mapping for the legacy
`AttendeeList` component, position-fill math, ad-hoc tournament data
hydration, and the hero/sticky CTA discriminator — all interleaved
with ~440 LOC of JSX.

The audit prescribed extracting a `loadEventDetail(id, viewer)` helper
returning a fully-typed `EventDetailViewModel`. Target was ≤300 LOC.

## Decisions

- **Single co-located loader file under `_loaders/`.** Followed the
  existing convention — `_components/` and route-specific helpers
  already live as underscore-prefixed siblings. The directory name
  signals "page-scoped data layer", separating it from `_components/`
  (rendering) without bloating either.
- **One view-model object, not multiple helper calls.** Considered
  splitting into `loadEventCore`, `loadPaidExtras`, `loadAdHocBundle`,
  but the page would then have to re-orchestrate the two-wave parallel
  fetch. Returning a single `EventDetailViewModel` keeps the page a
  pure renderer with a single `await`.
- **Preserve the two-wave side-load shape verbatim.** Wave 1 pulls
  pricing + 5 other independent reads in parallel; Wave 2 depends on
  `paid` (derived from pricing) so it runs after. The audit's
  performance work-in-progress relies on this shape; rewriting it
  now would conflict with the upcoming Suspense refactor.
- **Keep `generateMetadata` separate.** It only needs the event row,
  not the full side-load. Calls `handlers.getEventDetail.execute()`
  directly. React `cache()` could deduplicate the second fetch, but
  that's a P3 nice-to-have — left as a follow-up so this bundle stays
  pure refactor.
- **Type bridge to `AttendeeList`.** The component still takes the
  legacy snake_case `Attendee` shape. Rather than rewrite the
  component, the loader maps `event.attendees` (read-model camelCase)
  to `AttendeeListRow` (snake_case). Component rewrite is a separate
  P2 follow-up.
- **Aspirational ≤300 LOC deferred.** Landed at 566 LOC — a 35% cut
  from 887. The remaining bulk is JSX render branches (paid vs free,
  tournament vs pickup, ad-hoc vs roster, host vs viewer, external
  vs internal). Further cuts require componentization, which is a
  separate concern from the data-layer extraction the P1 called out.
  Carried as a P2 follow-up on the audit.

## Verify

`pnpm typecheck && pnpm lint && pnpm test && pnpm build` — all green.
Test totals unchanged from Bundle 22 (122 domain + 6 application).

Two iterations were needed during typecheck:

1. `viewerPosition` was typed as `string | null`; downstream
   `<PositionRsvpPanel>` expects `EventPosition | null`. Tightened
   the view-model type and imported `EventPosition` from
   `@pickupvb/domain`.
2. `AttendeeListRow.profiles.display_name` was typed as
   `string | null`, but the read model's `ProfileLite.displayName`
   is non-nullable. Tightened.
3. `friendIds` was typed `ReadonlySet<string>` and
   `payments` was typed `ReadonlyMap<string, AttendeePaymentInfo>`,
   but the AttendeeList component takes mutable `Set` / `Map`
   (it doesn't mutate; the prop type is just lax). Relaxed the
   view-model types to match.

Lesson: when a view-model bridges to legacy components, lean toward
the component's declared prop types rather than the strictest
read-only flavor — typechecker can't see that the component is
read-only in practice.

## Follow-ups deferred

- **JSX componentization for `events/[id]/page.tsx`.** Land the
  ≤300 LOC target by splitting the render branches. Candidates:
  a `<SignupArea>` switcher (paid/RSVP/tournament/ad-hoc/free-agent),
  a `<HostToolsPanel>` grouping (host broadcasts + divisions manager
  - ad-hoc panel + winners panel), and the JSON-LD/breadcrumb block
    into a single `<EventStructuredData>`. Logged as a P2 on the
    architecture audit.
- **React `cache()` for `getEventDetail`.** `generateMetadata` and
  `loadEventDetail` both call `handlers.getEventDetail.execute()`.
  Wrapping the call in `cache()` would dedupe the second fetch
  on the same request. P3.
- **Push `filledByPosition` into `EventDetailReadModel`.** The
  loader still recomputes it from `event.attendees`. Trivial DB-side
  agg in the infrastructure adapter — P2 on the audit.
- **Rewrite `<AttendeeList>` to take camelCase props.** Would remove
  the `AttendeeListRow` bridge in the loader. P3.

## Patterns surfaced

- **`_loaders/` as a sibling to `_components/`.** New page-scoped
  convention. Mirrors the existing pattern where page-specific
  helpers live as underscore-prefixed siblings. Worth promoting to
  AGENTS.md if a second page picks it up.
- **View-model assembly + two-wave parallel side-load** is a
  reusable shape for any page that mixes a domain read model with
  several admin/auth/pricing side-loads. The loader file is a good
  template for future page-diet refactors (the `groups/[id]/page.tsx`
  page is the next obvious candidate if it grows).
- **Bridge types belong on the consumer side.** `AttendeeListRow`
  could have been declared in `_components/attendee-list.tsx` since
  it's the component's input shape; putting it in the loader keeps
  the page-boundary mapping explicit and lets future loaders
  evolve the bridge without touching the component.
