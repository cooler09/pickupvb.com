# Bundle 73 — 2026-05-24 — Community claims: defense-in-depth match check

## Context

Audit follow-up to the community-listing claim flow shipped in
bundle 72. The original `ClaimCommunityListingHandler` had a single
authorization check:

```ts
const isHost = await this.isHostOfEvent(requesterId, eventId);
if (!isHost) throw new UnauthorizedError(...);
```

…where `isHostOfEvent` only asked "is `events.host_id` === requester?"
That meant **any user who hosts even one PickupVB event could claim
every active community listing** by passing their own event id at the
claim boundary. There was no check that the chosen event had anything
to do with the listing (same date? same city? roughly the same
sport?), and no DB constraint preventing the same `claimed_event_id`
from backing many `community_listings` rows.

The new UX shipped in the previous step (a `<select>` of the viewer's
own hosted events instead of a raw UUID input) limited which events a
typical user could pick from in the browser, but the server action
still trusted whatever `event_id` came back in the form — a hand-
crafted POST would bypass the dropdown entirely.

## Decision

Three layers, ordered cheapest-to-strictest:

### 1. UI filter (best-effort, UX-only)

In [community/[slug]/page.tsx](../../apps/web/src/app/community/[slug]/page.tsx),
filter the already-loaded `claimableEvents` down to `eligibleEvents`
that match the listing's `(day, city)`. Empty-state copy now
distinguishes "you have no upcoming events" from "you have events,
none of them match this listing's day + city". This is purely so the
dropdown isn't full of mismatched options — the server still rechecks.

### 2. Application-layer match check (the real gate)

`ClaimCommunityListingHandler`'s constructor dependency changes from
`isHostOfEvent: (userId, eventId) => Promise<boolean>` to a richer
port that returns the event facts needed to authorize the claim:

```ts
loadEventClaimFacts: (eventId) =>
  Promise<{
    hostId: string;
    coHostIds: string[];
    startsAt: Date;
    city: string | null;
    timeZone: string | null;
  } | null>;
```

`execute()` now:

1. Loads the listing — `NotFoundError` if missing.
2. Loads event facts — `NotFoundError('Event', …)` if missing.
3. Authorizes against `hostId` **or** `coHostIds` (co-hosts can claim
   on behalf of the event — they're already trusted to manage it).
4. Runs `matchesByDateAndCity(listing, facts)` — same calendar day in
   the listing's timezone (falling back to event timezone, then UTC)
   AND same city, case-insensitive, both sides required non-null.
5. On match mismatch → `ConflictError` with a specific message; the
   existing `claimListing` server action already routes that to
   `?notice=claimfail`, whose banner text now spells out the
   day + city + host-or-co-host requirement.
6. Only then `markClaimed(...)` and `save(...)`.

Why same-day + same-city instead of something stricter (sport,
distance-of-N-miles)? Listings are sourced from external sites with
fuzzy address strings, and tournament titles rarely line up
word-for-word with the host's PickupVB event title. Day + city is
strict enough that a random Atlanta host can't claim a Boston
listing, and loose enough that "starts 6pm Pacific" vs "starts 7pm
Pacific" on the same Saturday in the same city won't trip an
honest claim.

### 3. DB-layer belt-and-suspenders

New migration adds a partial unique index:

```sql
create unique index community_listings_claimed_event_id_unique
    on public.community_listings (claimed_event_id)
    where claimed_event_id is not null;
```

Even if the application check has a bug, the same PickupVB event id
can back at most one `claimed_event_id` row. Partial index so the
non-claimed listings (the common case) don't collide on `null`.

## Changes

- `supabase/migrations/20260612000000_community_listings_unique_claimed_event.sql`
  — new file. Partial unique index. Preamble follows the convention
  in [AGENTS.md](../../AGENTS.md).
- `packages/application/src/commands/community-listing.handler.ts` —
  replaced `isHostOfEvent` dependency with `loadEventClaimFacts`,
  added `matchesByDateAndCity()` + `sameCalendarDayInZone()` private
  helpers, threw `ConflictError` on match failure.
- `apps/web/src/lib/handlers.ts` — removed the old
  `isHostOfEvent` helper, added a new `loadEventClaimFacts` that
  parallel-loads `events` (host_id / starts_at / city / time_zone) and
  `event_co_hosts` (host_user_id, filtering out null group-only
  rows), and wired it into the handler construction.
- `apps/web/src/app/community/[slug]/page.tsx` —
  - Added a `formatDayKey()` helper that mirrors the application-
    layer day-key format.
  - Derived `eligibleEvents` from `claimableEvents`, applying the
    same day + city filter the server uses.
  - Dropdown now renders `eligibleEvents` and the helper copy says
    "Only your events on the same day and in the same city as this
    listing are shown."
  - Empty-state copy branches on `claimableEvents.length === 0` vs
    "you have events but none match".
  - `claimfail` banner copy now explains the rule.

## Follow-ups

- **Unit test for `ClaimCommunityListingHandler`.** The handler
  changed shape but still has no test coverage. Worth adding tests
  for: happy path (host matches, day matches, city matches), wrong
  host (UnauthorizedError), missing event (NotFoundError), wrong day
  (ConflictError), wrong city (ConflictError), co-host happy path,
  null-city listing (ConflictError — fail closed).
- **Production data check.** Before this index can land in prod, run
  `select claimed_event_id, count(*) from public.community_listings
where claimed_event_id is not null group by 1 having count(*) > 1;`
  — if it returns any rows the migration will fail. CI/CD applies
  migrations automatically; if there's preexisting duplicates the
  deploy will need a backfill first.
- **Distance / sport refinement.** Same-city is a coarse proxy for
  "same metro area." If hosts complain that legitimate cross-suburb
  claims get blocked (e.g. listing says "Bellevue", PickupVB event
  says "Seattle"), revisit with a geocoded distance check or a
  city-equivalence table. Not worth doing speculatively.
