# Bundle 101 — fix PostHog "no events arriving" on prod

## Why

User report: "my posthog analytics aren't working." Symptom narrowed to
zero events arriving in the PostHog project on prod, despite
`POSTHOG_API_KEY` + `POSTHOG_DISTINCT_ID_SALT` being set in Vercel and
the composition root resolving to `PostHogAnalytics` (not the noop).

Static review found the cause in two layers:

1. **`apps/web/src/lib/analytics.ts`** — `ConsentGatedAnalytics.capture`
   was implemented as `void this.gated(...)`, a floating promise.
2. **`packages/infrastructure/src/posthog-analytics.ts`** — the underlying
   `posthog-node` client was constructed with `flushAt: 1` and no
   `waitUntil`. `posthog-node` enqueues captures and flushes via a
   background HTTP request.

On Vercel, the lambda freezes the moment the response is returned.
With both layers fire-and-forget, the consent check + capture + HTTP
flush all lose the race against freeze, every time. The audit's own
design sketch ([docs/audits/analytics.md](../audits/analytics.md), under
"Adapter responsibilities") anticipated a `finally`-block `shutdown()`
call, but no call site ever wired one. Classic serverless × queueing-SDK
pitfall — the kind that's invisible in dev (long-lived Node process,
events flush eventually) and silent in prod (no error, just missing
data).

## What changed

### 1. Adapter accepts an optional `waitUntil`

[packages/infrastructure/src/posthog-analytics.ts](../../packages/infrastructure/src/posthog-analytics.ts) —
the `PostHogAnalytics` constructor now takes a fourth optional argument,
`waitUntil?: (promise: Promise<unknown>) => void`, and forwards it to
the underlying `PostHog(...)` config. `analyticsFromEnv()` mirrors the
new parameter and passes it through. No change for callers that don't
supply one (noop on local dev, hashed-id privacy contract unchanged).

The infrastructure package stays Next-free — `waitUntil` is just a
callback shape. The framework binding lives in `apps/web/`.

### 2. Composition root wires `next/server` `after()`

[apps/web/src/lib/analytics.ts](../../apps/web/src/lib/analytics.ts) —
introduces a `safeAfter(promise)` helper that calls `after(promise)`
inside a `try`/`catch`. The catch keeps cron/test/background callers
working: those run outside a request scope where `after()` would
throw "No request context," and they're presumed to live on a
long-lived host where a floating promise is acceptable.

Two consumers:

- `analyticsFromEnv(safeAfter)` — `posthog-node`'s built-in
  `waitUntil`-debounced flush is now extended via Next so the lambda
  stays alive long enough for the HTTP POST to land.
- `ConsentGatedAnalytics.capture` / `identify` — the gated chain
  (`await hasAnalyticsConsent()` then `inner.capture(...)`) is itself
  wrapped in `safeAfter`. Without this, the consent check resolves
  _after_ the response is sent and the inner `client.capture()` never
  fires.

The stale "Why fire-and-forget" doc comment was rewritten to explain
the `after()` mechanism.

## Verify

```
pnpm typecheck && pnpm lint && pnpm test && pnpm build
```

All green.

## Follow-ups

- No automated regression for the `after()` wiring — a missing
  `safeAfter` would silently re-introduce the bug. Adding a unit test
  that spies on `next/server`'s `after` from
  `ConsentGatedAnalytics.capture` would catch a future regression.
  Tracked in [docs/audits/analytics.md](../audits/analytics.md) status
  update.
- Web vitals (`/api/web-vitals`) also calls `analytics.capture` — it
  now benefits from the same fix automatically, since it goes through
  the shared `ConsentGatedAnalytics` instance.
- Stripe webhooks: the consent gate's "no request scope" fallback was
  already documented; the `after()` wrapper preserves the same
  fall-through behaviour for webhook callers (their cookie absence
  still results in `granted` under the US-first default).
