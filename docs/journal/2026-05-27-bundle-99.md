# Bundle 99 — invite-only / private events (P1 #1 closeout)

## Why

[Monetization audit](../audits/monetization.md) P1 #1 had one open
sub-item after Bundle 98:

> 4. **Invite-only / private event** — flag on event; doesn't
>    appear in `/events` listing; accessible only via direct link
>    or invite. Useful for league play and friend groups; pure
>    host capability. **Estimate: half a bundle.**

The pricing page ([apps/web/src/app/pricing/page.tsx#L45](../../apps/web/src/app/pricing/page.tsx#L45),
[L227](../../apps/web/src/app/pricing/page.tsx#L227)) already
advertised "Invite-only / private events" as a Pro perk, but the
feature was not actually wired:

- The `visibility` enum on `events` already had `invite_only`,
  `friends_of_host`, `friends_of_attendees` (from
  [supabase/migrations/20260512000000_init.sql#L23](../../supabase/migrations/20260512000000_init.sql#L23)).
- The new-event and edit-event forms already exposed all four
  options in their `<select>` — with no Pro gating.
- The server actions wrote whatever the form submitted, again
  with no gating.
- The `events_select` RLS policy made `invite_only` **unreachable
  to non-hosts**. The original init.sql comment flagged this:
  `-- invite_only requires explicit invite (not modeled yet)`.
  So a Pro-gated UI alone wouldn't have shipped a working feature
  — the read path was a dead end.

This bundle closes both gaps in one shot.

## What changed

### 1. RLS — make `invite_only` readable by anyone with the URL

New migration
[supabase/migrations/20260702000000_invite_only_events_readable_by_link.sql](../../supabase/migrations/20260702000000_invite_only_events_readable_by_link.sql)
drops and recreates `events_select` to add one branch:

```sql
or visibility = 'invite_only'
```

This is the "YouTube unlisted" model — the canonical
`/events/[id]` URL is reachable to anon and signed-in viewers,
but the event is excluded from every discovery surface because
those already filter `visibility = 'public'` at the query / view
layer:

- `/events` listing relies on RLS (auto-excluded for non-hosts).
- [apps/web/src/app/sitemap.ts#L38](../../apps/web/src/app/sitemap.ts#L38)
  hard-codes `.eq('visibility', 'public')`.
- The `public_numbers_views` views
  ([supabase/migrations/20260615000000_public_numbers_views.sql](../../supabase/migrations/20260615000000_public_numbers_views.sql))
  filter the same way.
- The `groups_and_co_hosts` policy stack (groups list / search)
  inherits the same filter.

**Discovery leak audit (follow-up).** Spot-checking after the RLS
change above, two surfaces were still `security invoker` /
direct-table queries that would now leak `invite_only` rows now
that RLS allows anon SELECT. Both were patched:

- New migration
  [supabase/migrations/20260702000100_search_events_filter_visibility_public.sql](../../supabase/migrations/20260702000100_search_events_filter_visibility_public.sql)
  recreates the `public.search_events` RPC (used by the `/events`
  map/list page) with `and e.visibility = 'public'` added to its
  where clause. The body mirrors the latest definition from
  [supabase/migrations/20260605000800_search_events_division_aware_chips.sql](../../supabase/migrations/20260605000800_search_events_division_aware_chips.sql)
  (post-`format`-column-drop). No signature change.
- [packages/infrastructure/src/supabase-event-repository.ts](../../packages/infrastructure/src/supabase-event-repository.ts)
  `searchFollowingFeed` (the friends feed) now adds
  `.eq('visibility', 'public')` to its events query — the feed
  is intentionally a discovery surface, not an invite surface.

The `friends_of_host` and `friends_of_attendees` branches are
unchanged — they already required an explicit friendship /
membership relation.

The "or invite" half of the audit's wording ("direct link or
invite") is deferred. A per-user `event_invites` table with
shareable tokens is a future enhancement; the link-only model
covers the common league / friend-group case shipped today.

### 2. Server-side Pro gating

New helper [apps/web/src/lib/visibility.ts](../../apps/web/src/lib/visibility.ts)
exports `clampVisibilityForHost(submitted, hostHasProBenefits)`.
The clamp is the **security boundary** — a Free host POSTing
`invite_only` via curl gets `public` back.

Wired in:

- [apps/web/src/app/events/new/actions.ts](../../apps/web/src/app/events/new/actions.ts)
  — checks `hasProBenefits(user.id)` (the creator is the host).
- [apps/web/src/app/events/[id]/edit/actions.ts](../../apps/web/src/app/events/%5Bid%5D/edit/actions.ts)
  — checks `hasProBenefits(detail.hostUserId ?? user.id)` so a
  Pro co-host editing a Free host's event can't promote it to
  invite-only. Group-only hosted events (no user host) fall back
  to the editor's entitlement.

Unit tests in [apps/web/src/lib/visibility.test.ts](../../apps/web/src/lib/visibility.test.ts)
cover the truth table (6 cases): empty / unknown → public,
public passes through, gated values clamp for Free + pass for Pro.

### 3. UI gating

Both forms now disable the `<select>` and pin it to `public` for
Free hosts, with a "(Pro)" suffix on the label and a one-line
Upgrade nudge linking to `/pricing`. Mirrors the
`RefundWindowField` pattern from Bundle 98.

- [apps/web/src/app/events/new/new-event-form.tsx](../../apps/web/src/app/events/new/new-event-form.tsx)
  — section 5 ("Visibility & advanced details"). Also updated the
  `invite_only` option label to "Invite only (unlisted — share by
  link)" so Pro hosts see what they're actually buying.
- [apps/web/src/app/events/[id]/edit/edit-event-form.tsx](../../apps/web/src/app/events/%5Bid%5D/edit/edit-event-form.tsx)
  — same treatment in the "Visibility" field of the basics
  fieldset.

### 4. Pricing page

No changes needed.
[apps/web/src/app/pricing/page.tsx](../../apps/web/src/app/pricing/page.tsx)
already lists "Invite-only / private events" in `PRO_TIER_FEATURES`
and in the side-by-side comparison table — that copy now matches
shipped behavior instead of being aspirational.

## Follow-ups deferred

- **Per-user invite tokens.** If feedback shows hosts want
  named invites (rather than a shareable link), add an
  `event_invites` table with token + optional `email` + optional
  `user_id`, and tighten the RLS branch from `visibility =
'invite_only'` to `... and (token in url matches OR auth.uid()
is in event_invites)`. Out of scope here.
- **OG image / unfurl for invite_only.** The OG image endpoint
  follows the same RLS read path, so a shared invite_only link
  unfurls fine in chat clients (anon read works). Verified by
  the RLS branch above; no code change needed in this bundle.
- **E2E spec.** Shipped:
  [apps/web/tests/e2e/visibility-gating.authed.spec.ts](../../apps/web/tests/e2e/visibility-gating.authed.spec.ts)
  mirrors the Bundle 98 `refund-window-gating.authed.spec.ts`
  pattern — Free host sees the visibility `<select>` disabled and
  pinned to `public` with the Pro nudge; Pro host can pick
  `invite_only`. Each test creates and cancels its own disposable
  open-play event. The "anon can load canonical URL but it 404s
  from `/events`" half is left for a future spec — anon-only
  flows aren't covered by existing storage states.
- **`PROVISIONED_VISIBILITY` / single source of truth.** The
  enum values are repeated in three places (DB enum, Zod schema
  in `packages/types`, the new `apps/web/src/lib/visibility.ts`
  helper). They agree today but only by inspection. A future
  cleanup could derive the helper's `ALLOWED_VISIBILITIES` from
  the domain `Visibility` enum directly.

## What this closes

- **P1 #1 sub-item #4** — invite-only / private events — shipped.
- **P1 #1 overall** — fully shipped. Sub-items #1 (templates,
  Bundle 86), #2 (analytics, Bundle 87), #3 (custom refund
  policy, Bundle 98), #4 (invite-only, this bundle). #5
  (co-host gating) was explicitly dropped 2026-05-24.
- Pro is now a complete feature product end-to-end. The pricing
  page no longer advertises any aspirational perk.
