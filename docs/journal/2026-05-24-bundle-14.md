# 2026-05-24 — Bundle 14: admin-client refactor (security P2 #4)

## Context

After Bundle 13a closed out three of the four performance listings, we
pivoted to the security audit. P2 #4 was the highest-impact open item
that didn't require external infra decisions (CSP needs an allowlist
inventory + report-only window; rate limiting needs a KV backend
decision). It also reads exactly like the cookbook calls for: server
actions reaching for the admin client to perform writes on behalf of the
authenticated caller, instead of going through RLS.

Three call sites:

- [checkout-actions.ts](../../apps/web/src/app/events/[id]/checkout-actions.ts)
  — admin INSERT into `event_attendees` to reserve a pending ticket
  spot, admin UPDATE to stash `checkout_session_id`, admin DELETE to
  roll back if Stripe session creation fails.
- [tip-actions.ts](../../apps/web/src/app/events/[id]/tip-actions.ts) —
  same shape for `event_tips`: admin INSERT, admin UPDATE, admin DELETE.
- [manage-payments-actions.ts](../../apps/web/src/app/events/[id]/manage-payments-actions.ts)
  — admin UPDATE on `event_attendees` for the host's manual
  mark-as-paid / mark-as-unpaid flow, plus admin INSERT into
  `event_payment_audit`.

The audit's prescription was "prefer `getServerSupabase()` (RLS-enforced)
for any write where the caller is the resource owner; reserve
`getAdminSupabase()` for webhook handlers, crons, and explicit admin
tooling." This bundle does exactly that.

## What shipped

### 1. New migration

[supabase/migrations/20260609000000_self_writes_attendees_tips.sql](../../supabase/migrations/20260609000000_self_writes_attendees_tips.sql)
adds:

- `event_attendees_update_own_pending` — caller can update their own
  row iff it's currently `payment_status = 'pending'` AND stays
  `'pending'`. This unlocks the `checkout_session_id` stash without
  letting a user self-promote to `'paid'`.
- `event_attendees_update_host` — host / co-host (via the existing
  `is_event_host()` security-definer helper from 20260514000400) can update any attendee row for events they host.
- `event_tips_select_own` — tipper can read their own pending row
  (needed for the `.insert(...).select('id').single()` round-trip on
  the pending insert).
- `event_tips_insert_own` — `auth.uid() = tipper_user_id` AND
  `status = 'pending'` AND `amount_cents > 0`.
- `event_tips_update_own_pending` — own row, pending → pending only.
- `event_tips_delete_own_pending` — own row, pending only (used by the
  rollback path).
- `event_payment_audit_insert_host` — host writes audit rows for events
  they host.

The webhook handlers continue to use the admin client because they run
with no user session and need to flip rows to `paid` / `refunded` — RLS
would (correctly) deny them as anonymous.

### 2. `checkout-actions.ts`

All four DB calls (insert pending, select existing on 23505, delete
rollback, stash session id) now run on `supabase` (the same handle
already used for `auth.getUser()`). Removed the `getAdminSupabase`
import.

### 3. `tip-actions.ts`

`loadEvent()` was previously creating its own admin client just to read
an event row; refactored to take the existing server client as a
parameter. Pending insert / session-id stash / rollback delete all run
under RLS. Removed the `getAdminSupabase` import.

### 4. `manage-payments-actions.ts`

Both the attendee `UPDATE` and the audit `INSERT` now run on the server
client. The existing `canManage` check (via `GetEventDetailQuery`) is
kept as a fast-path early return + belt-and-suspenders — if that ever
regresses, RLS still blocks cross-event writes because
`is_event_host()` evaluates against the actual caller.

## Decisions

- **Why the "stays pending" RLS shape.** The bare "own row" UPDATE
  would let a user self-promote to `payment_status = 'paid'`. PostgreSQL
  doesn't support column-level RLS directly, so the trick is to write
  both `USING` (old row) and `WITH CHECK` (new row) requiring
  `payment_status = 'pending'`. Result: the stash-session-id update
  works because it doesn't touch `payment_status`; an attempted
  promote-to-paid is denied because the new row would no longer match
  `WITH CHECK`.

- **Why reuse `is_event_host()` instead of writing a fresh subquery.**
  That helper already encodes host / event-co-host (user) /
  event-co-host (group admin) — exactly the same set of identities
  that `canManage` captures in the read model. Drift-free.

- **Why keep `canManage` check at all.** It's a fast `return` before
  the DB round-trip, and it lets the action surface a friendlier
  no-op for the rare regression-or-edit-during-race case. RLS would
  still block the write, but the user would see a generic error
  instead of a silent no-op.

- **Why not also wrap admin in an audited helper.** Admin is now
  only reached by Stripe webhook handlers, which already log the
  event id and have a dedicated `stripe_webhook_events` dedup table.
  No code path needs the "admin with re-checked auth" wrapper
  anymore.

## Patterns observed

- **"Own pending row" RLS** as the standard shape for any user-driven
  payment flow where a row is created in `pending`, mutated by the
  user a few times during checkout, then promoted by a webhook. The
  `USING + WITH CHECK = pending` pattern is the cleanest way to allow
  user mutation pre-payment but deny post-payment writes.
- **`is_event_host()` for host-write policies.** Defining the helper
  once as a `security definer` SQL function and reusing it in
  multiple policies keeps host / co-host / group-admin-co-host logic
  in one place.
- **Pass the supabase handle into helpers.** `loadEvent` minting its
  own admin client was the original sin here — once helpers
  encapsulate "their own" client, the principle of least privilege
  silently erodes.
