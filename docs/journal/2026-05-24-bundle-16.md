# 2026-05-24 — Bundle 16: rate limiting on email-sending paths (security P2 #6)

## Context

P2 #6 in [docs/audits/security.md](../audits/security.md#6-no-rate-limiting-on-email-sending-paths)
called out four files: the cron-driven notifications worker plus three
user-facing server actions that hand off to Supabase Auth's
`updateUser({ email })`, which in turn fires a confirmation email. The
worker has its own `CRON_SECRET` gate and is not user-triggerable, so
it's not part of the abuse vector here. The three actions can be
replayed by a bot to mail-bomb a target whose address the attacker
already knows (or harvests from a public roster).

The audit suggested Vercel KV or Upstash for shared limiter state. The
open question called out by the audit ("Existing KV store available, or
do we provision Vercel KV / Upstash for rate-limit state?") was still
unanswered.

## Decisions

### 1. Postgres, not KV

We backed the limiter with a Postgres table + `security definer` SQL
function rather than provisioning a new KV service:

- Supabase is already in the critical path for every server action.
  Adding a write to the same DB the request just talked to costs ~one
  round trip; provisioning a brand-new infra dependency would have
  taken longer and added a failure surface for relatively little win
  at our current traffic.
- Atomicity is free in Postgres. `insert … on conflict do update`
  takes a row-level lock; concurrent callers can't race past the limit.
  KV-based limiters usually need a Lua script or a sliding-window log
  to get the same guarantee.
- The data shape is tiny — one row per active key, naturally
  overwritten on each hit. Even at 1 row/sec sustained that's
  &lt;100KB/day of churn.
- Migrating later is cheap: the public surface is `consumeRateLimit()`
  in [apps/web/src/lib/rate-limit.ts](../../apps/web/src/lib/rate-limit.ts).
  Swapping its body to use Upstash leaves every call site untouched.

### 2. Fixed window, not sliding window

A sliding window is more accurate but needs either a sorted log of
timestamps (more storage) or token-bucket math (more code). For the
abuse model we care about — "did an attacker just send 50 emails in
the last hour" — a fixed window with a 1-hour reset is enough. The
worst-case slip is one window boundary's worth of bursts, which still
caps email volume at 2× the limit per attacker IP.

### 3. Fail-open on infra error

If `consume_rate_limit()` errors (network blip, Supabase down) we let
the request through and log a `warn` to Sentry. The alternative —
locking everyone out on infra failure — is strictly worse for UX and
doesn't help the abuse case any more than catching it 99% of the time
already does.

### 4. Two keys per surface: IP and email

We consume both buckets in parallel:

- **IP bucket** (`{scope}:ip:{ip}`, limit 20/h) — caps one attacker
  blasting many targets.
- **Email bucket** (`{scope}:email:{email}`, limit 5/h) — caps many
  attackers (or one with rotating IPs) blasting one target.

A request is blocked iff _either_ bucket is full. The blocked bucket's
`retry_after_seconds` is surfaced in the user-facing error string.

### 5. Worker route intentionally skipped

[apps/web/src/app/api/notifications/worker/route.ts](../../apps/web/src/app/api/notifications/worker/route.ts)
is invoked by a Vercel Cron and gated by a `CRON_SECRET` header check.
There's no user-driven trigger surface and per-IP / per-email keys
would be meaningless (the cron's IP rotates by region and there's no
email field on the request). Documented as ⏭ in the audit's remediation
log row.

## What shipped

### Database

[supabase/migrations/20260610000000_rate_limits.sql](../../supabase/migrations/20260610000000_rate_limits.sql):

```sql
create table public.rate_limits (
  key          text primary key,
  count        integer not null,
  window_start timestamptz not null default now()
);
alter table public.rate_limits enable row level security;
-- no policies — only consume_rate_limit() writes (security definer)
```

The `consume_rate_limit(p_key, p_limit, p_window_seconds)` function
returns `(allowed boolean, retry_after_seconds integer)`. It runs as
the function owner (`security definer`), so the table can stay
RLS-locked and the limiter still works for anon callers. Execute
grant is restricted to `service_role`.

### Application

[apps/web/src/lib/rate-limit.ts](../../apps/web/src/lib/rate-limit.ts)
is the only module that knows about the table:

```ts
export interface RateLimitOptions {
  key: string;
  limit: number;
  windowSeconds: number;
}
export async function consumeRateLimit(opts: RateLimitOptions): Promise<RateLimitResult>;
export async function getClientIp(): Promise<string>;
```

`getClientIp()` reads `x-forwarded-for` first (Vercel sets the
comma-separated chain; we take the first hop) with `x-real-ip` as a
fallback and an `'unknown'` sentinel as last resort. The sentinel keeps
the limiter key stable across requests without a resolvable address
rather than degrading to "no limit at all for those callers."

### Type-cast caveat

The new `consume_rate_limit` function isn't in the generated
`packages/supabase/src/database.types.ts` yet (the migration hasn't
run anywhere). To keep the verify quad green pre-regen, the helper
casts the rpc handle once:

```ts
const rpc = admin.rpc as unknown as (
  fn: 'consume_rate_limit',
  args: RpcArgs,
) => Promise<{ data: RpcRow[] | RpcRow | null; error: { message: string } | null }>;
```

The cast goes away after `pnpm --filter @pickupvb/supabase gen:types`
runs against a DB with the migration applied. A TODO comment is in
place in the helper.

## Verification

`pnpm typecheck && pnpm lint && pnpm test && pnpm build` — all green.
No runtime test fixtures exist for the rate-limit RPC (no Supabase
local DB harness in CI), so this bundle is "compile + behavioral
review" rather than "covered by an integration test."

## Follow-ups deferred

- **Type regen.** Run `pnpm --filter @pickupvb/supabase gen:types`
  after applying the migration locally; drop the cast.
- **Prune cron.** A nightly
  `delete from public.rate_limits where window_start < now() - interval '1 day'`
  would keep the table tidy. Not scheduled yet — volume is tiny and
  rows naturally collapse on next hit.
- **KV migration.** If write contention on `rate_limits` ever shows
  up (very unlikely at current traffic), swap the helper body to
  Upstash Redis behind the same `consumeRateLimit()` signature.
- **Per-email key normalization.** We lowercase the email at the call
  site in checkout-actions / guest-actions and pass it straight into
  the key. If we ever start accepting punycode / unicode addresses we
  may want a stricter canonicalization step.
- **Integration test.** A Supabase local DB + test that exercises the
  function under contention would be valuable; deferred until we add a
  general DB-integration harness.
