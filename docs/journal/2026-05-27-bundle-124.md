# Bundle 124 — Pool play: courts + parallel-slot solver (Phase 3 of ADR 0018) (2026-05-27)

## Context

Bundles 122 (Phase 1) and 123 (Phase 2) shipped match-length, schedule
density, and the work / ref team for [ADR 0018](../adr/0018-pool-play-configuration.md).
Phase 3 closes the original ask: hosts running a same-day tournament
on multiple courts need each match tagged with **which court** it plays
on and **which time slot** it shares with other matches running in
parallel — and the schedule must never ask a team to play and ref on
different courts at the same time.

The ADR records the design as greedy graph coloring over a conflict
graph (two matches are adjacent if they share `teamAId`, `teamBId`, or
`workTeamId`). This bundle implements that solver and wires it through
to the format-picker UI.

## Decision

- **`BracketConfig.courtLabels: ReadonlyArray<string>`** (default `[]`).
  Free text, chosen by the host (e.g. `['Court 1', 'Court 2', 'North
gym']`). Stored on the existing `tournament_brackets.config` JSON
  column — no schema change there.
- **`Match` gains `court: string | null` and `slot: number | null`.**
  1-indexed slot; null when `courtLabels` is empty. Free text on court
  rather than a structured `courts` table, per ADR — labels exist only
  to disambiguate parallel matches in the UI, and there's no other
  feature that would join to a courts table. New nullable columns on
  `bracket_matches` ([supabase/migrations/20260714000000_bracket_match_court_slot.sql](../../supabase/migrations/20260714000000_bracket_match_court_slot.sql)).
- **`assignCourtsAndSlots(matches, courtLabels)`** (exported from
  [packages/domain/src/brackets/generators.ts](../../packages/domain/src/brackets/generators.ts)).
  Greedy graph coloring with court-count capacity per color class:
  - For each match (in generator output order), pick the lowest-numbered
    existing slot that (a) has spare court capacity and (b) shares no
    team with any match already in that slot.
  - If no slot fits, append a new one. **Slots are unbounded** — slots
    are time, courts are space. The ADR's mention of an
    `InvariantViolation` "can't fit in N courts" case turned out to be
    unreachable with greedy + auto-extend: you always succeed by
    adding another slot. Left a note in the journal so the next
    reader doesn't go looking for a failure path that doesn't exist.
  - Court within a slot is fill-order: the Nth match placed in a slot
    takes `courtLabels[N]`.
- **`generatePoolPlay` accepts `courtLabels?: ReadonlyArray<string>`**
  and runs the solver as a post-pass _after_ work-team assignment,
  so `workTeamId` is part of the conflict graph (a team currently
  reffing match X can't also play in match Y in the same slot).
- **Format picker grows one text input** inside the existing pool-play
  fieldset: _"Courts (comma-separated, optional)"_ with placeholder
  `Court 1, Court 2, North gym`. `createBracketFromForm` splits on
  commas, trims, drops empties, and sets `config.courtLabels` when
  the resulting list is non-empty.
- **Match card shows `Court A · Slot 2`** under the match number when
  either field is set.

## Rejected alternatives

- **InvariantViolation when no fit exists.** The ADR floated it; in
  practice greedy + unbounded slot count never fails. A cap (e.g.
  "max 16 slots") would only catch pathological inputs and would
  surprise hosts running long tournaments. Left out.
- **Interleaving pool rounds before solving.** The current per-pool
  emission order means pool A's matches fill slots 1..K first, then
  pool B reuses slot 1 (disjoint teams, no conflict). The result is
  fine for realistic inputs; smarter ordering can land in Phase 3b
  if hosts report tight schedules.
- **Structured `courts` table.** Rejected by ADR; sticking with free
  text on `bracket_matches.court` and `courtLabels` in JSON config.
- **Slot assignment for double-elim / single-elim playoff matches.**
  Out of scope. The solver runs only on the pool-play generator path
  because that's where parallel-court conflicts realistically arise.
  Playoff matches typically run sequentially.

## Patterns surfaced

- **Solver as post-pass keyed by previously-stamped fields.** Phase 2
  introduced "stamp `workTeamId` after the round-robin emits matches";
  Phase 3 reuses the same shape — work-team must be stamped first so
  the slot solver sees the full conflict set. Order matters and is
  enforced by the linear sequence inside `generatePoolPlay`.
- **Free-text labels feeding a `<select>` rather than per-row text.**
  ADR called this out for typo resistance. The match-card edit UI
  hasn't been built yet, but when it lands the dropdown should be
  populated from `bracket.config.courtLabels` so a typo can't conjure
  a phantom court.
- **Unbounded slot count as a feature.** The temptation was to cap
  slots at some "reasonable" number; the right call was to let the
  schedule grow. Hosts who want fewer slots can add courts (Phase 3b
  reorder will let them squeeze further).

## Follow-ups deferred

- **Phase 1b (UI reorder).** Drag-and-drop within a pool's match list,
  re-running `assignCourtsAndSlots` after each reorder to update slot
  numbers without regenerating opponents.
- **Phase 2b (manual work-team override).** Single match's work team
  swap. The solver will need to re-run on that match's slot if the
  new work team conflicts with the rest of the slot.
- **Per-match court edit.** A `<select>` on the match card populated
  from `bracket.config.courtLabels` so a host can move a single match
  to a different court within its slot.
- **Regenerate Supabase types** (`pnpm db:migrate` + `pnpm --filter
@pickupvb/supabase gen:types`) once local Postgres is running, then
  remove the `as unknown as MatchRow[]` workaround in
  [supabase-bracket-repository.ts](../../packages/infrastructure/src/supabase-bracket-repository.ts).
- **Smarter slot ordering for tight schedules.** Current greedy emits
  matches per-pool; interleaving rounds across pools may reduce total
  slot count for some inputs.
