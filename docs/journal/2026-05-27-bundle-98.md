# Bundle 98 — monetization P1/P2 closeout: refund-policy gating, trial-funnel analytics, ADR

## Why

The [monetization audit](../audits/monetization.md) had three
remaining un-shipped items from its "What I'd ship in what order"
sequence after Bundle 87:

1. **Custom refund policy gating** (P1 #1 sub-item #3) — half a
   bundle to gate `refund_window_hours` behind Pro so Free hosts
   take the 24h default and Pro hosts can configure 0–720h.
2. **Trial-to-paid funnel capture** (P2 #5) — half a bundle to
   instrument `pro_trial_started` / `pro_trial_converted` so we
   can measure the funnel that ADR 0014 will set targets against.
3. **Monetization strategy ADR** (P1 #3) — half a bundle to write
   down _why_ $10 / 50% / 1-event/30d, so the lever isn't churned
   on a bad week.

User asked: "let's start implementing the first three and document
them." This bundle ships all three together — they're co-dependent
(the ADR cites the analytics events; the analytics events back the
ADR's success criteria; the refund gating is the last P1 #1
sub-item the ADR can call "complete enough to justify $10/mo").

## What changed

### 1. Custom refund policy gating (P1 #1 sub-item #3)

Server-side entitlement boundary lives in
[apps/web/src/lib/money.ts](../../apps/web/src/lib/money.ts):
`parseRefundWindowHours` now takes an optional
`{ allowCustom?: boolean }`. When `allowCustom: false`, it ignores
the input and returns `DEFAULT_REFUND_WINDOW_HOURS` (24) regardless
of what the form submitted. **This is the security boundary.** UI
gating is a UX nicety; a malicious actor POSTing `720` as a Free
host gets clamped to 24 here.

Wired into both action paths:

- [apps/web/src/app/events/new/actions.ts](../../apps/web/src/app/events/new/actions.ts)
  — `await hasProBenefits(user.id)` passed in.
- [apps/web/src/app/events/[id]/edit/actions.ts](../../apps/web/src/app/events/%5Bid%5D/edit/actions.ts)
  — same. (Note: this checks the _editing viewer's_ Pro status, not
  the original host's. In practice the viewer is always the host or
  a platform admin; co-hosts can't reach this surface. Documented
  as a follow-up below.)

UI gating:

- [apps/web/src/app/events/new/new-event-form.tsx](../../apps/web/src/app/events/new/new-event-form.tsx)
  — extracted a shared `RefundWindowField` helper that renders an
  editable 0–720 input for Pro hosts and a disabled "24" input
  with an "(Pro)" label hint + Upgrade nudge for Free hosts.
- [apps/web/src/app/events/[id]/edit/edit-event-form.tsx](../../apps/web/src/app/events/%5Bid%5D/edit/edit-event-form.tsx)
  — same helper, used in both the open-play and tournament
  branches. `viewerHasProBenefits` is now a required prop, threaded
  from [apps/web/src/app/events/[id]/edit/page.tsx](../../apps/web/src/app/events/%5Bid%5D/edit/page.tsx)
  (which was already computing the value).

Test added in
[apps/web/src/lib/money.test.ts](../../apps/web/src/lib/money.test.ts):
`allowCustom: false` clamps every input back to the default,
including the previously-valid `'72'` and `'720'`.

### 2. Trial-to-paid funnel analytics (P2 #5)

Two new variants on the `AnalyticsEvent` discriminated union in
[packages/domain/src/shared/analytics-port.ts](../../packages/domain/src/shared/analytics-port.ts):

- `pro_trial_started` — `{ hostId, plan, trialEnd }`.
- `pro_trial_converted` — `{ hostId, plan }`.

Fired from `handleSubscriptionChange` in
[apps/web/src/app/api/webhooks/stripe/route.ts](../../apps/web/src/app/api/webhooks/stripe/route.ts).
The dispatch case now forwards both `event.type` and
`event.data.previous_attributes` so the handler can detect the
trialing → active transition (the canonical successful conversion):

- `customer.subscription.created` + `status === 'trialing'` →
  `pro_trial_started`.
- `customer.subscription.updated` +
  `previous_attributes.status === 'trialing'` + new
  `status === 'active'` → `pro_trial_converted`.

Capture runs **after** the DB upsert so PostHog and `host_subscriptions`
stay consistent. The PostHog adapter swallows failures, so analytics
can't block a webhook ack — consistent with the
[fail-open contract](../../packages/domain/src/shared/analytics-port.ts)
on the port interface.

### 3. ADR 0014 — Monetization strategy

New ADR at
[docs/adr/0014-monetization-strategy.md](../adr/0014-monetization-strategy.md)
documenting the four-knob position:

| Knob          | Value              | Why                                                             |
| ------------- | ------------------ | --------------------------------------------------------------- |
| Pro price     | $10/mo, $100/yr    | Below noise floor of one paid ticket; under Meetup's $24 anchor |
| Fee discount  | 50% (5% → 2.5%)    | Visible at small GMV without zero-cliff; still clears infra     |
| Free-tier cap | 1 paid event / 30d | Tastes the platform; second event = upgrade trigger             |
| Trial         | 14d, card required | Mechanical convert; clean Stripe Billing transition             |

Plus four success metrics with explicit "revisit when" triggers, and
a list of rejected alternatives ($5 unlimited, $15 with co-host
takeaway, flat per-event fee, no-card trial, per-metro tiering) so
future-us doesn't relitigate them in a panic.

## Lessons / patterns observed

- **Entitlement gates belong at the server boundary, not the UI.**
  `parseRefundWindowHours({ allowCustom: false })` is a one-line
  clamp at the parser; UI just won't render the wider range. The
  parser is the source of truth — UI is decoration. Same pattern
  the sponsor a-la-carte flow uses (Bundle 85).
- **Co-dependent doc + code bundles.** The ADR _had_ to be in this
  bundle because the success metrics table cites the analytics
  events. Splitting it into a follow-up would leave the ADR
  half-true. Bundling docs with code is fine; pretending docs are
  separate is what creates ADR rot.
- **Stripe `previous_attributes` is per-event.** It's only present
  on `customer.subscription.updated`, not `.created` or `.deleted`.
  Typing it as `Partial<Stripe.Subscription> | undefined` and
  guarding before access keeps the trialing→active branch honest.

## Follow-ups deferred

- **Edit form uses _viewer's_ Pro status, not _host's_.** Today the
  edit surface is reachable only by the host (no co-host edit page
  ships yet), so viewer == host in practice. If we add co-host
  editing, the refund-window gate should check the host's
  entitlement, not the editor's, otherwise a Free co-host could
  preserve a host's existing Pro-set custom value. Tracked in
  `/memories/repo/followups.md`.
- **Backfill `pro_trial_started` for existing trialing subs.**
  Anyone who started a trial before this bundle won't have a
  `pro_trial_started` event captured. Acceptable pre-launch (active
  trials count is ~0). Post-launch we'd want a one-time backfill
  reading the Stripe API.
- **PostHog funnel UI.** The events are now flowing; building the
  funnel widget on the PostHog dashboard side is a manual config,
  not a code task. Note for the launch checklist.
- **Invite-only / private events** is the last P1 #1 sub-item.
  Half-bundle estimate per the audit; can ship anytime.
