# Bundle 120 — Walk-in team registrations (ADR 0017) (2026-05-27)

## Context

Bundle 117 (registration-workflow re-audit) logged six findings. Bundles
118–119 closed R1 / R2 / R3 / R6, leaving **R4 (P3)** as the last open
item: walk-in team registrations. The pain point is concrete and
recurring at indoor tournaments — a captain shows up the day of the
event with a roster that never pre-registered. Today the host has two
bad options:

- Create a fake account on the captain's behalf so they can run the
  existing ad-hoc signup flow (pollutes `profiles`, plus the captain
  never signs in to that account again).
- Skip the platform entirely, take cash, and never get the team into
  the bracket.

R4 was tagged P3 in the audit because the workaround existed; the user
called it in this bundle to close the registration-workflow audit and
unblock day-of operations.

## Decisions

Four product decisions were locked at the start of the bundle:

- **Nullable `captain_id`, freeform `captain_display_name` + `captain_phone`.**
  A walk-in has no platform account — the only identity is what the
  host typed at the score table. Allowing `captain_id = null` and
  carrying the name/phone on the registration row itself is the
  smallest change that lets a walk-in exist without a synthetic
  `profiles` row. The alternative (a placeholder "walk-in" user) is
  rejected for the same reason synthetic captains were rejected in
  Bundle 117: aliasing identity at the user table corrupts every
  downstream join.
- **Ad-hoc divisions only.** Walk-ins are conceptually identical to
  ad-hoc team registrations (no off-event team identity, lifecycle
  ends with the tournament). Forbidding them on roster divisions
  keeps ADR 0008's invariant intact (`roster` means "register an
  existing persistent `Team`") and avoids a parallel path through
  the bracket loader. Enforced in the `RegisterWalkInTeamHandler`
  against `division.teamRegistrationMode === AdHoc`.
- **Cash payment via a new `markPaidCash` domain method + `payment_note`.**
  Stripe is off the table for walk-ins by definition — no captain
  account means no Stripe customer, no card on file. Rather than
  shoehorning walk-ins through the existing
  `hostMarkTeamRegistrationPaid` (which writes `offline:host:<uuid>`
  as a sentinel `payment_intent_id`), walk-ins get their own
  state-transition method: `markPaidCash({amountCents, paidAt, note})`.
  The freeform `payment_note` column captures "Venmo from Joe",
  "envelope #14", etc. — context the host needs at the score table
  that the synthetic intent id can't carry. Cap at 500 chars.
- **RLS allows host inserts on walk-ins.** The existing
  `event_team_registrations_insert` policy only let captains sign
  themselves up. Rewriting it with two branches — captain
  self-signup OR `source ∈ {host, walk_in}` when `auth.uid() =
e.host_id` on a published ad-hoc division — keeps the policy
  shape that's already audited rather than adding a second policy.
  Belt-and-braces only since the admin client bypasses RLS, but
  it's the right shape for the day we switch to user-scoped
  clients here.

## Patterns surfaced

- **Backing `teams.captain_id` for accountless registrations.** The
  bracket reader and `events_view.team_count` both depend on
  `event_teams.team_id` → `teams` being populated. Rather than relaxing
  `teams.captain_id` (which would force every downstream consumer of
  `teams` to handle null captains), `ensureBackingTeam` uses the
  event's host as the nominal team captain when the registration
  itself has no captain. The registration row's own `captain_id`
  stays null — that's the source of truth for the public roster —
  but the backing team has a real user id so nothing downstream
  breaks. This is a useful general pattern any time we need to
  participate in an existing FK graph without a real owning user.
- **Source field as discriminant + UI pill.** A single `source`
  column lets the public roster, host panel, and analytics all
  branch on the same value rather than inferring origin from
  `captain_id IS NULL` or the `payment_intent_id` sentinel. Cheaper
  to grep and harder to get wrong than implicit signals.

  test fixture building a team-composition division has to set the
  mode explicitly.

## Follow-ups

- **Walk-in receipt path.** Cash walk-ins never hit
  `/profile/receipts` because there's no Stripe payment intent. If a
  walk-in captain later creates an account, we could thread their
  email into the registration and reconcile, but that's deliberately
  out of scope here — the audit is closed without it.
- **Phone number formatting.** `captain_phone` is freeform on
  purpose (international entries, "no phone — see in person" notes).
  If we ever want to text walk-in captains via Twilio, we'll need a
  normalize-on-write pass.
- **Walk-in attendance count.** `events_view.team_count` reflects
  walk-ins (they get a backing `event_teams` row), but the
  attendee-side counters do not — walk-in players are not in
  `event_attendees`. Acceptable for now; the host already sees
  walk-in players in the host panel's roster expand.

With R4 closed, all six Bundle 117 findings are now resolved. The
registration-workflow audit is fully remediated.
