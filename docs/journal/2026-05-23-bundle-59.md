# Bundle 59 — 2026-05-23 — TypeScript composite / project references (Organization P3, Wontfix-by-design)

## Context

The Organization audit's P3 "TypeScript packages don't use `composite`
/ project references" was filed with an unusually self-aware
remediation: _"Incremental builds would be slightly faster… Marginal
at current scale. Revisit if build times become painful."_ Six
months on, build times are still not painful — the verify quad we
just ran in Bundle 58 reported every turbo stage in single-digit
seconds on a warm cache, and clean-cache runs are well under a
minute.

Composite mode isn't free. Every package would need:

- `compilerOptions.composite: true` and `declaration: true` (forces
  `.d.ts` emission even for internal packages).
- An explicit `references` array in `tsconfig.json` listing every
  workspace dependency, kept in sync with `package.json` `dependencies`.
- `.tsbuildinfo` files added to `.gitignore` and to Turbo's
  `outputs`/inputs hashing so cache keys stay stable.
- `tsc --build` instead of `tsc --noEmit` for typecheck, which
  changes failure semantics (build mode aborts on the first failing
  project; non-build mode reports all errors).

That's ongoing maintenance for a speedup we can't currently measure.
Closure type: Wontfix-by-design with an explicit re-open trigger.

## Pattern notes

### Audit findings can ship with their own dismissal criteria

This P3 closed itself the moment the audit was written — the
"marginal at current scale" + "revisit if painful" framing is
already a Wontfix-with-trigger in everything but name. Finding that
shape in an old audit is a strong signal the right move is closure,
not implementation. Worth scanning other audits for phrases like
"only matters if", "negligible at current scale", "marginal" —
they're usually closure candidates.

### Re-open triggers should be quantitative when possible

Bundle 58's CI-Supabase closure leaned on a qualitative trigger
("if `smoke-prod.yml` stops covering real Supabase"). Bundle 59
can do better: clean-cache `pnpm build` > ~60s or `pnpm typecheck`

> ~15s sustained. Numeric thresholds give the next auditor
> something to compare against without re-running the analysis.
> Pattern to follow when a future Wontfix has a measurable signal.

### Two consecutive Wontfix-by-design closures is fine

There was a brief impulse to alternate "real implementation" and
"audit-doc" bundles. The right framing is the opposite: when the
backlog top is dominated by P3s that are genuinely fine as-is, the
correct response is a string of explicit Wontfix closures so the
backlog stops carrying them. The journal entries are the
implementation here — the durable artifact is the audit doc no
longer listing them as open.
