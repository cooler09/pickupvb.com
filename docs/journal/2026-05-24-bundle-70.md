# Bundle 70 — 2026-05-24 — Hide Pay CTAs when host can't actually collect

## Context

Host-facing follow-up to bundles 69 (ADR 0012 invariants) and the
subsequent UI cleanup that hid on-platform Stripe controls on the
event-create form when `paymentsOffPlatform` was set. The mirror image
on the public event page was still surfacing Pay buttons in two cases
where the checkout couldn't possibly succeed:

1. The event was created with `payments_off_platform = true` but the
   ad-hoc captain card still rendered a `Pay — $X` button (the roster
   `TournamentSignupPanel` and `PaidTicketPanel` already gated on the
   prop; the ad-hoc panel had been missed).
2. The host has no Stripe Connect row, or their row exists but
   `charges_enabled = false` (onboarding abandoned, account
   restricted, webhook flipped them off). In that state every payment
   action — ticket checkout, ad-hoc team checkout, roster team
   checkout — would 500 at the boundary because
   `getHostStripeAccount(hostId)` returns `null` and the actions
   throw `InvariantViolation`. The button looked clickable; the only
   feedback was an error toast.

User ask, verbatim: "Can we hide the pay action item on the event page
if the host is off platform payments or not registered with stripe?"

## Decision

One server-side derived boolean — `effectiveOffPlatform = event.paymentsOffPlatform || !hostStripeReady` —
fans out to all three Pay panels. Chose this over per-panel `await`s
because:

- The Stripe-readiness check (`getHostStripeAccount`) already lived in
  the cached loader for the tip jar — it just had a `!isHostOfEvent`
  skip clause and a tip-specific name. Generalising it is one rename +
  drop the skip.
- Computing the derived boolean inside `EventSignupArea` keeps the
  panels framework-light: they continue to take a single
  `paymentsOffPlatform` prop and don't need to know about Stripe.
- The two conditions collapse semantically — both mean "the user can't
  pay through the app, fall back to off-platform copy."

Rejected: extending the domain `VolleyballEvent` aggregate with a
`canCollectPayments` getter. Stripe readiness is infrastructure state
that lives outside the aggregate, so leaving the join at the
composition root is the right layer.

## Changes

- `apps/web/src/app/events/[id]/_loaders/load-event-detail.ts` —
  renamed `hostCanCollectTips` → `hostStripeReady` in the returned
  view-model; renamed `loadHostCanCollectTipsCached` →
  `loadHostStripeReadyCached`; dropped the `!isHostOfEvent` skip so
  the boolean is computed for the host's own event too. JSDoc updated
  to reflect the broader use.
- `apps/web/src/app/events/[id]/page.tsx` — renamed destructure;
  threads `hostStripeReady` into `EventSignupArea`; tip jar continues
  to receive the same flag under its existing prop name
  (`hostCanCollectTips`).
- `apps/web/src/app/events/[id]/_components/event-signup-area.tsx` —
  new `hostStripeReady` prop; computes
  `effectiveOffPlatform = event.paymentsOffPlatform || !hostStripeReady`
  once and passes it as `paymentsOffPlatform` to `PaidTicketPanel`,
  `TournamentSignupPanel`, and `AdHocTeamSignupPanel`.
- `apps/web/src/app/events/[id]/_components/ad-hoc-team-signup-panel.tsx` —
  added `paymentsOffPlatform?: boolean` prop (default `false`);
  forwarded into `CaptainRegistrationCard`; the Pay button now hides
  when off-platform and is replaced by a small "Pay the host $X in
  person (cash, Venmo, etc.)" line for parity with `PaidTicketPanel`.

## Patterns observed

- **One derived boolean beats N branches.** Three Pay panels, three
  Pay buttons, three checkout actions — but only one question: "can
  the app charge a card right now?" Centralising the join at the
  composition root meant the panels stayed dumb and the next payment
  surface added only has to read one prop.
- **Cached-loader fields drift.** `hostCanCollectTips` was named for
  its first consumer (the tip jar) and grew a skip clause that
  prevented reuse. Worth scanning other `loadXyzCached` helpers for
  the same pattern next time we touch the loader.
- **Stripe-readiness is composition-root concern.** Adding a
  `canCollectPayments` getter to the domain aggregate would have
  forced infrastructure into the domain layer. The right shape is to
  resolve it at the page boundary and pass a boolean.

## Follow-ups

- The three checkout actions
  ([checkout-actions.ts](../../apps/web/src/app/events/%5Bid%5D/checkout-actions.ts),
  [team-checkout-actions.ts](../../apps/web/src/app/events/%5Bid%5D/team-checkout-actions.ts),
  [roster-team-checkout-actions.ts](../../apps/web/src/app/events/%5Bid%5D/roster-team-checkout-actions.ts))
  still throw `InvariantViolation` when `getHostStripeAccount` returns
  null. With the UI gate in place that should never fire from a normal
  click — but a stale page after a host disconnects Stripe could still
  hit it. Defensive: catch the `InvariantViolation` in the action and
  flash-redirect with `?rsvp=host_not_ready` (or equivalent per
  panel). Tracked under registration-workflow audit.
- The webhook that toggles `host_stripe_accounts.charges_enabled`
  should also `revalidateTag('host-stripe:{hostId}')` so the 5-minute
  cache window doesn't leave Pay buttons visible after the host's
  account flips. Confirm the webhook handler busts the tag.
- A future affordance for hosts: a banner on their own event page
  when `hostStripeReady === false` that links to `/profile/billing`
  to finish Stripe setup. Right now the only signal is "the Pay
  button vanished."
