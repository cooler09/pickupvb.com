# 2026-05-24 — Bundle 15: CSP Report-Only (security P2 #3)

## Context

P2 #3 was last touched on 2026-05-17 when the five baseline headers
(HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`,
`Permissions-Policy`) shipped via `async headers()` in
[apps/web/next.config.mjs](../../apps/web/next.config.mjs). The CSP
piece was held back because it needed an allowlist inventory across
every third party and a Report-Only window before enforcement.

This bundle does the inventory pass and ships CSP as
`Content-Security-Policy-Report-Only`. Enforcement (renaming the header
to `Content-Security-Policy`) is tracked as P2 #3a and deferred until
after a clean soak.

## What shipped

[apps/web/next.config.mjs](../../apps/web/next.config.mjs) `async headers()`
now appends `Content-Security-Policy-Report-Only` to the existing baseline
headers. The policy is built from a string array joined with `; ` so each
directive is one readable line in source, with an inventory comment block
documenting the choices.

```
default-src 'self'
script-src 'self' 'unsafe-inline' https://challenges.cloudflare.com
style-src 'self' 'unsafe-inline'
img-src 'self' data: blob: https://*.supabase.co https://*.supabase.in https://*.tile.openstreetmap.org
font-src 'self' data:
connect-src 'self' https://*.supabase.co https://*.supabase.in wss://*.supabase.co wss://*.supabase.in https://challenges.cloudflare.com
frame-src https://challenges.cloudflare.com
worker-src 'self' blob:
object-src 'none'
base-uri 'self'
form-action 'self'
frame-ancestors 'none'
upgrade-insecure-requests
```

## Decisions

- **Report-Only first.** AGENTS.md + the audit doc both call for a soak
  window; we have no production traffic data yet, so shipping the strict
  policy directly would risk a Saturday-morning fire when an unnoticed
  third-party assumption breaks. Browsers log violations to devtools and
  the Reporting API but do not block.
- **No `report-uri` / `report-to`.** Adding a reporting endpoint is out
  of scope for this bundle — devtools-console reports are enough for
  the local + Vercel preview soak. A future bundle can wire reports to
  Sentry or a custom collector if needed for production.
- **Keep `'unsafe-inline'` on `script-src`.** We render
  `<script type="application/ld+json">` for JSON-LD in
  [layout.tsx](../../apps/web/src/app/layout.tsx) and
  [event-jsonld.tsx](../../apps/web/src/app/events/[id]/_components/event-jsonld.tsx).
  CSP applies to all `<script>` elements regardless of `type`, so the
  alternatives are (a) nonces via middleware, (b) hashes per inline
  block. Both are larger refactors and gate on Next.js middleware
  shape — deferred to P2 #3a. `'unsafe-inline'` here is the practical
  no-regression starting point and is still a defense-in-depth win
  versus no CSP at all (inline `eval`, dynamic injection, etc. are all
  still constrained by the other directives).
- **Keep `'unsafe-inline'` on `style-src`.** Tailwind doesn't ship
  inline `<style>` blocks in production, but components do use `style`
  attributes (`<div style={{ height: '320px' }}>` for the map, a few
  dashboard widgets). Dropping `'unsafe-inline'` here would require a
  hash pipeline + audit every `style=` site. Standard cost/benefit for
  a Tailwind app — leave it for now.
- **`frame-ancestors 'none'`.** Same intent as the existing
  `X-Frame-Options: DENY` (open question in the audit doc asks whether
  any white-label embedders exist — assumed no, since none have been
  mentioned). Browsers prefer `frame-ancestors` when both are
  specified, so this is the modern equivalent and a safe duplicate.
- **No Stripe origins.** Confirmed by grepping for
  `@stripe/stripe-js` / `loadStripe` / `js.stripe.com` — zero hits.
  Checkout flow is a server-side `redirect()` to the hosted Checkout
  page. If we later add Stripe.js (Elements, Express Checkout, etc.),
  the CSP must add `https://js.stripe.com` to `script-src`,
  `https://api.stripe.com` + `https://*.stripe.com` to `connect-src`,
  and `https://js.stripe.com` to `frame-src`.
- **Sentry under `/monitoring` tunnel.** Because `tunnelRoute` proxies
  ingest events to the same origin, no `*.ingest.sentry.io` allowlist
  entry is needed. If we ever disable `tunnelRoute`, this needs
  revisiting — flagged in the inline comment block.

## Patterns observed

- **CSP inventory is mostly a grep exercise.** The vast majority of
  third-party origins are referenced as string literals in the codebase
  (`https://challenges.cloudflare.com`, `https://*.supabase.co` in
  `next.config.mjs` `images.remotePatterns`, `https://nominatim.openstreetmap.org`
  in geocode helpers). Future audits can re-run the same query
  (`stripe\.com|cloudflare|turnstile|openstreetmap|photon|sentry\.io|googleapis|gstatic|fonts\.`)
  as a smoke test.
- **Tunnels collapse CSP entries.** `tunnelRoute` for Sentry pays off
  again here — every third-party SDK that supports proxying ends up
  cheaper from a CSP allowlist perspective. Worth remembering if we
  add Stripe Elements or PostHog later.
- **Report-Only is the cheapest "ship now, harden later" lever.** Same
  policy bytes, no enforcement risk. Pair with a soak window before
  promoting.
